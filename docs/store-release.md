# ストアに出すとき / Androidのデベロッパー確認

いまのすくすく手帳は**ストアに出さず、家族の端末へ直接入れる**方針
（docs/native-app-rewrite.md §8）。その方針は変えない。ただし2026年にAndroid側の
前提が変わり、**身内配布にも「開発者として登録した鍵」が要る**流れになった。
そのぶんと、「将来ストアに出すアプリを作る」ときの型をここにまとめる。

結論を先に書く。

| | 家族用（このリポジトリ） | ストア用（将来の新しいアプリ） |
| --- | --- | --- |
| 置き場所 | このリポジトリのまま | **別リポジトリで新しく作る**（家族の個人データと混ぜない） |
| ビルド | GitHub Actions（手動実行）＋手元 | EAS Build（無料枠 Android 15本/月）。Actionsの枠を食わない |
| 署名 | **自分たちのkeystore**（§3） | **Play App Signing**（アップロード鍵はEASに預けるか自分で持つ） |
| 配布 | Firebase App Distribution | Google Play |
| 口座 | **限定配布アカウント（無料・ID不要・20台まで）**（§2） | Play Console（$25・1回・本人確認あり） |
| 出す前に要るもの | なし | クローズドテスト12人×14日、target API 36、AAB（§4） |

**いま手を打つ価値があるのは §3（署名鍵）だけ。** ほかは必要になった時点でよい。
鍵の入れ替えは**家族の端末でアプリを入れ直す**ことになるので、台数もデータも少ない
いまがいちばん安く済む。

---

## 1. なぜ今この話が出てくるのか

Googleが「Androidデベロッパー確認（Android developer verification）」を始めた。
**認定Android端末では、登録されていないパッケージ名のアプリが入らなくなる。**
ストアに出す/出さないに関わらず効くので、いまの `.apk` を直接入れるやり方も対象になる。

| 時期 | 何が起きるか |
| --- | --- |
| 2026年8月 | **限定配布アカウント**が誰でも作れるようになった（§2）。未確認の開発者のアプリを入れる「詳細な手順」も用意された |
| 2026年9月30日 | ブラジル・インドネシア・シンガポール・タイの対象ストアで施行。**日本はまだ対象外** |
| 2027年〜 | 世界へ拡大予定 |

- **ADB（USB接続でのインストール）は対象外。** 開発のための導線は残る
- Firebase App Distribution 経由のインストールは通常のインストールなので、
  日本へ拡大した時点で対象になるとみておく
- Play App Signing を使っているアプリは**自動で登録される**

つまり「日本に来る前に、パッケージ名と自分たちの鍵を登録できる状態にしておく」のが
やることで、その前提が §3 の鍵の入れ替えになる。

## 2. 限定配布アカウント（家族用はこれで足りる）

| | |
| --- | --- |
| 費用 | **無料** |
| 本人確認 | **政府発行IDの提出は不要** |
| 配れる台数 | **20台まで**（利用者が端末ごとに明示的に許可する） |
| 要るもの | Googleアカウント（2段階認証オン）／お支払いプロファイル（法的な氏名と住所）／連絡先メール |
| できないこと | Google Playでの配信。広く配ること |
| あとから | **通常アカウントへ移行できる**（逆は不可） |

家族2人・20台の枠なので、すくすく手帳はこれで収まる。日本での施行が近づいたら作る。
そのときに登録するのが「パッケージ名 `com.sukusuku.app` ＋ 署名鍵」なので、
**鍵が自分たちのものになっている必要がある**。

## 3. 署名鍵をExpoのdebug鍵から自分たちの鍵へ移す

### いまの状態と問題

`npx expo prebuild` が作る `android/` には、Expoのテンプレートに入っている
**debug用のkeystore**があり、`assembleRelease` もそれで署名している。
これは**誰のExpoプロジェクトにも同じものが入っている共有の鍵**なので、
「このアプリは自分たちのものだ」と示す役に立たない。登録にも向かない。

### 手順（初回だけ）

手元（Windows）のPowerShellで行う。`keytool` はJDKに入っている
（docs/mobile-local-build.md §1 で入れたもの）。

```powershell
# 1. 鍵を作る（有効期限は長めに。無くすと同じアプリとして更新できなくなる）
& "$env:JAVA_HOME\bin\keytool.exe" -genkeypair -v `
  -keystore sukusuku-release.keystore `
  -alias sukusuku `
  -keyalg RSA -keysize 2048 -validity 10000

# 2. Base64にする（Windowsには base64 コマンドが無いのでPowerShellで作る）
[Convert]::ToBase64String([IO.File]::ReadAllBytes("$PWD\sukusuku-release.keystore")) `
  | Set-Content -NoNewline keystore.base64
```

`keystore.base64` をメモ帳で開き、中身をまるごとコピーして次の Secret に貼る。

リポジトリの Settings > Secrets and variables > Actions に登録する。

| Secret | 中身 |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | 手順2の中身 |
| `ANDROID_KEYSTORE_PASSWORD` | keystoreのパスワード |
| `ANDROID_KEY_ALIAS` | `sukusuku`（手順1の `-alias`） |
| `ANDROID_KEY_PASSWORD` | 鍵のパスワード（keytoolで別に聞かれる。同じでもよい） |

**keystoreファイル本体はリポジトリに入れない。** 無くすと詰むので、
パスワードと一緒に手元＋別の場所（NAS・パスワードマネージャ）に控える。

### CI側

`.github/workflows/mobile-apk.yml` に「自分たちの鍵で署名し直す」工程を入れてある。

- `ANDROID_KEYSTORE_BASE64` が**未登録のあいだは何もしない**（今までどおりdebug鍵）
- 登録した時点から、ビルドした `.apk` を `apksigner` で署名し直す
- どの鍵で署名されたかは実行ログ（`apksigner verify --print-certs`）で確かめられる

### 切り替えるときに起きること

**署名が変わると上書きインストールができない。** 新しい鍵で署名した最初の `.apk` は、
家族の端末で**いったんアンインストールしてから**入れる。

| 消えるもの | 残るもの |
| --- | --- |
| ログイン状態（入れ直したあと1回ログインする） | 予定・記録・リストなどSupabase側のデータ全部 |
| 端末内の控え（`src/lib/offline/`）。**送信待ちの記録があると消える**ので、圏外で付けた記録が残っていないか確かめてから入れ替える | |
| 設定タブの通知のオン/オフ（端末ごとに入れ直す） | |

手元でビルドするときも同じ鍵で署名する必要がある（docs/mobile-local-build.md §5）。

## 4. ストアに出すアプリを作るときの型

将来「公開用のアプリ」を作るときは、このリポジトリを作り変えるのではなく
**別のリポジトリで新しく作る**。すくすく手帳は家族の個人データ（子の記録・保活・
氏名）が仕様書ごと入っているため、公開を前提にした作りと混ぜない。

そのうえで、最初から次の形にしておくと後戻りがない。

| 決めごと | 最初からこうする | 理由 |
| --- | --- | --- |
| 署名 | **Play App Signing**（Googleが配信用の鍵を持ち、こちらはアップロード鍵を持つ） | アップロード鍵を無くしても復旧できる。デベロッパー確認の登録も自動 |
| ビルド | **EAS Build**（無料枠 Android 15本/月） | 鍵の管理・AAB生成・ストア提出（EAS Submit）まで面倒を見る。Actionsの無料枠を消費しない |
| 成果物 | **AAB**（`.aab`）。`.apk` はストアに出せない | 新規アプリはAAB必須 |
| target API | **API 36（Android 16）以上** | 2026年8月31日以降、新規アプリも更新もこれ未満は出せない（延長申請で2026年11月1日まで）。Expo SDK 54はこの世代だが、出す前に `android/build.gradle` で実際の値を確かめる |
| アカウント | Play Console（**$25・1回**） | 2023年11月13日以降に作った**個人**アカウントは、製品版に出す前に**12人以上のテスターで14日間連続のクローズドテスト**が要る（2024年12月に20人→12人へ緩和）。人を集める時間を見込んでおく |
| versionCode | CIの実行番号など**単調増加する値**を焼き込む | 手で管理すると必ずどこかで下がる（このリポジトリと同じ仕組みでよい） |
| iOSも出すなら | Apple Developer Program（**$99/年**）とMacまたはEAS Build | Androidだけなら要らない |

**順番**: ①作る → ②EAS Buildで内部テスト版を出す → ③クローズドテスト（12人×14日）→
④製品版へのアクセスを申請 → ⑤公開。③が実時間で効いてくるので、公開したい日から
逆算して1か月は見ておく。

## 5. 検討して見送ったもの

| 見送るもの | 理由 |
| --- | --- |
| すくすく手帳そのものをストアに出す | 家族の個人データを前提にした作りで、他人が使えるものではない。審査・サポート・プライバシーポリシーの手間だけが増える |
| いますぐ限定配布アカウントを作る | 日本はまだ施行対象外。§3の鍵さえ先に済ませておけば、必要になってから作れば間に合う |
| ストア用アプリもGitHub Actionsでビルドする | 鍵とAABとストア提出をすべて自前で書くことになる。EAS Buildの無料枠のほうが速くて安い。Actionsの無料枠は口座単位で共有なので、アプリが増えるほど食い合う |
| CIをやめて手元ビルドだけにする | 「誰の環境でも同じものが出る」保証が無くなる。配るものはCIで作り、日々の確認は手元、の分担にする |
