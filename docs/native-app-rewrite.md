# ネイティブへ作り直す（案D）— 進め方

[ネイティブアプリ化の検討](./native-app.md)の案D（React Nativeで画面ごと作り直す）を
選ぶことにした。その前提での、**どこに作るか・何が持っていけるか・どの順で進めるか**の
メモ。

## なぜ殻（案B）をやめたか

Capacitorの殻はVercel上のPWAをWebViewで開くだけなので、**中身は今のWebのまま**。
授乳アラームは直るが、それ以外は何も変わらない。狙いが「授乳アラーム」から
「アプリの作りそのものをネイティブにする」へ動いたので、殻では届かない。

案Dで初めて手に入るもの:

- **圏外でも使える。** 端末にデータを持って同期する形にできる。殻では白紙のまま
- **起動が速い。** 画面が端末の中にあるので、Vercelへの往復を待たない
- 通知・音・振動・常駐通知・ウィジェットが、回避策なしにOSの作法で書ける
- 画面の動き（スクロール・戻る・キーボード）が端末の作法どおりになる

代わりに払うもの: **画面はまるごと書き直し**。次の§2で実際の量を出す。

---

## 1. どこに作るか

**別リポジトリにはしない。いまのリポジトリに `mobile/` を独立したプロジェクトとして足す。**
「同じプロジェクトを書き換える」形にもならない（Next.jsとReact Nativeは同居できないため、
`src/` を直していく進め方にはできない）。

```
sukusuku/
├ src/          ← 今のPWA。凍結したまま置いておく（移行が終わるまで動かさない）
├ supabase/     ← 共通のバックエンド。PWAとネイティブの両方から使う
├ mobile/       ← 追加。Expo(React Native)の独立したプロジェクト
│   ├ package.json    ← 依存はこちらで完結させる（ルートとは混ぜない）
│   ├ app/            ← 画面
│   └ android/        ← `expo prebuild` で生成。前面サービスのKotlinもここ
└ docs/
```

### 同じリポジトリに置く理由

- **バックエンドが共通で、作り直しの途中で必ず触るから。** FCMのトークンを置くテーブル、
  Web Pushの送信経路の分岐など、`supabase/` への変更とそれを使うクライアントは対で動く。
  リポジトリが分かれると、スキーマの変更と利用側が別々にマージされることになる。
- **移行期は2つのクライアントが同じDBを触るから。** Android 2台がネイティブへ移っても、
  Mac/iPhoneはPWAのまま残る（§5）。片方の都合だけでスキーマを変えられない状態が続くので、
  両方が1つのリポジトリで見えている方が安全。
- 検討の経緯（`docs/`）が既にここにある。

### ルートとは混ぜない

- ルートの `package.json` / `tsconfig.json` / `eslint.config.mjs` は**触らない**。
  `mobile/` が自分のものを持つ。
- **npm workspacesにはしない。** Next.js 16 とExpoはReactの要求バージョンが別々に動くので、
  `node_modules` を共有すると解決できなくなる。`mobile/` で `npm install` する。
- Vercelは今までどおりルートのNext.jsだけを見る。`mobile/` は素通りする。

### 共有パッケージは作らない

`src/lib` の計算やAPI層を `packages/core` に切り出して両方から使う形は、**採らない**。
PWAは凍結して最後は畳む前提なので、共有の受け皿を整備するコストが回収できない。
持っていける部分は `mobile/` へ**コピーして**持っていく。凍結側は動かないので、
コピーが分岐していく心配も小さい。

## 2. 何が持っていけて、何が書き直しか

`src` 配下は全部で約10,900行。内訳と扱いは次のとおり。

| 区分 | 行数 | 扱い |
| --- | ---: | --- |
| 画面（`src/components/`） | 6,375 | **全部書き直し。** Tailwind + DOM 前提なので移せない |
| ルーティング・認証（`src/app/`, `src/proxy.ts`） | 約700 | 作り直し。考え方が別物（§3） |
| 計算・API層（`src/lib/api/*`, `dateUtils`, `careLogUtils`, `feedingSchedule`, `milestones`, `nurseryChecklist`, `seedData`） | 約1,500 | **そのまま持っていける。** 素のTypeScript |
| 型（`src/types/`） | 1,044 | そのまま。`supabase.ts` は生成し直す |
| 端末に張り付いた部分（`alarm.ts`, `nursingTimer.ts`, `push.ts`, `nursingAlarmSync.ts`） | 約830 | **規則は残し、鳴らし方は作り直す**（§4） |

ざっくり **書き直しが約7,000行、持っていけるのが約2,500行**。

### 置き換えの対応表

| 今 | ネイティブ側 |
| --- | --- |
| Tailwind CSS | NativeWind（クラス名の書き方をほぼ保てる）か `StyleSheet` |
| `lucide-react`（25箇所） | `lucide-react-native`。ほぼ同じ名前で入れ替わる |
| `recharts`（成長曲線・記録タブ） | `victory-native` か `react-native-svg` で描き直し |
| Next.js App Router / `src/proxy.ts` | Expo Router |
| Supabase SSR（Cookie・`getClaims()`・サーバー側の先読み） | セッションを端末に保存する形へ。**先読みの設計は作り直し**（§3） |
| Web Audioでの音の合成（`alarm.ts`） | 前面サービス + `USAGE_ALARM`（鳴らし分けは完全に再現できる） |
| Web Push + Service Worker（`sw.js`） | FCM + ローカル通知 |
| `<input type="file">` での書類アップロード | `expo-document-picker` / `expo-file-system` |

## 3. 認証と初回表示は考え方から変わる

いまは**サーバー側で**セッションを検証し、ついでに最初のデータまで取ってから画面を返している
（`src/app/page.tsx` の `getClaims()` と `listTasks()` の先読み、`src/proxy.ts` の振り分け）。
これは起動を速くするために入れたもの（README「起動パフォーマンス上の設計方針」）だが、
**ネイティブにはサーバー側が無いので、そのままは持っていけない**。

代わりにネイティブでは、

- セッションは端末に保存され、**起動時にはもうログイン済み**（毎回の検証の往復が要らない）
- 画面は端末内にあるので**すぐ出る**。データは出したあとに埋まる形になる
- そのため「最初の1画面ぶんを端末に控えておく」設計が効く。これは§6のオフライン対応と
  同じ仕組みで済むので、まとめて考える

つまり**速さの出どころが「サーバーで先に取る」から「端末に持っている」へ移る**。
移植ではなく作り直しになるのはこの部分。

## 4. 授乳アラームは調べ済みのものを使う

鳴らし分け（**短い「ピッ」＝5分 / 長い「ポーン」＝30分**）を保ったまま確実に鳴らす方法は、
[Capacitor版の設計メモ](./native-app-android.md)の§3で調べ終わっている。
**結論は作り直しでもそのまま使える**（案②＝授乳中だけ前面サービスを動かす）。

- ローカル通知を並べる案①は、Android 8以降で音と振動がチャンネルに固定されるため
  鳴らし分けができない。前面サービスなら音も振動も自由に組める
- 常駐通知に「授乳 12分 左」と出せるので、聞き逃しても通知バーで分かる
- `AudioAttributes` を `USAGE_ALARM` にすればマナーモードでも鳴る
- 端末のバッテリー最適化から除外する設定を1回入れておく

`src/lib/alarm.ts` の**長短の組み立ての規則はそのまま持っていく**（体で覚えている部分なので
実装が変わっても意味は変えない）。`nursingTimer.ts` の計測そのもの（左右の累積、
何回目まで鳴らしたか）も規則としては持っていけるが、置き場所は前面サービス側へ移る。

サーバー予約のWeb Push（`nursing_alarms`・1分おきのcron・`send-nursing-alarms`）は、
ネイティブで鳴るようになった時点で役目が終わる。PWAを畳むときに一緒に片付ける。

## 5. 先に決めたいこと — Mac と iPhone をどうするか

いま通知を登録しているのは **Android 2台と Mac 1台**。

殻（案B）ではPWAが共通の画面だったのでMacは何も失わなかったが、**案DではPWAとネイティブが
別のコードベースになる**ので、これ以降の作り込みは自動的にAndroid側にだけ乗る。
どう畳むかで§7のフェーズ2以降の行き先が変わるので、先に決めたい。

| | 中身 | 代償 |
| --- | --- | --- |
| **(a) PWAを凍結したまま残す** | Macは「今できること」だけできる | 機能差が開いていく。ただし追加の作業はゼロ |
| **(b) React Native for Web で1本にする** | 画面をネイティブとWebで共用する | Web側の作り込みが増え、§3の先読みの利点は捨てる |
| **(c) PWAを畳む** | Androidの2台だけにする | Macから使えなくなる |

**(a) を既定にしておく**のが素直。凍結したPWAは動かさなければ壊れないので、置いておく費用は
実質ゼロ。(b) は「両方で同じ画面を使いたい」と実際に困ってから考えれば足りる。

## 6. オフライン対応は自動では手に入らない

[検討メモ](./native-app.md)の§1-2に書いたとおり、**ネイティブにしただけでは圏外で使えない**。
データはSupabaseにあるので、端末側に持つ仕組みを別に作って初めて圏外で開ける。

- 端末内に控える（`expo-sqlite` など）＋ オンラインになったら同期する、の設計が要る
- 記録（授乳・おむつ・搾乳）は**圏外でも付けられて、後から送られる**のが望ましい。
  授乳中に電波が悪くて記録できないのは、いちばん困る形の失敗
- 予定やメモは読めれば足りることが多いので、書き込みの同期まで作るかは分けて考えてよい

**案Dを選ぶ理由の中でいちばん大きいのがここ**なので、「画面を移し終わったら考える」ではなく、
記録まわりを作るとき（§7のフェーズ1）に一緒に設計する。

## 7. 進める順番

| フェーズ | やること | 終わったとき |
| --- | --- | --- |
| **0. 土台** | `mobile/` にExpoを置き、Supabaseへログインできるところまで。ロジック（約1,500行）を移植 | 実機で自分のデータが1つ読める |
| **1. 授乳** | 記録タブの授乳まわりの画面＋前面サービス（Kotlin）＋端末内に控える仕組み（§6） | **授乳だけネイティブで回せる。**他はPWAで見る |
| **2. 残りの画面** | ホーム / 予定 / メモ / 情報 の各タブ | Android 2台がネイティブ1本になる |
| **3. 通知をFCMへ** | `supabase/functions/*` に送信経路を追加、トークンのテーブル | 予定のリマインダーがネイティブに届く |
| **4. 畳む** | §5で決めた形にする。`nursing_alarms` とcronを片付ける | `src/` を消してリポジトリを整理できる |

- **フェーズ1で一度実機に入れて使う。** ここで当初の目的（授乳アラーム）は達成されるので、
  フェーズ2が長引いても困らない状態を先に作る。
- フェーズ1と2の間はAndroidに**ネイティブとPWAのアイコンが2つ並ぶ**。
  授乳はネイティブ、それ以外はPWA。
- PRは画面1つ＝1PRくらいに切る。ロジックの移植は画面より先に入れておく。

## 8. ビルドと配布

- **ストアには出さない。** `.apk` を自分たちの端末に直接入れる。審査も登録も要らない。
- ビルドは手元のPC（Android Studio / `./gradlew`）か EAS Build。Macは要らない。
  **いまのClaude Code側の環境にはAndroid SDKが無いのでビルドは通せない。**
  コードを書くのがこちら、`.apk` を作って実機で試すのが手元、という分担になる。
- **署名鍵(keystore)は1つ作って保管し、リポジトリにはコミットしない**（`.gitignore` へ）。
  無くすと同じアプリとして更新できなくなる。
- 殻と違い**画面が端末の中にあるので、変更のたびに入れ直しが要る**。
  ここは案Bより手間が増えるところ（Expoの開発ビルドを入れておけば、
  開発中は入れ直さずに更新を反映できる）。
