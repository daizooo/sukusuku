## なぜ殻（案B）をやめたか

Capacitorの殻はVercel上のPWAをWebViewで開くだけなので、**中身は今のWebのまま**。
授乳アラームは直るが、それ以外は何も変わらない。狙いが「授乳アラーム」から
「アプリの作りそのものをネイティブにする」へ動いたので、殻では届かない。

案Dで初めて手に入るもの:

- **圏外でも使える。** 端末にデータを持って同期する形にできる。殻では白紙のまま
- **起動が速い。** 画面が端末の中にあるので、Vercelへの往復を待たない
- 通知・音・振動・常駐通知・ウィジェットが、回避策なしにOSの作法で書ける
- 画面の動き（スクロール・戻る・キーボード）が端末の作法どおりになる

代わりに払うもの: **画面はまるごと書き直し**。次の§2で実際の量を出す。

## 1. どこに作るか

**別リポジトリにはしない。いまのリポジトリに `mobile/` を独立したプロジェクトとして足す。**
「同じプロジェクトを書き換える」形にもならない（Next.jsとReact Nativeは同居できないため、
`src/` を直していく進め方にはできない）。

```
sukusuku/
├ src/          ← 今のPWA。ネイティブ側はここに準拠する。通知はフェーズ3までこちらで受け取る
├ supabase/     ← 共通のバックエンド。PWAとネイティブの両方から使う
├ mobile/       ← 追加。Expo(React Native)の独立したプロジェクト
│   ├ package.json    ← 依存はこちらで完結させる（ルートとは混ぜない）
│   ├ app/            ← 画面
│   └ android/        ← `expo prebuild` で生成。前面サービスのKotlinもここ
└ docs/
```

### 同じリポジトリに置く理由

- **バックエンドが共通で、作り直しの途中で必ず触るから。** FCMのトークンを置くテーブル、
  Web Pushの送信経路の分岐など、`supabase/` への変更とそれを使うクライアントは対で動く。
  リポジトリが分かれると、スキーマの変更と利用側が別々にマージされることになる。
- **移行期は2つのクライアントが同じDBを触るから。** Android 2台が順にネイティブへ移る間、
  まだ移っていない側はPWAのまま残る（§5）。片方の都合だけでスキーマを変えられない状態が
  続くので、両方が1つのリポジトリで見えている方が安全。
- 検討の経緯（`docs/`）が既にここにある。

### ルートとは混ぜない

- ルートの `package.json` / `tsconfig.json` / `eslint.config.mjs` は**触らない**。
  `mobile/` が自分のものを持つ。
- **npm workspacesにはしない。** Next.js 16 とExpoはReactの要求バージョンが別々に動くので、
  `node_modules` を共有すると解決できなくなる。`mobile/` で `npm install` する。
- Vercelは今までどおりルートのNext.jsだけを見る。`mobile/` は素通りする。

### 共有パッケージは作らない

`src/lib` の計算やAPI層を `packages/core` に切り出して両方から使う形は、**採らない**。
PWAは凍結して最後は畳む前提なので、共有の受け皿を整備するコストが回収できない。
持っていける部分は `mobile/` へ**コピーして**持っていく。凍結側は動かないので、
コピーが分岐していく心配も小さい。

## 2. 何が持っていけて、何が書き直しか

`src` 配下は全部で約10,900行。内訳と扱いは次のとおり。

| 区分 | 行数 | 扱い |
| --- | ---: | --- |
| 画面（`src/components/`） | 6,375 | **全部書き直し。** Tailwind + DOM 前提なので移せない |
| ルーティング・認証（`src/app/`, `src/proxy.ts`） | 約700 | 作り直し。考え方が別物（§3） |
| 計算・API層（`src/lib/api/*`, `dateUtils`, `careLogUtils`, `feedingSchedule`, `milestones`, `nurseryChecklist`, `seedData`） | 約1,500 | **そのまま持っていける。** 素のTypeScript |
| 型（`src/types/`） | 1,044 | そのまま。`supabase.ts` は生成し直す |

## 3. 認証と初回表示は考え方から変わる

いまは**サーバー側で**セッションを検証し、ついでに最初のデータまで取ってから画面を返している
（`src/app/page.tsx` の `getClaims()` と `listTasks()` の先読み、`src/proxy.ts` の振り分け）。
これは起動を速くするために入れたもの（README「起動パフォーマンス上の設計方針」）だが、
**ネイティブにはサーバー側が無いので、そのままは持っていけない**。

代わりにネイティブでは、

- セッションは端末に保存され、**起動時にはもうログイン済み**（毎回の検証の往復が要らない）
- 画面は端末内にあるので**すぐ出る**。データは出したあとに埋まる形になる
- そのため「最初の1画面ぶんを端末に控えておく」設計が効く。これは§6のオフライン対応と
  同じ仕組みで済むので、まとめて考える

つまり**速さの出どころが「サーバーで先に取る」から「端末に持っている」へ移る**。
移植ではなく作り直しになるのはこの部分。

## 4. 授乳アラームは調べ済みのものを使う

確実に鳴らす方法は、[Capacitor版の設計メモ](./native-app-android.md)の§3で調べ終わっている。
**結論は作り直しでもそのまま使える**（案②＝授乳中だけ前面サービスを動かす）。

- ローカル通知を並べる案①は、Android 8以降で音と振動がチャンネルに固定されるため
  鳴らし方を自分で決められない。前面サービスなら音も振動も自由に組める
- 常駐通知に「授乳 3分 左」と出せるので、聞き逃しても通知バーで分かる
- `AudioAttributes` を `USAGE_ALARM` にすればマナーモードでも鳴る
- 端末のバッテリー最適化から除外する設定を1回入れておく

> **鳴らし方は凍結中にPWA側で変わった。** 検討時の「短い『ピッ』＝5分 / 長い『ポーン』＝30分」で
> 経過時間そのものを伝える形は、授乳が**セット制**（左5分 → 右5分 → ゲップ5分）へ作り直された
> ときに役目を終えている。いまは**区切りが5分に達したら1回だけ鳴らす**（伝えたいのは経過時間
> ではなく「次へ移る合図」）。長短の組み立ての規則そのものは `alarmPattern.ts` /
> `AlarmPattern.kt` にPWA版と同じ形で残してあり、実際に鳴るのは短音1回になる。

`nursingTimer.ts` の計測そのもの（区切りごとの累積、セットの数え方）は規則として持っていけるが、
鳴らす置き場所は前面サービス側へ移る。ゲップの5分まで終わったらそのセットを締めるのは、
アプリを閉じている間はサービス側、開いているときはアプリ側が行う。

サーバー予約のWeb Push（`nursing_alarms`・1分おきのcron・`send-nursing-alarms`）のうち、
**鳴らす役目はネイティブで鳴るようになった時点で終わっている**（`send-nursing-alarms` は
ネイティブの宛先へは送らない）。PWAを畳むときに一緒に片付ける。

ただし `nursing_alarms` の行そのものは**ネイティブ版でも預ける**。この表にはもう1つ
「いま授乳中だから『そろそろ次の授乳』を送らない」という役目があり、預けないと
飲ませ終えたばかりなのに家族全員へ通知が飛ぶ（docs/notifications.md §11）。
PWAを畳んだあとも、この役目のほうは残る。

## 5. Webをどうするか — Androidネイティブ1本にする（決定）

求めるものが**「ネイティブアプリ並みに正確でリアルタイムな通知・アラーム・バイブ」**と
**「今後の多機能化に備えること」**なので、**Expo(React Native)でAndroidネイティブを1本作り、
今のPWAは凍結してVercelに置いたまま**にする。

**iPhone / Macは考えない。** 2026-09-18に、家族の誰もiPhoneでは使っていないことを確認した。
Webに残す理由はこれで無くなったので、あとは§7のフェーズ4の条件が済めば畳める。

### なぜ「WebとAndroidを1コードベースで」にしないか

React Native for Web で Web にも出す案は、**求めている要件と正面からぶつかる**ので採らない。

- **通知とアラームはWebでは原理的に満たせない。** Web Push経由になるのでcronの粒度ぶん遅れ、
  鳴らし分け（ピッ＝5分 / ポーン＝30分）はできず、通知チャンネル任せになる。
  つまりWebにも出すということは、**いちばん大事な機能について常に2つの実装
  （ネイティブの前面サービスと、Webのフォールバック）を抱え続ける**ということ。
- **多機能化の足かせになる。** ウィジェット、常駐通知からの操作、バックグラウンド同期、
  共有シートからの書類の取り込み、カメラ直結——ネイティブ寄りの機能を足すたびに
  「Webではどうするか」の分岐が増える。
- Expo Web は静的書き出しなので、いまの起動速度の作り込み（§3のサーバー側先読み）を
  捨てることになり、**Web版はむしろ今より遅くなる**。

Macを考えないなら、Webを出す理由は「あれば便利」程度しか残らない。
要件のために払う代償として割に合わない。

### なぜ殻（Capacitor）でもないか

前面サービスを入れれば通知とアラームの要件は満たせるが、**多機能化で毎回WebViewの制約に
当たる**。WebViewにはPush APIもNotification APIも無いので、通知を伴う機能はすべて
ブリッジ越しの作り込みになる。1つ目の機能で得をして、2つ目以降で払い続ける形になる。

### 凍結したPWAはどうするか

消さずにVercelに置いたままにする。動かさなければ壊れないので、置いておく費用は実質ゼロ。
役割は§9のとおり縮んでいき、要らなくなった時点で畳む。

## 6. オフライン対応は自動では手に入らない

[検討メモ](./native-app.md)の§1-2に書いたとおり、**ネイティブにしただけでは圏外で使えない**。
データはSupabaseにあるので、端末側に持つ仕組みを別に作って初めて圏外で開ける。

- 端末内に控える（`expo-sqlite` など）＋ オンラインになったら同期する、の設計が要る
- 記録（授乳・おむつ・搾乳）は**圏外でも付けられて、後から送られる**のが望ましい。
  授乳中に電波が悪くて記録できないのは、いちばん困る形の失敗
- 予定やメモは読めれば足りることが多いので、書き込みの同期まで作るかは分けて考えてよい

**案Dを選ぶ理由の中でいちばん大きいのがここ**なので、「画面を移し終わったら考える」ではなく、
記録まわりを作るとき（§7のフェーズ1）に一緒に設計する。

### フェーズ4（畳む）に入る条件

iPhone / Macを考えないことが決まった（§5）ので、**PWAを恒久的に残す理由はもう無い。**
残っているのは次の4つで、上から順に片付ける。

| | 条件 | 状態 |
| --- | --- | --- |
| A | ネイティブ版の通知が実機に届くこと | **済**（2026-09-18、予定のお知らせが実機に出ることを確かめた） |
| B | 用が済んだ通知を消すこと（PWA版の `notificationCleanup.ts`）をネイティブ版へ移す | **済**（2026-09-18、`mobile/src/lib/notificationCleanup.ts`） |
| C | `/auth/confirm` の受け口をディープリンクへ移す（§9） | **済**（2026-09-18、`mobile/app/auth/confirm.tsx`。Supabaseへの登録だけ手元に残る） |
| D | Web Pushの経路を片付ける（`_shared/webpush.ts`・`VAPID_KEYS`・`kind = 'webpush'` の行） | **送る側は済**（2026-09-18）。残りはPWA版・鍵・行の片付け |

- **Bは埋まった。** これで、畳んだときに減る機能は無くなった。
- **Cも埋まった。** ネイティブ版に新規登録と確認リンクの受け口が入ったので、
  Vercelを畳んでも登録ができる。ただし**SupabaseのRedirect URLsに `sukusuku://**` を
  足すまでは働かない**（手元でしかできない。mobile/README.md）。
- **Android 2台の両方が移り終えていること**も前に要る。`kind = 'fcm'` の宛先を持たない人が
  残っていれば、その人はPWA版でしか通知を受け取れない（docs/notifications.md §11）。
- **Dは2段階で進めている。** 第1段（済）は送る側の撤去だけ。`_shared/webpush.ts` を消し、
  配信は `kind = 'fcm'` の宛先だけに絞った。**`VAPID_KEYS` は消していない**ので、戻すのは
  鍵ではなくコードを戻すだけで済む。第2段でPWA版・鍵・`webpush` の行を片付ける。
- **急ぐ理由は無い。** VercelはHobbyなので置いたままでも費用はかからず、凍結している限り
  差分も出ない。畳んで得られるのは「リポジトリの見通し」だけで、失うのは**ネイティブ版が
  壊れたときの退路**（PWAはURLを開くだけだが、ネイティブ版は `.apk` を入れ直す）。
- `src/` を消すのは最後。デプロイを止めてしばらく置き、困らないと分かってからでよい。

## 8. ビルドと配布

- **ストアには出さない。** `.apk` を自分たちの端末に直接入れる。審査も登録も要らない。
- **`.apk` はPRごとにCIで作る**（`.github/workflows/mobile-apk.yml`）。
  `mobile/` を触ったPRでGitHub Actionsが走り、実行ページの Artifacts から `.apk` を
  落として端末に入れられる。`src/` がVercelのプレビューで確かめられるのと同じ形を
  ネイティブ側にも用意したもので、**これが凍結の原因（実機で一度も動かないまま
  積み上がること）への手当て**にあたる。
  - 初回だけ、リポジトリの Settings > Secrets and variables > Actions に
    `EXPO_PUBLIC_SUPABASE_URL` と `EXPO_PUBLIC_SUPABASE_ANON_KEY` を登録する
    （Web版の `.env.local` と同じ値）。ビルド時にJSへ埋め込まれるため、
    未登録だとCIは「登録してください」と言って止まる。
  - 署名はExpoが用意するdebug用の鍵のまま。ストアに出さないので足りる。
    自分たちの鍵に変えるのは、入れ替えの手順を固めてからでよい。
  - **作るのは arm64-v8a のぶんだけ**（`-PreactNativeArchitectures=arm64-v8a`）。
    既定の4つ（armeabi-v7a / arm64-v8a / x86 / x86_64）ぶんネイティブをビルドすると、
    そこだけで37分かかる（実測。ほかの工程は全部で2分弱）。入れる端末はどちらもarm64
    なので、残りは作っても使わない。エミュレータ用のx86系が要るときは手元で作る。
  - **mainへのpushでは作らない。** PRで作ったものと中身が同じで、1つの変更あたりの
    所要時間とActionsの消費が倍になるため。マージ後の分が要るときはActionsのページから
    手で走らせる（PRのArtifactsは30日残るので、普段はそちらで足りる）。
- 手元でも作れる。Android Studio か `./gradlew`、あるいは EAS Build。Macは要らない。
  **Claude Code側の環境にはAndroid SDKが無いのでここでは通せない**ので、
  コードを書くのがこちら、実機に入れて使うのが手元、という分担は変わらない。
- **署名鍵(keystore)は1つ作って保管し、リポジトリにはコミットしない**（`.gitignore` へ）。
  無くすと同じアプリとして更新できなくなる。
- 殻と違い**画面が端末の中にあるので、変更のたびに入れ直しが要る**。
  ここは案Bより手間が増えるところ（Expoの開発ビルドを入れておけば、
  開発中は入れ直さずに更新を反映できる）。

## 9. 今のデータとVercelはどうなるか

### データは全部引き継がれる。移行作業はゼロ

実データはすべてSupabase側にあり、**クライアントを作り直しても一切触らない**。
同じプロジェクトに同じアカウントでログインすれば、今までの記録がそのまま出る。
エクスポート／インポートも移行スクリプトも要らない。

- **15テーブル** — `care_logs`（授乳・おむつ・搾乳）・`tasks`・`growth_records`・
  `family_profiles`・`nurseries`・`gifts`・`documents`・`children`・`families`・`users` ほか
- **Storageの `documents` バケット** — アップロードした書類の実体
- RLSは `family_id` で効いているので、そのまま同じ見え方になる
- ログインはメール＋パスワード（`signInWithPassword`）なので、ネイティブでもそのまま使える

引き継がれないのは**端末の中にしか無い3つ**だけで、どれも実害はない。

| もの | 中身 | どうなる |
| --- | --- | --- |
| `sukusuku:activeNursing` | 計測中の授乳の途中経過 | 引き継がれない。「今まさに授乳中」の一時値なので問題なし |
| `sukusuku:nursingAlarm` | アラームの音・バイブ・間隔の設定 | 入れ直し（数タップ）。`feeding_settings` はDB側なので残る |
| `push_subscriptions` の行 | Web Pushの購読（端末＋ブラウザ紐づけ） | FCMのトークンとして登録し直し。古い行は掃除する |

### Vercelはアプリの経路から外れる

**ここが殻（案B）との決定的な違い。** 殻はVercelのURLを開くのでVercelが落ちるとアプリが
白紙になるが、**ネイティブはSupabaseへ直接つながるのでVercelを経由しない**。
通知の送り主（`send-reminders` などのEdge Function）もSupabase側にあり、Vercelとは無関係。
コード上もVercelに依存している箇所は無い。

Vercelプロジェクトは**残すが、役割が縮んでいく**。

| 時期 | Vercelの役割 |
| --- | --- |
| フェーズ0〜1 | 凍結したPWAを配信。ネイティブがまだ授乳しか持たないので、他のタブはここで見る |
| フェーズ2以降 | 画面としての役目は終わる。残るのは**メール確認リンクの受け口**（`/auth/confirm`） |
| 条件C以降 | その受け口もアプリへ移った（下記）。Vercelはもう経路に居ない |
| 畳んだあと | デプロイを止める。Hobbyプランなら費用は元々かからない |

**`/auth/confirm` だけは注意が要る。** サインアップ確認メールのリンクはURLを開くので、
受け口がどこかに要る（`src/app/auth/confirm/route.ts`）。選択肢は2つ。

- **凍結したPWAをそのまま受け口として残す**（楽。Vercelを畳まなければ何もしなくてよい）
- **ディープリンクに変える**（`emailRedirectTo` をアプリのスキームへ向け、
  SupabaseのRedirect URLに登録する。Vercelを完全に畳める）

家族2人が既にログイン済みで、新規のサインアップがめったに起きないなら、
**前者のまま置いておくので足りる**。

### 2026-09-18、後者（ディープリンク）を採った

畳むのが決まった以上、**Vercelを畳まないことを前提にした手当ては先送りにしかならない**ため、
受け口ごとアプリへ移した。

- `mobile/app/auth/confirm.tsx` が `sukusuku:///auth/confirm` を受け、
  確かめる順序も行き先もPWA版（`src/app/auth/confirm/route.ts`）と同じにしてある
- ネイティブ版のログイン画面に**新規登録を足した**（PWA版と同じ切り替え・同じ文言）。
  `emailRedirectTo` は `Linking.createURL('/auth/confirm')` で作る
- Supabaseのクライアントを `flowType: 'pkce'` にした。既定の implicit は
  `#access_token=…` の断片で戻るため、ディープリンクでは拾えない
- **手元に残る作業が1つある。** Supabaseの Authentication > URL Configuration の
  Redirect URLs に `sukusuku://**` を足すこと。ここに無いリンクは戻ってこない
