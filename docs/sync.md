# 他の端末での変更を画面へ届ける仕組み（変更台帳 family_sync）

2026-10-09 に決めた。妻が記録した授乳が夫の画面に出ない、が発端。

## 1. 困りごとと原因

- 各タブは起動時に1回読んだきり。タブは一度開くと残るので、パートナーの端末での変更は
  アプリを開き直すまで出ない（家計・リスト・暮らしも同じ）
- Realtime は使っておらず、読み直すきっかけが育児タブの「授乳中の印」の1分ごとの確認しか無かった
- 実測: 本番DBには16:49・17:21の授乳があるのに、画面は14:19のまま。「次の授乳の目安」も古い記録から計算されていた

## 2. 仕組み

```
共有表への書き込み ──(DBトリガ)──▶ family_sync.changed[表名] = 時刻
                                         │ Realtime（この1表だけ。行の中身は載らない）
                                         ▼
アプリ: FamilySyncProvider（台帳の1行を見張る）
   ├─ Realtime で届く
   ├─ 前面へ戻ったとき・つながり直したとき・Realtime が切れているときに1回読む
   ▼
各画面: useFamilyRefresh(['表', …], 読み直す関数)
        自分の表の時刻が前と違うときだけ、その画面が読み直す
```

- **台帳 `family_sync`**: 家族ごとに1行。`changed` は `{表名: 最後に変わった時刻}`。時刻はサーバーが付ける
  （端末の時計とは比べない。前に見た時刻と「同じか違うか」だけを見る）
- **トリガ**: 共有表（35表）に `family_sync_ins/upd/gone`。**文ごとに1回**だけ台帳を書く（100行まとめて入れても1回）
  - 家族のIDを列で持たない表（`growth_records`・`list_groups`・`list_items`・`nursing_alarms`）は、
    `attach_family_sync` の第2引数で親をたどる
- **Realtime に載せるのは `family_sync` だけ。** 表ごとに載せない理由: 削除の通知が RLS で絞れず他の家族の行IDが届く、
  家計の金額などが通知の経路に出る。台帳なら時刻しか流れず、RLS（自分の家族の行だけ）がそのまま効く
- **台帳が読めない・Realtime がつながらないとき**: 30秒ごとに台帳を取りに行く（つながったら止める）。
  それも読めなければ、画面は前に読んだ分のまま（読み込みの失敗で画面は止めない）

## 3. 画面側の決まり

読み込みを関数にして `useFamilyRefresh(tables, refresh, options?)` に渡す。

| | mobile | PWA |
|---|---|---|
| 台帳係・フック | `mobile/src/lib/familySync.tsx` | `src/lib/familySync.tsx` |
| 時刻の比べ方（テストあり） | `mobile/src/lib/familySyncStamps.ts` | `src/lib/familySyncStamps.ts` |
| 台帳係を置く場所 | `app/_layout.tsx`（SessionProvider の内側） | `SukusukuApp.tsx` の外側 |

- `tables` はその画面が**読む**表。API関数が読む表を漏れなく並べる（足りなければ CI の `check:family-sync` が落ちる）
- 読み込み中の表示には戻さず、届いたら差し替える作りにする。失敗しても画面を止めない
- 見ていない画面は読み直さない。mobile は見ていない間に変わった分を「開いたときに1回」読み直す
- `onResume: true`: 変更の通知を待てない画面だけ。育児の記録は、端末内に溜めた未送信の書き込みを
  前面へ戻った・電波が戻ったときに送る（`sync` が最初に未送信を送る）
- 起動時の読み込みは画面自身が行う。台帳は「後から変わった分」を拾う
  - 最初の台帳を受け取ったのが画面を出してから5秒以内なら、その時点の画面は最新とみなす。
    それより後（圏外で起動して、あとでつながった）なら、取りこぼしがあり得るので1回読み直す
- 自分の端末での保存でも台帳は変わるので、保存後にもう一度読み直す（結果は同じ。0.4秒の間でまとめて1回）

## 4. 新しい表・新しい画面を足すとき

1. **新しい共有表**: その migration の中で `select public.attach_family_sync('public.表名');`。
   家族のIDを列で持たない表は第2引数で親をたどる（`supabase/migrations/0078_family_sync.sql` の例）
2. **新しい画面・タブ**: 読み込みを関数にして `useFamilyRefresh` に渡す
3. 確かめる: `npm run check:family-sync`（CIでも動く）。本番では `select * from public.family_sync_missing();` が空であること
   - `family_id` を持たない表の付け忘れは、この検査では見つからない（レビューで見る）
4. 家族で共有しない表（端末の宛先・配信の記録など）は、`scripts/check-family-sync.mjs` の `NOT_SHARED` と
   `family_sync_missing()` の除外に足す

## 5. 検討して選ばなかったもの

- **画面ごとに「戻ったとき」の読み直しを足す**（PR #223 の初版）: 渡し忘れた画面だけ古いまま。時間の間引きでは、
  変わっていないのに読んだり、変わったのに読まなかったりする
- **表ごとに Realtime を購読**: §2 のとおり、削除の通知が絞れない。購読の数も画面ごとに増える
- **取得層を作り直す（TanStack Query など）**: 全画面の読み込みと、いまの setState ベースの楽観更新を書き換える大きな改修。
  台帳＋宣言で同じ「変わったところだけ読む」が得られる
- **相手が記録したときに FCM のデータ通知で起こす**: Android は裏でも届くが、端末の電池設定で届かないことがあり、
  通知の許可に依存する。台帳の読み直し（前面復帰）で足りる

## 6. 限界

- アプリが裏にある間は、画面は更新されない（前面へ戻ったところで台帳1回で追いつく）
- 同時に開いて共同編集しているときは、相手の保存から約0.5秒で出る。自分の操作の最中に読み直しが入ると、
  楽観更新の途中の表示が一瞬戻ることがある（次の読み直しで直る）
- 台帳は家族ごとの1行なので、同じ家族の書き込みはこの行を順に更新する。2人利用では競合しない
