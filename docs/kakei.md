## 0. 収支の見直し（2026-10-11に決定。特別費を生活費と分けて計算するのをやめる）

月によって収支が大きく振れる（賞与の月は大きくプラス、年払い・固定費の多い月は大きくマイナス）のを、**ならさずに実額のまま**見る。
ならし（賞与と特別費の予定を12か月に配る）・繰越（口座残高の参照）も検討したが見送った（予想できない特別費があり、
貯金への移動や家族間の入金で口座残高は複雑になるため）。振れ幅はそのままにして、**年初からの累計と月平均**で見る。

### 0.1 数え方

- **収入** ＝ 給与 ＋ 賞与 ＋ 臨時収入。**支出** ＝ 生活費 ＋ 特別費。**収支** ＝ 収入 − 支出（実額）
- **家族のお金は、登録した口座すべてをひとまとまり**として数える。**登録口座の間の移動はすべて振替**（集計に入れない。妻から夫への生活費の入金も、
  貯金の口座への移動も同じ）。登録していない口座への送金は支出、外からの入金は収入
- 貯金へ移した額も集計に入れない。毎月のプラスは、収支の累計にそのまま残る
- 口座は**総残高の計算用**（§9.3）。収支の数え方には使わない

### 0.2 特別費はカテゴリとして収納する

> **2026-10-13: 特別費の枠組みは無くした。** 標準のカテゴリ（`DEFAULT_CATEGORIES`）から大分類「特別費」を外し、画面・コメントの「特別費」も消した。
> 本番DBに該当の表・列・大分類は無い（確認済み）。以下は経緯として残す。年に数回の大きな出費は、ふつうの大分類・固定費で記録する。

- **別枠をやめ、大分類「特別費」を1つ**作る。生活費の大分類と同じ一覧・内訳・分析（§4）に並べる。
  **小分類は持たない**（2026-10-11。0086 で今の項目を小分類にしたが、使わないことにして削除した）。使うときは大分類「特別費」を直接選び、
  **品名**で区別する（例: 自動車税）。必要になれば、小分類は後から足せる。今の「カテゴリ」（住居費・車維持費など13個）のくくりも持たない
- **固定のもの**（自動車税・年払いの保険・学校の納付など）は、設定の**固定費**に登録する（記録する月・日・額。§3.3）。
  予定外のものは、品名を付けて普通の記録として入れる
- **やめるもの**: 特別費の予定（`special_plans`）、家計の設定の「特別費の予定」の画面（`SpecialSettings`）、「特別費」の1行（年の予算の残り）、
  特別費の年の流れとこれから5年の見通し（docs/home.md §10.3）、記録の入力で「その年の予定から選ぶ」こと。
  **特別費の大分類には予算を置かない**（置く仕組みは生活費と同じなので、必要になれば置ける）
- 賞与は特別収入（`special_items` の `kind = 'income'`）をやめ、**固定収入**（§0.3）にする

### 0.3 固定収入（家計の設定に新設。給与・賞与）

- **給与**: 見込み額・振込日（毎月◯日）・休日のとき（既定は前営業日）・入金先の口座（**銀行の口座だけ**）・収入の小分類。
  **賞与**: 1回ごとに1件のルール（月・日・見込み額）。「複製して足す」（日・月・額を写し、品名に「のコピー」が付く。月・日を直して保存）で回を増やす（2026-10-13に「同じ名前でもう1回」をやめて複製に一本化）。賞与の月と日は複数にできる
- **振込日の決め方**（2026-10-11）: 「日にち」（毎月◯日。31は末日）か「**第◯◯曜日**」（第1〜第4・最終 ＋ 曜日。例: 12月の第2金曜日、最終金曜日）。
  休日のときの動かし方は、そのあとに今までどおり当てる。DBは `money_recurring.week_of_month`（1〜4＝第1〜第4、5＝最終）・`weekday`（0＝日〜6＝土）と
  関数 `money_rule_date`（0088）。自動で記録を作る関数と、見込みの額を出す関数がこれで日付を出す
- あらかじめ登録して、**見込みの記録を自動で作る**（§3.3 の仕組み。振込日に作る。見込み → 給与明細などで額を直すと確定）
- **履歴**: 設定の画面の下に、**その年の収入の記録**を新しい日から出す（見込みの印つき。年は送れる）。見込み額の変更の版は持たない
  （2026-10-11。複雑にしないため。記録は確定すると実績の額になる）
- **実装**（2026-10-11）: 新しい表は作らず、`money_recurring`（カテゴリが収入のルール）を使う。設定の「固定収入」は収入のルールだけ、
  「固定費」は収入以外のルールだけを出す同じ画面（`RecurringSettings` の `mode`）。履歴は `incomeRecordsInYear`

### 0.4 振り返り

- **月**: 収入・支出・**収支（±）**・**年初からの累計**。減った月は「−」と黒、増えた月は緑（§2.1）
- **年**（年が終わったあとの振り返りも同じ面）: 収入・支出・**最終的に残った額（収支）**・**月平均**（収支 ÷ 記録のある月数）。
  月ごとに、収支の棒と年初からの累計の折れ線を重ねる。大分類ごとの年間の増減（特別費もその1行）。**前年との比べ**は、前の年の記録がある年から出す
- **集計の開始月は持たない**（2026-10-11。いったん設定にしたが、使うのは今回だけなので取りやめた。さらに、集計は**10月分から**始めることにした）。
  記録は切り替えで削除したので、10月より前の記録は無い。年と累計は、**記録のある月だけ**を数える（§4.2）ので、2026年の年は自然に10月から数える
- **実装のメモ**（2026-10-11）
  - 数える月＝**振替だけではない記録のある月**（`buildYearSummary` の `recorded`）。月平均・累計・前年比はすべてこの月だけで数える
  - 月の累計は `yearToDateBalance`。記録の無い月・振替だけの月は null で、月の画面に累計を出さない
  - 前年との比べは `compareWithPreviousYear`: 今年の数える月のうち、前の年の同じ月も数えられるものだけを、月数をそろえて比べる
    （使い始めの年は12か月ぶんそろわないため。比べられる月が無ければ出さない）
  - 年の画面は、結論 → カテゴリ（内訳）（2026-10-16。§4.2。末尾にあった「月」の一覧は2026-10-19に外した。月へは推移のグラフから行く）

### 0.5 切り替え（2026-10-11）

- 記録（`money_records`。462件、2026-04-01〜10-06）を削除する（品目は `on delete cascade` で一緒に消える）。**固定費のルール・カテゴリ・口座・特別費の項目は残す**。
  口座の補正は0件なので、削除後は全口座の残高が0になり、最初に入れる補正が「はじめの残高」になる
- 手順: ① 記録を削除（削除を含む文なので、Claude は流さず SQL Editor で渡す）→ ② 全口座（証券を除く）の残高を補正する。カードは未払い総額のマイナス →
  ③ **カードの10月分の利用を入れ直す**（11/26・11/27・12/2 の引き落としは、入れ直した記録から自動で作られる）→
  ④ **9月までの利用分の引き落とし**（4枚それぞれ。10/26・10/27・11/2）は記録が無く自動では作られないので、明細の額で手で振替を入れる →
  ⑤ 見込み型の固定費は、過去の記録が消えるので、ルールに入れた額を実態に近づける
- （2026-10-24〜）補正は日付と結ばない増減になったので、④の振替や③の入れ直しの記録は残高に入る。先に記録を入れてから補正すると、補正の差が小さくなる（§9.3）

## 0.7 予算・固定費・カテゴリの見直し（2026-10-21に決定。家計簿のシートをもとにする）

> **予算・自動記録ルール・カテゴリの関係は §0.8（2026-10-23）が優先**。この節の「自動記録ルールは予算とは別物」「帯に出す見込み・日付未定」はやめた。

家計をまとめたシート（Google ドライブ「家計簿」。固定費・予備費・変動費・収入）を、家計の設定へ移す。**§3.1・§3.3・§3.6・§3.7 より、この節が優先**。

- **年間予算は 変動費・予備費・固定費**（2026-10-22に見直し。前日の「予算を充てるのは変動費と予備費だけ」を改めた）。固定費も額の決まった予算で、
  **毎月は追わない**だけ（月の振り返りで予算との差を出さない）。設定の「固定費」は記録を作るためのルールで、名前を **「自動記録ルール」** に、「予算」を **「年間予算」** にした
- **自動記録ルールは記録のためだけ。予算とは別物**（2026-10-22。PR3。migration 0129）。予算・支出の分け方・年末の着地見込みにルールは使わない
  - **予算は「単価 × その年に発生する回数」**。回数は**発生月と頻度**で決まる（毎月なら単価×12、偶数月なら×6、年に1回なら×1。◯年ごとは当たる年だけ。
    期間〔時短→フルタイムなど〕の外は数えない）。変動費は今までどおり大分類の月の予算（`money_budgets`）。収入・予備費・固定費は
    **予算の明細**（`money_budget_lines`。小分類ごと・何行でも。単価・発生月〔毎月／月を選ぶ／発生月なし〕・◯年ごと・期間・名前）
  - **発生月なし**（予備費・オイル交換・ふるさと納税など）は月に置かず、その年に1回ぶんを**見込み支出**として数える
  - **支出の分け方は大分類の「予算の分け方」だけで決める**（`money_categories.budget_group`。変動費・予備費・固定費〔確定〕・固定費〔見込み〕。
    カテゴリの大分類の編集で選ぶ。一覧の見た目は変えない）。ルールの有無・予算の有無は関係しない（変動固定費の小分類はルールが無くても見込み）
  - **年末の着地見込み＝締めた月は実績 ＋ 締めていない月はその月の予算**（収入・予備費・固定費の明細のうち、その月に発生する回 − 変動費の月の予算）
    **＋ 発生月なしの見込み**（小分類ごとに「年の額 − 締めた月までの実績」〔0未満は0〕。12月の収支に入れる）。月に均等に割り振ることはしない
  - 年の振り返りの固定費は、確定・見込みの実績と年の予算、予算と違ったもの（締めた月までの実績と、その月までに発生する回の予算の差）
  - **日付未定のルール**は帯に出さず、**締めまでに同じ小分類の記録が無ければ、締めの未確認の明細に出す**（`undatedPendingInMonth`。中は帯の見込みと同じ）
  - 0127 の `money_reserve_budgets`（予備費の年の額）は使わない（0130 で消す）。画面イメージ https://claude.ai/artifact/Nphe5xZtZjJ8xBjczmS1MN
- **固定費のルール（自動記録ルール）**は「種類」と「記録の作り方」の2つで決める
  | | 自動で記録する（その日に記録を作る） | 帯に出す（記録の上の帯から確かめて記録する） |
  | --- | --- | --- |
  | **確定**（額が決まっている。`amount_mode = 'fixed'`） | 家賃・保険・おこづかい・仕送り／児童手当 | 自治会費・祭礼費・自動車税・JAF など（日・月が決まらないもの） |
  | **見込み**（額が変わる。`'estimate'`。旧「予定」） | 電気・ガス・水道／給与・賞与 | 車検・スマホ・生成AI |
  - 収入も同じ（児童手当は確定、給与・賞与は見込み。0124 で収入をいつも見込みにしたのを 0125 で戻した）。振替はいつも見込み
  - 帯に出すもの（`makes_record = false`）は出金元・お店・日を持てる（記録するときの下書き）。**日が決まらないものは「日付未定」**（`day_known = false`）にし、帯には出さない
  - 帯に出すものは、**同じ小分類の記録が入ると済**になる（自動で結びつく。§3.6 の実績との結びつき）
  - **◯年ごと**（`interval_years`。2〜10）: 車検・2年ごとの火災保険。開始月（期間の始まり＝最初の回）の年から数え、間隔の年の記録する月だけに当たる
- **変動固定費（見込み）**は年間予算の固定費の「見込み」に入る（月の予算オーバーの判定には入れない）。年末の着地見込みには見込みの額で入れ、
  実績が入ったら実績に置き換える。年の振り返りの固定費の枠で「見込みより +¥1,200」のように差を見せる
- **自動車保険**（大造 6月 33,000、いづみ 1月 23,350）は変動固定費（見込み・帯に出す）
- **帯**（記録の面の上。PR1b）: 見出しは「未確定明細 n件」の1行だけ（Gmail の未確認の明細と、日が来た帯に出す見込み。横に「Gmail n件・見込み n件」）。
  押すと一覧（見出しは「Gmail から取り込んだ明細」「見込み」の2つ。ボタンは置かない）。月の締めは今のまま（触らない）
  - 帯に出す見込みは、その回の日（休日の扱いを含めた日）から出す。予定の月を過ぎて記録が無い回は今月に送られて出る（日は今日）。
    日付未定・済（同じ小分類の記録が入った）・今月はなしの回は出さない（`pendingEstimates`）
  - 見込みの行を押すと中（下から開く画面）に、カテゴリ・日・出金元と額（直せる）、「この額で記録する」「翌月へ送る」「今月はなし」
    - この額で記録する: 額・出金元・日・カテゴリ（品名・お店も）で記録する。出金元があればその場で記録し、無ければそれを入れた記録の入力を開く
    - 翌月へ送る: ルールの `deferred_until` に翌月1日を入れ、その日まで帯に出さない（そのあと記録が無ければまた出る）
    - 今月はなし: その回（予定の月）を `skipped_months` に足す
  - Gmail の明細の行は今までどおり（押すと片づけ方を選ぶ枠）
- **カテゴリ**: 変動費の大分類（水道光熱費・日用品費・食費・おしゃれ費・医療費・交通費・娯楽費・育児費）に、大分類 **固定費・変動固定費・予備費** の3つを足す。
  この3つの小分類は、シートの支出の項目そのもの（家賃・車検・冠婚葬祭のお祝い など）
- **予備費**は小分類ごとに年の予算を持つ（仕事関係 60,000 を足す）。振り返りは小分類ごとの予算と残りを出す
- **年間予算と振り返り（PR2。2026-10-22。画面イメージ https://claude.ai/artifact/3KUdUNxCVShHE8JoddUsjv ）**
  - 支出の分け方（`spendGroupOf`）: 大分類の予算の分け方（PR3。上の項）

## 0.8 予算・カテゴリ・自動記録を1つにまとめる（2026-10-23に決定。§0.7 より優先）

§0.7 で予算（`money_budget_lines`）と自動記録ルール（`money_recurring`）を切り離した結果、家賃なら予算とルールを別々に作り、
額・月・小分類を2回入れることになった（カテゴリは追加と名前だけ、ルールから予算は見えない）。**予算を本体にし、1つの表にまとめる**。
画面イメージ https://claude.ai/artifact/E7b5G4mW4PuwmdkNrc8gQX

- **予算1件＝`money_recurring` の1行**（単価 × 発生月・頻度・期間・品目の名前）。同じ小分類に何件でも持てる（妻と子の誕生日がどちらも8月なら2件）
  - **自動記録はその行のオン／オフ**（`makes_record`）。オンにすると日（日にち／第◯◯曜日）・休日・出金元（入金先）・お店を決め、サーバーがその日に記録を作る
    （`make_money_recurring_records` は変えない）。オフは記録を作らない。発生月なし（`no_month`。0136）は自動記録できない
  - 確定／見込み（`amount_mode`）は種類で決まる: 固定費（見込み）・変動費は見込み、固定費（確定）・予備費は確定。収入だけ行ごと（「毎回同じ額」）
  - 振替は予算に数えない。家計の設定の「振替」で直す（`RecurringSettings` は振替だけ）
- **種類は5つ**: 収入・変動費・固定費（確定）・固定費（見込み。旧「変動固定費」）・予備費。支出の種類は大分類の予算の分け方（`budget_group`）で決める
  （予算1件ごとにすると、同じ小分類の記録をどれで数えるか決まらないため）。小分類の種類を変えると、その種類の大分類へ移る（変動費は大分類を選ぶ）
- **変動費の月の予算**（`money_budgets` をやめた）も同じ行で持つ: **大分類の行だけ**（2026-10-24に、小分類の行はやめた。下の「どの種類も予算の1行」）。12月だけ違う額などは件を分ける
- 数え方: 収入・予備費・固定費は予算の明細の形（`budgetLinesOf`）、変動費は大分類の月の予算の形（`variableBudgetsOf`）に直して、§0.7 の数え方をそのまま使う
- **年間予算の画面**（`BudgetEditor`）で全部決める。カテゴリ・自動記録の設定も、ここから（家計の設定の入口は「年間予算」が先頭。2026-10-24に作り直し）
  - 家計の設定の入口の見出しは **「年間予算」「振替」「よく行くお店」「Gmail 取り込み」**（2026-10-24。短くした。中身は従来どおり: 年間予算＝予算・自動記録・目標割合、振替＝振替の自動記録）。
    **カテゴリ（アイコン・色・並び）の入口は、年間予算の右上の「カテゴリ」**に移した（2026-10-24。設定の入口からは外した）
  - 上の枠（影で浮かせ、下の一覧と分ける）: **円グラフ1つ（1周＝収入）**。支出の種類（変動費・固定費・確定・固定費・見込み・予備費）を青の濃淡で並べ、
    残りが収支見込み（緑）。赤字の年は支出の種類を1周に並べ、収入からはみ出した分（収入に対する割合）を外側の赤い弧で出す。円の中は「収入 ¥xxx万」
  - 円の下: 収支見込み（黒字は緑で「+」なし、赤字は赤で「−」）・収入・支出、続けて支出の種類を「名前（xx%）」と額で。割合は**収入に対する割合**で、
    一桁は前に数字1つぶんの空き（U+2007）を入れて右の括弧をそろえる。名前は左寄せ、割合・額は右寄せ
  - 行（収入・支出・支出の種類）を押すと、下の一覧はその種類だけになる（「支出」は支出の種類すべて。もう一度押すと全部）。絞っている間は見出しを折りたたまず、折りたたみの印も出さない
  - 下の一覧: 収入・変動費・固定費（確定）・固定費（見込み）・予備費の見出しごと（太字の見出し。押すと折りたたむ）。収入の見出しの下線は緑、ほかはグレー。
    行は名前と年の額だけ（詳細は押して開く枠で見る）。その年に発生しない予算はグレーにして「期間外」を付け、各見出しの一番下に並べる
  - 変動費の行は大分類。押すと予算の枠が開く（2026-10-24に、大分類の画面はやめた。大分類の名前・アイコン・小分類は枠で直す）
  - **どの種類も「予算の1行」で数える**（2026-10-24に決定。変動費は小分類ごとに予算を持つとややこしいので、大分類だけに持たせた）:
    変動費＝1行が**大分類**（小分類は記録の分類だけ。予算なし）／予備費・固定費（確定・見込み）＝1行が**小分類**（＝品目。小分類の名前が品目の名前）／
    収入＝1行が小分類（種別）で、同じ小分類に予算が複数あるときは品目名で区別する。大分類・小分類は、予算の行を作ると一緒にでき、消すと一緒に消える
  - **予算の枠（追加・編集）**: すべて枠の中の「左に項目、右に値 ›」の1行。**「分類」の項目は種類で変わる**（2026-10-24）:
    - **変動費**: 種類・名前（大分類の名前）・アイコン（押すと「アイコンと色」。出金元のアイコンの色と同じ候補）・小分類（すべてをチップで並べる。
      押すと名前・別の大分類へ移す・消す。「＋ 小分類」で足す）。新しい大分類は「予算を追加」（種類＝変動費）で、名前・アイコン・小分類を入れて保存すると、
      大分類と予算の行が同時にできる。枠の下の「この大分類を消す」で、小分類と予算の行もまとめて消える（確認に件数を出す。記録には名前だけが残る）
    - **予備費・固定費（確定／見込み）**: 種類・名前（小分類の名前＝品目の名前。大分類は種類そのもの）。「この品目を消す」で小分類と予算の行を消す。
      種類を変えて保存すると、その小分類は選んだ種類の大分類へ移る（直すときに種類を選べるのは、この3つの間だけ）
    - **収入**: 種類・大分類・小分類・品目。小分類は選ぶ画面で一覧から選ぶか、新しい名前で作る（選んでいる小分類の名前を直す・消すもそこから）。
      変動費・収入は、種類を変えるときは消して作り直す（種類の選択を押せなくする）
    予算（金額・いつ・期間）、自動記録（オン／オフ。オンで日・出金元〔入金先〕・お店、収入は「毎回同じ額」）は種類によらず同じ。
    **大分類を先にカテゴリの設定で足さなくてよい**（予算が本体で、カテゴリは予算を表示するだけ。カテゴリの設定〔CategoryEditor〕は、アイコン・色・並びを直す場所のまま）
  - **固定費（見込み）の年の額は、月ごとに前年の記録で見込む**（2026-10-24。自動記録と同じ考え方。`estimatedBudgetYearAmount`）: 発生月ごとに
    前年の同じ月の記録があればその額、無ければ予算の額。水道光熱費のように季節で変わるものを、予算の額を一律にせず前年の実績の重みで出す。
    年間予算の一覧・上の枠（円グラフ・収支見込み）・枠のプレビューに使う。サーバーの自動記録（`make_money_recurring_records`）は変えない
    （もともと 前年同月 → 直近3回の平均 → 予算の額 の順で見込みの額を決める）。振り返り・目標割合は従来どおり予算の額のまま
  - 固定費（確定）・固定費（見込み）・予備費は**大分類＝種類**（大分類の名前も種類の名前。無ければ作る）
  - カテゴリの無い行（古いルール）は「カテゴリなし」に出し、押してカテゴリを決める
  - 目標割合（変動費・予備費・固定費の、収入に対する目標）と振り返りとの連動は §0.9（2026-10-24）
- **月の締めの「今月記録予定の固定費 n件」**: 自動記録オフの固定費（確定・見込み）で、その月が発生月なのに同じ小分類の記録が無いもの
  （日が未定で、いつ払うか分からないから出す。設定は持たない）。発生月なしは出さない。押すと未確定明細の一覧で「この額で記録する」「翌月へ送る」
  （その回を外し、翌月の締めに出す。`skipped_months` と `deferred_until`）「今月はなし」（`skipped_months`）。記録の上の帯には見込みを出さない（帯は Gmail の明細だけ）
- 移し替え（0136）: 予算の明細は、同じ小分類・額・発生月・頻度・期間のルールがあれば結びつけ、無ければ自動記録オフの行として足す。
  変動費の月の予算は大分類の行として足す（ずっと続く毎月の小分類の行〔電気・ガス・水道〕の分は引く）。
  `money_budget_lines`・`money_budgets` は使わなくなる（あとで SQL Editor で消す）
- 変動費の整理（2026-10-24。migration 0140・適用済み）: 水道光熱費（電気代・ガス代・水道代。小分類ごとに予算を持って毎月の記録を自動で作っていた）は、
  大分類だけの予算では持てないので、小分類を**固定費（見込み）へ移し**、空になった大分類は使わなくした（`archived_at`）。日用品費の小分類の予算2行（消耗品・雑貨）は、
  大分類の1行（20,000）に合算し、元の行は使わなくした（`archived_at`。削除はしない）
- 本番の設定（2026-10-23）: 自治会費・祭礼費は月が分からないので、固定費（確定）・自動記録オフ・発生月なし。大分類「固定費」は「固定費（確定）」に名前を直した（2026-10-24）

## 0.9 振り返りは予算に対して見る・目標割合（2026-10-24に決定。旧「目安の割合」）

振り返り（MoneyReviewView）は「予算に対して、どうだったか」を見る場所にする。年間予算（§0.8）は計画だけを見る。
画面イメージ https://claude.ai/artifact/5JBQSn5URoSyRCqNKfUJ3r

- **並び順は家計全体で 変動費 → 予備費 → 固定費（確定・見込み）**（予備費も変動費の一部のようなもの）。年間予算の一覧・円グラフの並びも同じ
- **月の振り返り**: 結論は今のまま（収支・収入・支出の実績、見込みの件数、この月を締める）。その下に見出しごと
  - 変動費: 大分類ごとに 予算 − 実績・使った割合の帯・「実績 / 予算・%」。予算の無い大分類は実績の額だけ（「予算なし」は出さない）
  - 予備費: 記録のあった小分類の額だけ（予算が月に割り当たらない）
  - 固定費: 記録のあった小分類の額だけ（帯は付けない）。中を「確定」「見込み」に分け、見込みは「予算より ¥x」（その月の予算 − 実績）を添える。月は発生月なしの予算と比べない
  - カテゴリなし: カテゴリの無い品目（削除したカテゴリの品目を含む）の件数と額
  - 予備費・固定費・カテゴリなしの行を押すと、その記録の一覧（年はその年）。変動費は今までどおり大分類の詳細
- **年の振り返り**: 年は1〜12月で見る（使い始めた年を除く。下の特例）
  - 結論は**収支見込み**（収入・支出も見込み。`buildYearLanding`）。締めた月は実績。締めていない月のうち、今月まで（締め忘れた月も）は記録があるので、
    支出は**予算と実績の大きいほう**（変動費は大分類ごと、予備費・固定費は小分類ごと）。翌月からは記録が無いので**予算だけ**。
    収入は予算に対する変動を追わず、締めるまで予算（締めると、その月の実績が収支見込みに入る）。発生月なしは「年の額 − 今月までの実績」の残りを12月に置く
  - 月平均・前年の同じ期間との比べは出さない（予算と関係が無い）。予算との差は結論に出さず、下の行で見る
  - 推移（§4.8）は今のまま（締めた月は実線、ほかは点線。数え方は収支見込みと同じ）
  - 行の出し方は月と同じで、右の額は**残り（年の予算 − 年初からの実績）**、帯と「実績 / 予算・%」も実績（見込みは行に混ぜない）。予備費だけは年の予算（発生月なしを含む）と比べる行（変動費と同じ）
- **見出しは折りたためる**。はじめは変動費・予備費を開き、固定費は閉じておく
- **目標割合**（旧「目安の割合」。2026-10-24に名前を変え、**年間予算の画面の上の枠の下**から決める。年間予算で全部決める）:
  変動費・予備費・固定費（確定＋見込みの全体で1つ）の、収入に対する目標（%）。**種類ごとだけで、項目（大分類・小分類）ごとには持たない**。
  - 画面（案C）: 上の枠の円グラフ・凡例の下に「目標割合」の帯。**折りたたみで、はじめは閉じる**（閉じている間は「合計85%・貯金15%」）。
    開くと 変動費・予備費・固定費・**貯金** の4つ（貯金 ＝ 100% − 合計。旧「収支（残り）」）。「編集」でその場で入力欄に変わり、キャンセルか保存。
    合計が100%を超えると赤で保存できない。空は目標なし。家計の設定の入口からは外した（専用の画面〔`RatioTargetSettings`〕はなくした）
  - 表は `money_ratio_targets`（0137）

  レシートから読んだ記録なら、mobile はそのまま次のレシートを撮る（PWA は写真の選択を押した操作の中でしか開けないので、次の入力の「レシートから追加」から）。
  取り込んだ明細から開いた記録・既にある記録の編集では出さない
- **振替**: 出金元 → 入金先（例: 生活費用の口座 → 貯金用の口座）。**振替は集計に入れない**（貯金への振替も同じ。
  貯金は自動で算出せず、記録があればしたということ、無ければしなかったということ。2026-10-08に変更）。
  ~~出金元の「貯金用」は目印だけ~~ **「貯金用」の設定は削除**（2026-10-12）。貯金用の口座も、名前で分かるだけの**ただの口座**として扱う。
  `money_wallets.is_saving`・`saving_target` は使わない（古いアプリが書き込むため列は残す）
- **Zaim から変えるところ**
  - カテゴリの選択の上に**よく使う小分類**、各大分類に**今月の残り**。品目でカテゴリを選ぶと、その大分類の今月の残りが出る
  - ~~特別費は、その年の予定から選ぶ（選ぶと予算の額が入る。これが特別費の「済」になる）~~ **やめた**（2026-10-11）。
    特別費は大分類「特別費」の小分類を選んで入れる。予定外のものは小分類を足して記録する（§0.2）
  - 置かないもの: 電話番号・時刻・タグ・写真・「常に集計に含める／含めない」（振替は集計に入れない、で足りる）。
    レシートの読み取り（§10）でも写真は記録に残さない（読み取りに使って捨てる）

### 3.3 毎月自動で記録するもの（固定費・給料。2026-10-08に決定）

口座から落ちるもの・口座に入るものは、**項目ごとにルールを登録**し、その日に記録を自動で作る。

- **ルール（項目ごと）**: カテゴリ・出金元（口座）・お店（相手先）・**引き落とし日**（毎月◯日。31は末日）・**休日のとき**（翌営業日／前営業日／そのまま。
  祝日は `japaneseHolidays.ts`）・**額の決め方**（固定額／過去の記録から見込む）・**記録する月**（毎月か、賞与のように決まった月だけ）
  - 休日＝銀行の休業日（土日・祝日・12月31日〜1月3日）。祝日はDBの `jp_holiday_name` で、`japaneseHolidays.ts` と同じ数え方
    （2020〜2060年で一致を確かめた。2026-10-08）
- **収入・振替はいつも見込み**（2026-10-20。migration 0124）: 給与は残業・休日出勤で毎月変わり、振替（給与口座の肥後銀行 → 生活費の三井住友の定額自動入金など）も
  賞与の月や余剰を移す月でほぼ毎月額を変えるので、「固定」という考え方をやめた。額の決め方（入れた額／過去の記録から）にかかわらず、
  その日に**見込みの記録**（`is_estimate`）を作り、実額に直すと確定になる（支出の固定は今までどおり確定で作る）。
  画面の呼び名は「収入の見込み」「振替の見込み」（一覧の額は「見込み ¥◯」）。記録しない「予定」（§3.6）は支出だけのまま
- **どの月の支出か**: **落ちた月**（引き落とし日の月）。使った月（電気を使った月など）ではない
- **期間**（2026-10-15。0102）: ルールに**開始月・終了月**（どちらも任意。空は無期限）を持たせる。育休・復帰・時短で額や有無が変わる収入・支出を、
  ルールを消さずに登録するため（例: 育児休業給付金 〜2027/8、時短後の給与 2027/9〜。67%→50% のように額が変わるものはルールを分ける）
  - 期間は**どの月の分か**（記録の `month`。入金・引き落としのある月）で決める。後払いの給付金は、入金の月で入れる
  - 期間の外の月は、**記録を作らず**（`make_money_recurring_records`）、**予算にも足さない**（`fixedBudgetRows`）
  - 見込みの額は、**期間の始まりより前の記録を使わない**（時短後の給与の見込みが、出産前の給与の記録から出ないように）。
    そのルールが作った記録は期間に関係なく使う（`money_recurring_estimate`・`estimateRecurringAmount`）
  - 設定の画面では「2027/9」の形で入れる。一覧の行に「・2027/9〜」と添え、期間が終わったルールは一覧の下に畳む（押すと開き、編集できる）
- **見込みの額**: その項目の**過去1年の記録**から自動で出す。給料も同じ（賞与は別の項目にして、平均を崩さない）
  - 項目の過去の記録＝カテゴリ（小分類）・出金元・お店が同じ記録。Zaim から取り込んだ記録（2026年5月〜）も使う
  - 出し方: **前年同月の記録があればその額、無ければ直近3回の平均**（どちらも見込みでない記録だけ）。記録が1件も無ければルールに入れた額。
    前年同月は「前年のその月の引き落とし日の前後10日」で探す（休日で月をまたいだ回も拾うため）。
    1年分がそろうまで（2027年春ごろ）は季節のずれが出るが、確定で直る
  - 固定額の項目（家賃・ローンなど）は見込まず、その額で**確定**として作る
  - **予算にも同じ額を使う**（2026-10-11。§3.1）。支出の固定費は、カテゴリの大分類の、その月の予算に足される。見込みの計算はアプリ側にも写してある（`estimateRecurringAmount`）
- **見込みは、固定収入・固定支出の見込みの額で自動で作った記録だけ**（2026-10-16。`isFixedEstimate`＝見込み かつ ルールから作った 振替でない記録）。財布・デビットの記録は入れた時点で確定、カードも Gmail から取り込んで確かめてから記録に入るので、見込みは無い。カード代金の引き落としの振替も見込みとして扱わない
- **見込みと確定**: 見込みで作った記録には「見込み」の印を付ける。**自宅に届く通知など**（検針票・利用明細・給与明細）を見て額を直すと確定になる。
  振り返り（§4）では見込みの額だと分かるように出し、月の締め（§3.4）でまだ確定していないものを一覧にする
  - 印は、記録の一覧では金額の左。振り返りでは「見込みの額 n件を含みます」と、年の月ごとの行
  - 記録の詳細で額を直して保存すると確定。額が合っていたときは「この額で確定する」。額を変えずに保存したときは見込みのまま
- **作る場所**: サーバーで毎朝5時（pg_cron の `make_money_recurring_records`。夫婦どちらの端末にも頼らない）。
  同じ月に二重に作らない（ルールと月の組み合わせで1件）
  - ルールごとに「どの月の分まで作ったか」を持ち、それより後の月だけを作る。**作った記録を人が消しても、作り直さない**
  - 実行が飛んだ日は7日前の分までさかのぼる。**ルールを作る前に来た分は作らない**（もう手で入れているはずなので）
- カード代金の引き落としもこの仕組みで作る（§3.4）
- **特別費のうち決まっているもの**（自動車税・年払いの保険など）は、**記録する月**を決めたルールとして登録する（カテゴリは大分類「特別費」の小分類。§0.2）。
  **給料・賞与は固定収入**として登録する（賞与は回ごとに月・日・見込み額。履歴つき。§0.3）

### 3.4 カードの月末の照合（今の財布方式）

- カードの出金元に **締め日・引き落とし日・引き落とし月・引き落とし口座** を設定する（2026-10-08に決定。引き落とし月は2026-10-09に追加）
  - 引き落としは、**締め日のあとに来る最初の引き落とし日**（15日締め・10日払いなら翌月10日。末日締め・27日払いなら翌月27日）。
    休日なら翌営業日（カードの引き落としは翌営業日なので、選ばせない）
  - **引き落とし月**（2026-10-09。`money_wallets.pay_month_offset`。0080）: 「自動」（上の数え方）か、締め日の月から数えて「翌月」「翌々月」と決める。
    月末締めの翌々月2日払いのカードは「翌々月」にする（9月末締め → 11月2日。自動だと翌月の2日になり合わない）。
    決めたカードは、引き落とし月の `pay_day` に、引き落とし月から月数を引いた月の締め日までの1か月分で振替を作る（`make_money_recurring_records`）
  - 設定をそろえた時点で、もう過ぎた引き落としの分は作らない（手で入れているはずなので）
- カードで払った記録は、**出金元（カード）ごと**に、締め日で区切った期間（前回の締め日の翌日〜今回の締め日）の合計として積み上がる
  （Zaim のマイナス残高にあたる。§8 の1 は締め日で区切ると決めた）
- 引き落とし日に、その期間の合計で **振替（引き落とし口座 → カード）を自動で作る**（§3.3 の仕組み。見込みの印つき）。
  支出はカードの品目で数えているので、振替にして二重に数えない
  - 期間の合計＝そのカードの支出 − 収入（返品）。0円以下なら作らない
- 締め日を過ぎたら、カードごとに明細の合計を入れる → 合計が合えば「締める」（合わなければ差額を出し、記録を見直す）。
  締めると、引き落としの振替は明細の額で確定する。お店からの売上の届きが遅れて記録と明細の期間がずれた分も、ここで見直す
- 締めた月の記録は、締めを外すまで直せないようにする（あとから合計が変わらないように）
- **カードの引き落としを翌月分に回す**（2026-10-15。`money_records.card_next_period`。0104）: 締め日の近くに使ったのに、お店からの
  売上の届きが遅れて次の引き落としに入る記録のため。出金元がカードで、日付が**25日以降**の記録（支出・収入）の詳細にだけ、
  チェックボックス「カードの引き落としを翌月分に回す」を出す（それ以外は false で保存する。`canCardNextPeriod`）
  - 効くのは**カードの引き落とし額だけ**。印のある記録は、日付の期間（前回の締め日の翌日〜今回の締め日）の**次の期間**で数える
    （DB の `make_money_recurring_records` のカードの部分と、アプリの `cardBilling` の未請求）。記録そのものは日付の月の収支・締めに入る
  - 一覧の行に「翌月払い」の印。カードの詳細の「引き落とし」の行に、前の期間から回ってきた額を「うち9月分（翌月払い） ¥4,000」と添える
    （9月は回した記録の期間の締め日の月。`cardCarriedIn`）
  - 保存は今の `save_money_record` のまま、アプリが保存のあとに列を更新する（関数の作り直しに削除の文が入るのを避けた）
- **これまでの引き落とし額**（2026-10-09）: カードの詳細は「履歴 / 引き落とし」の2つ（口座の「推移」は折れ線だったが、カードは残高の推移より
  引き落としの額が知りたいので替えた）。引き落とし月ごと（新しい月から）に、口座 → カードの振替の合計（自動で作った見込みも人が入れた分も数える。
  見込みを含む月には「見込み」の印）と、締め日・引き落とし月の設定があれば「ご利用 9/1〜9/30」の利用期間を添える（`cardPaymentHistory`・`cardUsagePeriod`）

### 3.5 家計の設定（2026-10-08に決定。設定データを、記録とは別に、いつでも編集・追加できるようにする）

予算・種類・出金元・お店は**設定データ**で、記録（§3.2）ではない。予算・種類・お店は見出し「家計」の右の歯車から**1か所で**編集・追加できる。
**出金元は「口座」の面（§7 の7）で足す・直す**（2026-10-08に、歯車の設定から外した。口座の一覧から持ってくる形にするため）。
記録の入力中に出る選択画面（カテゴリ・お店）からは、これまでどおり足せる。出金元は選ぶだけ（口座の面で足す・直す）。

  2026-10-08に、保存のたびの自動登録から変えた。一度きりのお店まで登録され、Zaim のように膨らむため）。
  「この記録だけに使う」を選んだお店は記録にだけ名前が残り、選択画面には名前で探したときだけ出る（2026-10-20まで最近使ったお店に出ていたが、邪魔なのでやめた）。

- お店の選択画面は、**登録したお店**を**直近1年に使った回数の多い順**（同じ回数は名前順）に出す（`storeChoices`。2026-10-20。以前は先頭に最近使ったお店〔新しい順〕を出していた）。
  開いても検索欄にはフォーカスせず、キーボードは出さない（検索欄を押したときだけ出す。2026-10-21）。
  名前で探したときは、登録していない前に使ったお店も「前に使ったお店」に出す
- 同じ系列のお店（「ドラッグストアコスモス」「ドラッグストアコスモス 下城南中前店」など）は、どの店舗かまでは分けない。
  2026-10-08に、Zaim から取り込んだお店を1つの名前にまとめ、記録のお店の名前も書き換えた（一度きりの整理。設定に「まとめる」は置かない）
- 戻る操作は、開いている設定の面 → 設定の入口 → 家計タブの順

### 3.6 支出の予算の分け方と、記録しない固定支出（2026-10-17に決定、2026-10-18に見直し。migration 0114）

家計の管理の軸を決めた。**集計は目的（大分類）で、予算は性質で分ける**。性質は大分類に持たせず、**予算の行がどこから来たか**で表す。
支出の予算は **変動費・固定費（確定・予定）・予備費** の3つ（2026-10-18。項目が多いと見づらいため）。

| 予算 | 中身 | 予算の立て方 |
| --- | --- | --- |
| 変動費 | 食費・日用品など、日々のやりくりで守るもの | 大分類ごとの**手入力の月額**（毎月同じ額が基本。重みは手で付けない） |
| 固定費・**確定** | 家賃・ローン・保育料・サブスクなど、**額が固定**のもの | 固定支出のルール（`amount_mode = 'fixed'`。記録を自動で作る）→ その月の予算に自動で足す |
| 固定費・**予定** | 必ず出るが、額が変わるもの。電気・ガス・水道（毎月）と、車検・自動車保険・ふるさと納税・行事（年に数回）は**頻度が違うだけ**で同じ扱い | 固定支出のルールのうち確定でないもの。毎月のもの（自動で記録して額を見込む。§3.3）と、**記録しない**もの（下） |
| 予備費 | 起きるかどうかも、いつかも分からない出費 | 年の額と、紐づけた小分類（§3.7） |

1つの大分類に性質が混ざる（例: 車＝ガソリン〔変動〕・ローン〔確定〕・車検〔予定〕）ので、大分類を性質で分けない。
（呼び名は「見積特別費」→「見積費」→ 2026-10-18に固定費の「予定」へ。コードの関数名は `estimateCost…` のまま）

**記録しない固定支出（予定）**: 車検・ふるさと納税のように、カードや現金で払うもの。固定支出のように記録を作ると、カードの取り込み・手入力と二重になるため、記録は作らない。

- **ルール**: `money_recurring` の `makes_record = false`。持つのはカテゴリ（**専用の小分類**。例: 車 › 車検）・品名・予定の月（`months`）・期間・額だけ。
  **出金元は持たない**（`wallet_id` は null。DBの check `money_recurring_estimate_no_wallet` でも止める）。`make_money_recurring_records` は出金元の無いルールを作らないので、関数は変えていない
- **実績との結びつき**（`estimateCostsInYear`。DBに持たず、表示のたびに計算）: その年に**ルールの小分類**で入った記録（支出の品目のうち、その小分類の分）を、その回の実績にする。
  同じ小分類の回が年に2つ以上あれば、記録ごとに**予定の月がいちばん近い回**へ当てる（同じ近さなら早い回）。手で紐づける操作は無く、記録の画面は変えない
- **置く月**（予算と着地見込みに足す月。額は予定の額のまま。予定と実績の差が見えるように）
  | 回の状態 | 置く月 |
  | --- | --- |
  | 済（実績がある） | **実績の月**（いちばん多く入った月）。早く・遅く払っても、予算がその月へ移る |
  | 予定の月が今月以降で、実績が無い | 予定の月 |
  | 予定の月を過ぎたのに、実績が無い | **今月**（今年のとき。年末まで見込みに残す）。過ぎた年は予定の月のまま |
  | 今年はなし（`skipped_months` に予定の月） | どこにも置かない。予算の画面で回を押して切り替える |
- **ルールを作った月より前の回は出さない**（使い始める前の回が今月へ送られないように）。その前の記録は実績に当てない
- **額**: 「入れた額」（`amount_mode = 'fixed'`）か「**前回の実績から見込む**」（`'estimate'`。`estimateCostBasis`）。前回＝その年より前に、その小分類の記録が入った
  いちばん新しい月の合計（予定の月から2か月以内の月があればそちらを選ぶ。帰省の8月と12月のように同じ小分類で年に2回あるもの）。2年に1回の車検は2年前の回を使う。前回が無ければ入れた額。
  月は自動では動かさず、前回の月が予定の月と違えば編集の画面に「前回は10月でした（10月にする）」と出す
  - 予算の画面の「確定」は、自動で記録する**固定額**のルールだけ。記録しないルールは、入れた額でも「予定」に並べる
- **予算**: `estimateBudgetRows`（大分類×年×12か月。`fixed: true`・`estimate: true`）を、固定費の行と同じく手入力の予算に並べる。
  月の予算＝手入力（変動費）＋固定費（`fixedBudgetFor`）＋記録しない予定（`estimateBudgetFor`）＋予備費で数えた分（§3.7）。生活費の大分類のものだけ。ルールを作った年から今年の翌年まで
- **着地見込み**（§4.6）: 月の見込みから、その月に置いた予定も引く
- **画面（予算。2026-10-18）**: 上の枠＝収入・支出（変動費・固定費〔確定・予定〕・予備費）・収支見込み。その下に**収入**（固定収入の一覧。固定費と同じ行で、押すと「固定収入」の編集）。
  変動費＝大分類をすべて（「前年から引き継ぎ」などの注釈は付けない）。固定費＝1つの枠に「確定」「予定」の見出し（押すと折りたたむ。見出しに年の合計）。ルールの行は、左に大分類のアイコンと、**カテゴリ（大きく）・品名（その下）**（お店は出さない）、右に年の合計（収入は緑）、その下に記録する月と1回の額（「月 ¥98,000」。回ごとに違うものは平均で「約」。月は「奇数月」「3か月ごと」のように短く。`monthsLabel`）。記録しない回は、右に額、その下に月。金額の横に「年」は付けない。変動費も右に年の合計、その下に「月 ¥◯」。押すと、そのルールの「固定支出」の編集が開く（記録しない回は「今年はなし」か「固定支出を開く」を選ぶ）。文字はスマホで読める大きさ（名前・額16、注釈13）。予定は、毎月のもの（年の合計）のあとに、
  記録しない回を月の順に（実績があれば「済」。ほかの状態のラベルは付けない。押すと「今年はなし」）。予備費＝§3.7。説明・注釈は付けない
- **画面（固定支出）**: 編集のいちばん上に「記録の作り方: 自動で記録する／記録しない（予定）」。記録しないときは出金元・お店・日・休日の欄を出さない。
  車検のように数年に1回のものは、期間を「2027/3〜2027/3」にして1回きりにし、次の回は「複製して足す」
- **弱点**: 実績が別の小分類に入ると（カードの取り込みで「車 › その他」に入るなど）、その回は実績が無いまま今月へ送られ、実績と二重に見込まれる。
  記録の小分類を直すか「今年はなし」にする
- **まだやらないこと**: 月の締めの画面に「実績が無い予定」を出すこと

### 3.7 予備費（2026-10-18に決定。migration 0115）

起きるかどうかも、いつかも分からない出費（冠婚葬祭・家電の故障など）のための**年の額**。予算の一部で、**紐づけた小分類の予算**になる。
カテゴリ「予備費」は作らない（何に使ったかの集計が崩れるため）。記録はいつもどおり、中身に合う小分類に付ける。

- **データ**: `money_reserves`（家族・年で1行。額）。その年の行が無ければ、前の年のいちばん近い行の額（`reserveAmountFor`）。
  紐づけた小分類は `money_categories.reserve`（家族で1つの予備費なので、年には持たない）。`money_bootstrap` の `reserves` で読む
- **数え方**（`reserveUsage`・`reserveBudgetRows`）: その年の支出の記録を日付の順に見て、紐づけた小分類の品目を、予備費の残りがあるうちは**その記録の大分類・月の予算**に同じ額だけ足す
  （その月の大分類が予算を超えたように見えない）。残りを超えた分は足さない（ふつうに予算を超える）
- **着地見込み**（§4.6）: 予備費で数えた分は、その月の大分類の予算として引く。**まだ使っていない分**は、今年は今月から12月へ均等に置いて引く（`RESERVE_ROW` の行）。
  先の年（今年の翌年まで）は12か月へ均等に。過ぎた年の残りは置かない
- **画面（予算）**: 見出し「予備費　年 ¥◯」（押すと年の額を決める）。枠の中は「小分類」の見出し（押すと折りたたむ）の下に、紐づけた小分類（押すと外す）と「＋ 追加する」。
  予算の設定の画面なので、実績は出さない

### 9.2 証券の評価額（銘柄ごと。§7 の6。2026-10-08に設計）
評価額＝銘柄ごとの**保有数 × 価格**（ドル建ては × 為替）。価格はサーバーで1日1回取り、評価額の増減を出す。

#### 9.2.1 価格の取り方（2026-10-08に、本番DBの `pg_net` から実際に取って確かめた）

| 持っているもの | 取り方 | 確かめたこと |
| --- | --- | --- |
| 米国株・米国ETF（ドル建て） | **Alpha Vantage** の `GLOBAL_QUOTE`（ティッカーで1銘柄1回） | JSON で終値（`05. price`）と取引日（`07. latest trading day`）が返る。無料の鍵は1日25回・1分5回（第三者の資料。公式のページは作業環境から開けない）。1日1回・1銘柄1回なので足りる。鍵は Supabase の secret（`ALPHA_VANTAGE_API_KEY`）に置く |
| 国内の投資信託 | **投資信託協会「投信総合検索ライブラリー」の基準価額CSV**（ISINコードと協会コードで1本1回）。運用会社ごとのCSVは使わない（1か所で全社の投信が取れる） | CSV（Shift_JIS）で、年月日・基準価額（円、1万口あたり）・純資産総額・分配金・決算期が**設定来ぶん**返る。営業日の夜に更新される。利用規約は作業環境から開けず未確認 |
| 為替（ドル → 円） | **Frankfurter**（ECB の参照レート、鍵なし） | JSON で `{"base":"USD","date":…,"rates":{"JPY":…}}` が返る。ECB の営業日ごとに1回。証券会社の為替とは少し違うので、評価額は目安 |

- 取りに行くのは**毎朝7時（日本時間）に1回**（pg_cron → Edge Function `fetch-security-prices`）。米国市場の終値と、前の営業日の夜に出た基準価額がそろう時刻
- Alpha Vantage の無料の鍵は1日25回まで。毎朝は米国株1銘柄1回、銘柄を足したときも1銘柄1回（週次）。
  1分5回までなので12.5秒ずつ空ける（米国株が10銘柄を超えると、Edge Function の時間の上限 150秒に近づく）
- 2026-10-08に、持っている銘柄（米国株9・投信4）が全部取れることを確かめた（銘柄はここに書かない）。
  投信は ISIN と協会コードの**両方**が要る（片方だけでは返らない。協会コードが違うと別のファンドが返る）
- Alpha Vantage は「1秒に1回まで」もある（並べて呼ぶと断られる。2026-10-08に確かめた）。1銘柄ずつ間を空けて呼ぶ
- アプリを通さずに銘柄を入れたときは、関数を cron と同じ秘密のヘッダーで `{ backfill: 銘柄のid }` として呼ぶと、過去1年を作る
- 取れなかった日（休場・祝日・失敗）は、その前に取れた価格を使う。価格の日付は取得元の日付（取引日・基準日）のまま持つ
- **過去の価格も取れる**（投信は設定来、為替は期間指定）。米国株は、日次の全期間が有料なので（2026-10-08に無料の鍵で断られた）、
  **週次の、分割・配当を調整した終値**（`TIME_SERIES_WEEKLY_ADJUSTED`）を使う。調整しない値だと、分割の前の値に今の保有数を掛けて跳ねる
  （2026年4月に1→5の分割をした銘柄が実際にある）。過去1年の推移は、米国株だけ週ごとの点になる
  過去の**保有数**は分からないので、**過去1年は今の保有数で作る**（2026-10-08に決定。§9.2.5）
- Google スプレッドシートを挟む案と、Yahoo!ファイナンスなどの画面から読み取る案は採らない（経路が増えて壊れやすく、規約に触れるおそれ）

#### 9.2.2 データ（migration 0070_money_wallets_securities.sql・0071_money_securities.sql）

```
money_wallets.type に 'securities'（証券口座）を足す（check の作り直し）
money_wallets に  icon_color（アイコンの色 '#rrggbb'。null＝種類ごとの標準の色）を足す（0074）
money_securities   銘柄。 id / family_id / name / kind('us_stock'|'jp_fund'|'cash') / code(ティッカー。投信は ISIN) /
                   fund_code(投信の協会コード) / currency('USD'|'JPY') / position / archived_at
                   （cash は預り金。価格は1。ドルの預り金は currency='USD'）
money_holdings     保有（預り区分ごとに1行）。 id / family_id / wallet_id(証券口座) / security_id /
                   account('nisa'|'nisa_tsumitate'|'tokutei'|'ippan') / quantity(株数・口数。小数あり) /
                   cost_price(取得単価。円。投信は1万口あたり。ドル建ても円で入れる) /
                   archived_at（wallet_id・security_id・account で1行）
money_security_prices  価格。 security_id / price_on(取得元の日付) / price（security_id・price_on で1行）
money_fx_rates     為替。 currency / rate_on / rate(1単位あたりの円)（家族によらない。読むだけ）
money_holding_values   保有ごとの日々の評価額。 holding_id / value_on(日本時間の日付) / quantity / price / fx /
                   value(円) / cost(円)（holding_id・value_on で1行）
```

- **推移は `money_holding_values` から出す**（毎朝その日の行を作る）。保有数を後から直しても過去の評価額は変わらない。
  保有を編集・追加したときは、その日の行を作り直す（トリガー。使わなくした保有は、その日から 0）。
  行を作るのは関数 `refresh_money_holding_values(p_from, p_to)`（今の保有数で。p_to の日は作り直し、前の日は無いときだけ作る）
- 評価額（円）＝ 保有数 × 価格 × 為替（投信は ÷ 10000）。取得額（円）＝ 保有数 × 取得単価（同）。評価損益 ＝ 評価額 − 取得額、％ ＝ 評価損益 ÷ 取得額
- 全部 `family_id` 単位のRLS（為替だけは家族によらない公開の値なので、ログインしていれば読める）
- 価格・評価額の書き込みはサーバー（Edge Function・pg_cron）だけ

#### 9.2.3 総残高へ入れる

- 証券口座の残高 ＝ **その日の評価額の合計**（`money_holding_values`。その日の行が無ければ前の日の行）。
  記録（振替など）からは数えず、補正もしない
- 総残高と総残高の推移に入れる（`walletBalanceOn`・`dailyBalances` で、証券口座だけ評価額を使う）
- 積立・買付の振替（口座 → 証券）は今までどおり記録する（出金元の口座の残高は減る）。
  証券口座の側は評価額で数えるので、保有数を直すまで評価額には入らない

#### 9.2.4 画面

- **口座の面**: 証券口座も種類ごとの一覧に並ぶ（残高＝評価額）。アイコンは証券を1つ足す
- **証券口座の詳細**（押す）: 上に**評価額**と**評価額の推移**（`BalanceTrend`。はじめは全期間。1ヶ月・半年・1年）、
  下に**保有銘柄の一覧**（銘柄名・評価額・評価損益の金額と％。損益は ▲緑／▼赤）。**Zaim と同じく預り区分ごとに1行**で、
  並びは 特定 → NISA成長投資枠 → NISAつみたて投資枠 → 一般（区分の中は銘柄の並び順）、預り金は最後（2026-10-08に変更）。
  一覧の下に「銘柄を足す」。補正のボタンは出さない
- **銘柄の詳細**（行を押す）: 上にその行の評価額と推移、下に詳細（評価損益・現在値（投信は基準価額）・取得単価・保有株数（投信は保有口数））。

  追加したときにその場で価格を取り、過去1年の評価額も作る

#### 9.2.5 決めたこと（2026-10-08）

1. **取得単価は円で入れる**（ドル建ても）。Zaim の画面に円で出ているのをそのまま入れる。取得時の為替は持たない
2. **過去1年の評価額は、今の保有数 × その日の価格で作る**（銘柄を追加したときに作る。保有数を直しても、作った過去の行は直さない）。
   その間に積立や売買があった分は合わないが、目安とする
3. 「評価額の増減を、入れたお金と運用の増減に分けて出す」（下の箇条）は今回は入れない（積立を止めているので、今は増減がほぼ運用の分になる）
4. **評価額の履歴は、開いたときに読む**（2026-10-09。口座の面を開いてから一覧が出るまで6秒近くかかったため）。
   `money_holding_values` は1年で数千行あり、全部を1000行ずつ順に読むと往復が増えて遅い。
   - 口座の一覧の残高に要るのは保有ごとの**最新の1行**だけなので、DBの `money_latest_holding_values(p_family_id)`（0075）で読む。
     アプリの `loadSecurities` は、はじめは最新の1行だけを `values` に入れる（`historyLoaded: false`）
   - 推移（総残高・証券口座・銘柄）を開いたときに `loadSecurityHistory` で履歴を読む（1ページ目で総数が分かるので、残りは並べて読む。
     読む列は推移に要るものだけ）。読めるまでは推移の所に「読み込み中...」を出す。一度読んだら、保存後の読み直しでも履歴まで読む
   - 価格の取得は今までどおり**1日1回**（毎朝7時5分、pg_cron → `fetch-security-prices`）。アプリは価格を取りに行かない

- **保有数は預り区分（NISA・特定など）ごとに持つ**。証券のアプリでは同じ銘柄が区分ごとに別の行に出るので、行ごとに見比べて直せるようにする
- **評価額の増減は、入れたお金と運用の増減に分けて出す**。積立・買付は振替（口座 → 証券）の記録があるので、評価額の増減からそれを引くと運用の増減になる
- 保有数は**人が銘柄を編集・追加して直す**（積立は今は止めている。§8 の4）。買付・売却・配当の再投資のときに直す
- 銘柄名・保有数・金額はリポジトリに書かない（家族の私的なデータ）

#### 9.2.6 起動の読み込みを1回にまとめる（2026-10-09）

家計タブの起動は、種類・予算・出金元・お店・定期・残高・記録・日用品の台帳・特別費の項目と予定・証券の銘柄と保有・最新の評価額の
**13本**を読んでいた（日用品の台帳は2026-10-09に削除し、いまは12本。`0084`）。Android の OkHttp は同じホストへの同時リクエストが5本までなので、3回に分かれて走る。DBは速い
（本番で約40ms、返す JSON は約500kB）ので、**往復をなくす**ほうが効く。

- DBの `money_bootstrap(p_family_id)`（0076）が、この13本を表の行そのままの JSON（`to_jsonb`）で1回で返す。記録は品目を `money_items` に入れた形。
  呼ぶ人の権限（RLS）で読む。アプリの `loadMoneyBootstrap`（`lib/api/moneyBootstrap.ts`）が呼び、行 → 画面の型への変換は個別に読むときと同じ
- 評価額の履歴は含めない（§9.2.5 の4。推移を開いたときに読む）。履歴を読んだあとの読み直しだけ、履歴も並べて読む
- 全か無か: 読めなければ起動の読み込み全体が失敗する（以前は証券だけ読めなくても他の面を出していた）。表が全部そろっているので許す
- 保存後の読み直し（お店・台帳・証券など）は、これまでどおり個別に読む。記録が数千件になって JSON が数MBを超えるようになったら、記録だけ分けて読むことを考える

  - 一番上に**総残高**（押すと**総残高の推移**。2026-10-08に、固定をやめて一覧と一緒に流れるようにした）、その下に**出金元ごとの残高**
    （カテゴリごと。Zaim と同じく**2列のタイル**。アイコンは記録の一覧と同じ `WalletTypeIcon`）。
    総残高に入れるのは使っている出金元だけ。**「確定／未確定」の印は出さない**（出しっぱなしでうるさいので外した。補正は、振り返りで抜けに気づいたときなど、
    通帳・銀行のアプリと違うときだけ行う）
  - **数え方**（`walletBalanceOn`）: 残高 ＝ 今日までの記録（支出・収入・振替）の合計 ＋ **補正の増減**の合計。補正が1つも無ければ記録の合計。
    **補正は日付と結ばない「ただの増減」**（2026-10-24。以前は「その日の終わりの残高」で、それ以前の記録は数えなかったため、補正より前の日付の記録を足しても残高が変わらなかった）。
    あとからどの日付の記録を足しても残高に入る。今日より先の日付の記録は入れない。
    出金元のない記録は数えない。収入は入金先に増え、支出は出金元から減り、振替は出金元から減って入金先に増える
    （DBの表は `money_wallet_balances` のまま。画面の言葉だけ「補正」にした）
  - **口座の詳細**（出金元を押す。証券口座は除く）: 上に残高と「残高を補正」、その下に「**履歴 / 推移**」の2つ
    （2026-10-08に、使わない「残高計算」のタブを外した）
    - **履歴**: その出金元の記録（支出・収入・振替の出金元か入金先）を日ごとに。押すと記録の詳細（`RecordDayList`。「記録」の一覧と同じ部品）。
      記録は口座ごとに持たず、記録の出金元・入金先から表示のたびに探すので、記録に出金元が入って保存された時点で自動で入る。
      **残高の補正**も同じ日の先頭に1行で混ぜる（「残高を補正」と**補正の増減だけ**。総額は画面の上にあるので出さない。補正した日の先頭。押すと取り消し）
    - **推移**: 日ごとの残高の折れ線（`dailyBalances`）と、残高が変わった日の一覧。期間は**はじめは全期間**で、1ヶ月・半年・1年に切り替えられる
  - **残高を補正する**: 詳細の上の「残高を補正」から。**日付は無い**。通帳・銀行のアプリの残高（マイナスも可。カードは初めからマイナス）を入れる。
    入れながら**今の残高**（記録と補正から出した額）と**差**を出す（差 ＝ 入れた額 − 今の残高）。差の分を、補正の増減として保存する（差が0なら補正しない）。
    補正した日は今日で、履歴の並びにだけ使う。同じ日に何度か補正したときは増減を足して1件にする。記録の側は直さない（差を埋める「残高調整」の記録は作らない）
  - **履歴に残すか選べる**（2026-10-08）: 補正のたびに「履歴に残す」（はじめは入）を選ぶ。残さない補正は、口座の履歴に行が出ないだけで、
    残高には同じに効く（列 `show_in_history`。0068）。残さなかった補正は画面に行が無いので、取り消すには差を打ち消す補正を入れる
  - **はじめの残高**: 記録は使い始めの月（取り込んだ分は2026年5月）からなので、最初の補正の増減が、使い始め前の残高を含む形になる。
    案内の文字は出さない（余計な文字を入れない。2026-10-08）
  - **総残高の推移**: 総残高を押すと開く。使っている出金元の合計を、日ごとの折れ線と、残高が変わった日の一覧で見る（期間の切り替えは同じ）
  - **折れ線に触れる（なぞる）と、その日の日付（曜日つき）と残高が線の上に出る**（点線・丸・吹き出し）。指を離しても、次に触れるか期間を変えるまで残る。**触れて離す（タップ）と、その日を選ぶ。なぞって選ぶのは、折れ線を0.25秒ほど押さえてから**（マウスはすぐ。2026-10-26）。押さえずに横へ払うと、画面の切り替えのスワイプになる（口座の詳細の履歴⇔推移を、折れ線の上からも行き来できるように。以前は折れ線の上の横の動きを日の選択に使い切っていて、推移から履歴へ戻れなかった）（推移の折れ線は総残高・出金元・証券の評価額で共通）
  - **カードの残高**（2026-10-08）: 残高は**未払いの総額**（マイナス）で、月末にはリセットしない。引き落としの振替（§3.4）が入ると、
    その分だけ減る。引き落とし日の前は、先月の請求と今月の利用が両方入っているので、**請求済み**（締め日を過ぎて引き落とし待ち）と
    **未請求**（直近の締め日のあとの利用）に分けて、**カードを押した先の詳細の上**に添える（`cardBilling`。締め日を設定したカードだけ。0円の行は出さない）。
    **一覧の行には出さない**（文字を増やさないため。2026-10-08）。
    例: 末日締め・25日払いなら、10月1日〜25日は「請求済み＝9月の利用（10/25払い）」と「未請求＝10月の利用」が並ぶ。
    引き落とし日は休日のずれを入れない目安
  - **出金元の追加・編集・削除・（使わなくしてあるものの）また使う**もこの面（追加は一覧の「出金元を足す」、編集は詳細の鉛筆。カードの締め日・引き落とし日・
    引き落とし口座を含む）。家計の設定（歯車）の「出金元」は外した。記録の入力中の「出金元を選ぶ」画面では選ぶだけ（2026-10-20に、足す・直すを外した）
  - **証券口座は別のPR**（§7 の6）。銘柄ごとの評価額（§9.2）ができるまでは口座の面に入らない。できたら、証券口座は
    「残高の推移と保有銘柄の一覧」→ 銘柄を押すと「上に評価額の推移、下に詳細（評価損益・現在値・取得単価・保有株数）」にする
- 消す前に、**Zaim の全期間の CSV を書き出して手元に残す**（かぞく手帳に取り込んだのは2026年5月以降だけ。§6）。
  書き出した CSV はリポジトリに入れない

### 9.5 Zaim の入出金通知メールから取り込む（2026-10-12に決定）
> **2026-10-20にやめた**（§9.9・§9.11）。銀行の入出金は Gmail から取り込まない。下は経緯として残す（突き合わせ・取り込みのルール・口座の対応は、カードの利用通知の取り込みでそのまま使う）

銀行の入出金を、Zaim が送る入出金通知メールから**自動でかぞく手帳へ取り込む**。取り込んだ明細（以下「明細」）は、
そのまま記録にするのではなく、**振替の組み合わせ → 自動で作った記録（見込み）との照合 → 手入力した記録との確認**の順に突き合わせ、
どれにも当たらないものだけを「未確認」に残す。

#### 9.5.1 届くメール（2026-10-12に、受信している Gmail で実物を確かめた）
- 差出人 `info@zaim.net`。Gmail では「プロモーション」に入る（取り込みは差出人で探すので関係ない）
- 通知金額は **1円以上**に設定済み（本文に「1 円以上の入金がありました」）。Zaim の連携口座すべてが1つの Zaim（1つの Gmail）に届く
- 形（入金・出金とも同じ。プレーンテキストにしたもの）:

| 部分 | 例 | 取り出すもの |
| --- | --- | --- |
| 件名 | `楽天銀行にて出金がありました（肥後銀行 （支店） 普通預金 （名義人）（依頼人名:（名義人） 振込予定日:2026年10月12日 管理番号:…））` | `{口座名}にて{入金\|出金}がありました（{内容}）`。内容は**最初の「（」から最後の「）」まで**（中にかっこが入れ子で入る） |
| 本文の1行目 | `新着の出金 10 月 12 日（月） ￥20,000 楽天銀行 肥後銀行 （支店） …` | `新着の(入金\|出金) {月} 月 {日} 日（曜） ￥{金額。カンマあり} {口座名} {内容}` |
| 本文 | `連携先として登録している楽天銀行にて 1 円以上の出金がありました。` | 照合用（口座名の確かめ） |

- **年が無い**ので、メールの受信日時から決める（受信月より大きい月なら前の年。12月の明細が1月に届く場合）
- **残高は入っていない**。残高はこれまでどおり記録から数え、ずれたときに補正する（§9.3）
- 明細を見分ける番号は無い。**Gmail のメッセージID**で1回だけ取り込む
- 例: 楽天銀行 → 肥後銀行への振込（20,000円）は、**楽天銀行の出金**（02:27着）と**肥後銀行の入金**（02:42着）の2通で届いた。
  Zaim の取得は口座ごとなので、**2通の間は数分〜数日あく**
- 入金の内容は `振込 （依頼人名）`。引き落とし・給与・ATM・カード代金の文面はまだ届いていない（届いたら§9.5.8 に足す）

#### 9.5.2 取り込みの経路
1. **Google Apps Script**（通知が届く Gmail のアカウントで動かす。自分のアカウントなので Google の審査・7日ごとの再認証は要らない）を
   **5分ごと**に動かし、`from:info@zaim.net subject:(入金がありました OR 出金がありました) -label:かぞく手帳済` を探す
2. 1通ずつ、メッセージID・受信日時・宛先・件名・本文の1行目を **Edge Function `money-feed-ingest`** へ POST する（読み取り＝解析はサーバーでする。
   文面が変わったときに Apps Script を直さずに済むように）
   - 合言葉: Apps Script のスクリプト プロパティに置いた鍵を `Authorization` で送る。サーバーは鍵のハッシュで家族を決める（`money_feed_tokens`）
3. 受け付けた（同じIDが既にある場合も）ら、スレッドにラベル `かぞく手帳済` を付ける。送れなかったものは次の回にまた送る
4. サーバーは**解析 → 口座を決める → 突き合わせ（§9.5.4）**を1回で行う。解析できなかったメールも捨てず、「読めない」として残す
- Apps Script のコードはリポジトリに置く（`tools/gas/gmail-feed.gs`）。貼り付けと時間トリガーの設定は手で1回だけ
- **取り込むのは開始日時より後に届いたメールだけ**（スクリプト プロパティ `START_AT`。動かし始めた日時にする）。
  2026-10-12に届いた2通（楽天銀行 → 肥後銀行の20,000円）は通知を確かめるための試しの振込。**取り込みを試すのに使い、そのまま本番に残した**
  （実際に動いたお金なので、振替の記録として正しい。§9.5.11）

#### 9.5.3 口座を決める
- 出金元（口座）に **「Zaim での口座名」**（`money_wallets.feed_name`）と **所持者**（2026-10-12に決定）を持たせる。
  家計の設定の「Zaim 取り込み」の**口座の対応**で入れる（2026-10-12に、出金元の編集ではなくここ1か所にした。届いた口座名が並び、押して出金元と所持者を選ぶ）
  - **所持者** ＝ 誰の口座か（表示名。例: 本人・妻・子）と、その人の **Zaim のアカウント**（Zaim に登録したメールアドレス＝通知の宛先）、
    **名義（カナ）**（`money_wallets.holder_name`・`holder_zaim_email`・`holder_kana`）
- 決め方（上から順に、1つに決まったところで止める）:
  1. 通知の**宛先**（Zaim のアカウント）と件名の**口座名**が両方一致する口座
  2. 内容の `依頼人名:` が**名義（カナ）**と一致する口座（自分の口座から振り込んだ出金は、依頼人名が口座の名義になる）
  3. 覚えた内容（§9.5.6）で口座が決まっているもの
  4. 決まらなければ「未確認」に入れ、「この明細の口座を選ぶ」（選んだら、宛先・口座名・内容を覚える）
- **同じ銀行の口座が2つ**（三井住友銀行が本人と子の2つ）: 所持者で分ける。**子の口座は、子用の Zaim アカウントで連携する**と、
  宛先で確実に分けられる（Gmail の `+` 付きアドレス〔例: `本人のアドレス+子の名前@gmail.com`〕で登録すれば、通知は同じ Gmail に届き、宛先だけが変わる。
  Zaim がこの形のアドレスで登録できるかは登録時に確かめる）。同じ Zaim のままなら、2 → 3 → 4 で決める

#### 9.5.4 突き合わせ（明細が届くたび。サーバーの関数 `money_feed_process`）
上から順に試し、当たったところで止める。「前後n日」は明細の日付で比べる（日数は取り込みの設定で変えられる。§9.5.6）。

1. **振替の組み合わせ**: 反対向き（出金⇔入金）で、**額が同じ**、**別の登録口座**、日付が**前後3日**、まだ組になっていない明細があれば、
   2つを1つの**振替**（出金した口座 → 入金した口座。日付は出金の日）にする
   - 先に届いた片方は、相手が届くまで「未確認」に入れておく（相手の明細を待っている印を出す）。相手が届いた時点で自動で振替になる
   - 先に届いた片方が**手入力との確認**（4）に入っていても、相手として組む（2026-10-12に試して直した。組まないと、同じ手入力に対して
     確認が2つばらばらに出る）。組んだあと、2つまとめて確認に回す
   - 片方を先に人が支出・収入として記録していた場合は、下の4と同じく確認に回す
   - 同じ条件の相手が2つ以上あるときは自動で組まず、確認に回す
2. **取り込みの設定のルール**（§9.5.6）: 上から順に条件を見て、最初に当たったルールの動き（記録にする・振替にする・補正のみ・記録しない など）をする。
   - 記録・振替を**作る**動きのときは、作る前に 4（手入力との確認）を先に見る。手入力があれば作らずに確認に回す
3. **自動で作った記録との照合**: その口座の、**固定費・固定収入・カード代金のルールで作った記録**（`recurring_id` があるか、カード代金の振替）で、
   明細とまだ結びついておらず、日付が**前後5日**（休日のずれ）のもの
   - **結ぶルール**（§9.5.6。「自動の記録と結ぶ」「補正のみ」）が当たったときは、それに当たる記録と結び、**額を明細の額にして確定**する（見込みの印を外す。§3.3 の確定と同じ）
   - 覚えていないときは、**額が同じ**記録が1つだけなら結んで確定する。額が違う・2つ以上あるときは「未確認」に回し、候補として出す
   - カード代金の振替を明細で確定したら、§3.4 の月末の照合にもその額を使う（明細の合計と比べる額は変えない）
4. **手入力した記録との確認**（人が先に入れていた場合）: その口座の、人が入れた記録（ルールで作っていない・明細と結びついていない）で、
   **額が同じ**、日付が**前後3日**のものがあれば、**記録を作らず「確認」に回す**（下の §9.5.5）
   - 振替（1）のときは、出金した口座・入金した口座のどちらかに当たる手入力（振替・支出・収入）を探す
5. どれにも当たらないものは**「未確認」**に残す（記録は作らない）

- 結びついた・作った記録には、どの明細から来たかを持たせる（`money_records.feed_id`）。記録の詳細に「Zaim から取り込み」と出す
- 明細から作った・確定した記録を人があとで直しても、明細は結びついたまま（額を直したら、記録の額を正とする）

#### 9.5.5 手入力があったときの確認
- 確認は「未確認」の一覧の先頭に、**明細と、当たった手入力の記録を並べて**出す。選ぶもの:

| 当たった手入力 | 選ぶもの | 結果 |
| --- | --- | --- |
| 同じ口座の組の**振替** | **同じ取引** | 手入力の振替に明細を結ぶ（日付・額は手入力のまま。違っていれば明細に合わせるかを聞く） |
| | 別の取引 | 新しく振替を作る |
| 片方の口座の**支出か収入**（振替を支出・収入で入れていた） | **振替に置き換える** | 手入力の記録を消し、振替を作る |
| | 手入力を残す | 明細を手入力に結び、振替は作らない（もう片方の明細は単独の明細として 2〜5 へ進む） |
| | 別の取引 | 新しく振替を作る |
| 単独の明細と同じ額の**支出か収入** | **同じ取引** | 手入力に明細を結ぶ |
| | 別の取引 | 2〜5 へ進む |

- 逆の順（明細が先に取り込まれ、あとから人が同じものを入れる）も防ぐ: 記録の入力で口座を選んで保存するとき、
  その口座に**同じ額・前後3日の明細から来た記録**があれば「同じ取引が取り込まれています」と出し、**入れる／入れない**を選ばせる
  （2026-10-12に実装。新しく入れる記録だけ。口座は入れる記録の出金元・入金先のどちらかが、明細から来た記録の出金元・入金先のどちらかと同じなら同じとみなす。
  日数は取り込みの設定の「手入力との確認」の幅。明細から来た記録は、新しい500件の明細が結んだ・作った記録。`feedDuplicates`。入れないを選ぶと記録の入力に戻る）

#### 9.5.6 取り込みの設定（家計の設定に「Zaim 取り込み」を足す。2026-10-12に決定）
家計の設定（歯車）に **「Zaim 取り込み」** の欄を足し、取り込みに関わる設定を**ここ1か所で**決める。

| 項目 | できること |
| --- | --- |
| **取り込みの状態** | 最後に明細が届いた日時・この1か月の件数・「読めない」の件数。**取り込みの鍵**の発行と作り直し（Apps Script に貼る。作り直すと古い鍵は使えない）。取り込みの開始日時（§9.5.2 の `START_AT` と同じ値を見せる） |
| **口座の対応** | Zaim の口座名（＋宛先）ごとに、かぞく手帳の出金元と所持者（§9.5.3）を決める。届いたことのある口座名は自動で並び、対応が無いものに印。出金元の編集（「口座」の面）で入れたものと同じ値 |
| **取り込みのルール** | 明細をどう扱うかのルールの追加・編集・並べ替え・削除（下の表）。上にあるルールから先に見る |
| **突き合わせの幅** | 振替の組み合わせ（はじめは前後3日）・自動の記録との照合（前後5日）・手入力との確認（前後3日）の日数 |

**取り込みのルール**（`money_feed_rules`）は「**条件**」と「**動き**」の組:

| 条件（全部に当たったとき） | 中身 |
| --- | --- |
| 口座 | 出金元を1つ、または「どの口座でも」 |
| 向き | 入金・出金・どちらでも |
| 内容 | **含む文字**（例: `ATM`・`ｶｰﾄﾞ`）か、**内容の決まった部分が同じ**（覚えたルール。下の「次から同じ内容は自動で」で作る） |
| 金額 | 範囲（任意。例: 1,000円以上） |

| 動き | 結果 | 例 |
| --- | --- | --- |
| **記録にする** | 支出／収入の記録を作る（カテゴリ・お店を決めておく） | 電気代の口座振替 → 支出・水道光熱費 › 電気代 |
| **振替にする** | 相手の出金元を決めて振替を作る（出金なら 口座 → 相手、入金なら 相手 → 口座） | **ATM の出金 → 財布（家族）への振替** |
| **自動の記録と結ぶ** | 固定費・固定収入のルールを1つ決め、そのルールで作った記録（前後n日）と結んで、**額を明細の額にして確定**する。当たる記録が無ければ「未確認」 | 給与の振込 → 固定収入「給与」 |
| **補正のみ** | **新しい記録は作らない**。その口座から引き落とすカード（`pay_wallet_id`）の、カード代金の振替（自動で作った見込み。前後n日）があれば額を明細の額にして確定し、無ければ「記録しない」で済ませる（残高のずれは口座の補正で直す） | **カードの引き落とし**（カードの利用は日々の記録で数えているので、二重に数えない） |
| **記録しない** | 何もしない（明細は「記録しない」として残す） | 利息など、気にしない小さな入金 |

- 内容の文字（ATM・カード会社の名前）は銀行ごとに違い、まだ実物が届いていない（§9.5.8）。はじめは「ATM の出金 → 財布（家族）」
  「カード会社の引き落とし → 補正のみ」の**ひな形**を用意し、実物が届いたら含む文字を合わせる
- 補正のみで、カード代金の振替が2枚以上（同じ口座から同じ日に落ちる三井住友カード2枚など）当たるときは、**額が同じもの**と結ぶ。決まらなければ「未確認」
- ルールで作った・結んだ記録の詳細には、どのルールで決まったかを出す（押すとそのルールの編集へ）

#### 9.5.6.1 「未確認」の明細を片づける・覚える
- 場所: 家計タブの「記録」の面のいちばん上（一覧と一緒に流さず固定）に「**未確認 n件**」（0件なら出さない）。押すと一覧。
  1件以上あるあいだは、面の切り替えの「記録」の右上に赤い点を出す（0件になったら消す。2026-10-18。以前は「口座」の面の上）。口座の詳細の履歴にも、その口座の未確認を先頭に出す
- 1件を押すと、**額・日付・出金元・お店**を見せて、**記録を作成する／記録しない**だけを選ぶ（2026-10-19）:
  - **記録を作成する**: 記録の入力を、**額・日付・出金元・向き（支出／収入）・お店（利用先から当てたもの。当たらなければ利用先そのまま）**を入れた状態で開く。
    額はカテゴリの決まっていない1行で入れ、カテゴリは人が選ぶ（選ぶまで保存できない。同じお店でも、複数のカテゴリを買う・
    いつもと違うカテゴリを買うことがあるため。額を分けて品目を足してもよい）。
    保存すると、その記録と明細を結ぶ（`money_feed_resolve` の結ぶ。未確認から消える）。閉じたら明細は未確認のまま
  - **記録しない**: 残高の補正で済ませるものなど。明細は「記録しない」として残す（同じ明細をまた出さない）
  - 以前あった「振替にする」（Gmail 取り込みでは振替の通知が来ない）・「既にある記録と結ぶ」（手入力した時点で確定しているのでほぼ使わない）・
    「次から同じ内容は自動で」は、未確認の画面から外した。取り込みのルール（§9.5.6）は家計の設定で作る
- （以前）記録にする・振替にする・結ぶ・記録しないとき、「**次から同じ内容は自動で**」を選べた（はじめは入）。
  **口座 ＋ 向き ＋ 内容の決まった部分**（内容から数字・日付・`（依頼人名:…）`・`管理番号:…` を除き、全角半角をそろえたもの）を条件にした
  取り込みのルール（§9.5.6）を、選んだ動きで**一覧のいちばん下に**足す（「覚えたルール」の印。編集・削除は同じ欄で）
- 「読めない」メール（解析できなかったもの）は件名をそのまま出し、手で口座・向き・日付・額を入れて同じ流れに乗せる
  （2026-10-12に実装。`money_feed_fill`。入れると未確認に戻して突き合わせ、振替の相手が来ていれば組む。片づかなければ同じ枠で続けて選ぶ）。
  「記録しない」も選べる

### 9.6 カードの利用通知メールから取り込む（2026-10-15に決定）

Zaim を解約するので、銀行の入出金は取り込まない（メールに金額が出ないため）。代わりに**カード会社の利用通知メール**を、
§9.5 と同じ明細（`money_feed`。`source = 'card_mail'`）として取り込み、同じ突き合わせ・未確認・取り込みのルールを使う。

#### 9.6.1 届くメール（2026-10-15に、受信している Gmail で実物を確かめた）
- **三井住友カード**（`statement@vpass.ne.jp`。件名「家族カードご利用のお知らせ【三井住友カード】」など）: 本文に
  `ご利用カード：三井住友カードＶＩＳＡ（ＮＬ）`・`◇利用日：2026/10/15 13:51`・`◇利用先：YOKAMONNE JIYONANTEN`・`◇利用金額：4,415円`
- **楽天カード**（`…@mail.rakuten-card.co.jp`）: `■利用日:`・`■利用先:`・`■利用金額: … 円` の形を想定（実物はまだ届いていない。届いたら確かめる）。1通に何件も入ることがあるので、件ごとに明細にする
  （`source_id` は「GmailのメッセージID」「ID#2」…）。楽天カードは楽天市場・楽天モバイルの支払いがほとんど
- どちらも**承認照会の通知で、確定した請求ではない**（ガソリン・取消で額が変わる。携帯電話・ETC などの継続的な利用は届かない）。
  確定した額は月末の照合（§3.4）で見る
- 取消の通知・利用の行が読めないメールは「読めない」に残す（人が片づける）

#### 9.6.2 出金元（口座の対応）
- 口座名（`account_name`）は、**三井住友カードは「ご利用カード」に Amazon が入っていれば「三井住友カード（Amazon）」、それ以外は家族カードも含めてすべて「三井住友カード」**、

- 出金元に結ぶのは §9.5.3 と同じ（初めて届いたら「口座を選ぶ」。次から同じ口座名はその出金元）

  （取り込みのルール・自動の記録との照合・手入力との確認）は同じ

#### 9.6.3 お店とカテゴリ
- **覚えたお店だけ自動で記録にし、ほかは「未確認」に入れる**（2026-10-15に決定）。自動で記録にするのは、取り込みのルールで覚えたもの
  （未確認で「記録にする」＋「次から同じ内容は自動で」。§9.5.6）
- 未確認の「記録を作成する」で開く記録の入力には、**利用先に当たるお店**（`money_feed.store_hint`。Edge Function が取り込むときに入れる）を初めから入れておく
  （以前はそのお店でいちばん多いカテゴリ `storeCategoryGuess` も入れていたが、2026-10-19にカテゴリは人が選ぶことにした。§9.5.6.1）。
  **当て方は、登録したお店の名前をローマ字にして当てるだけ**（`matchStoreByRomaji`）。ひらがな・カタカナ・英字だけの名前が対象。
  書き方の揺れ（ヘボン式と訓令式、「じょ」を JO と JIYO、長音、撥音、促音）はそろえてから比べ、利用先がその名前で始まれば当たり
  （例: よかもんね → YOKAMONNE JIYONANTEN）。当たらなければ利用先をそのままお店にする
  - **2026-10-22にやめたもの:** 同じ利用先の前の記録のお店を覚えて入れる（iDデビットのように利用先が同じ別の店に入る）、
    登録したお店の一覧から Claude Haiku 5.5 に選ばせる（XPRICE が「ローソン」になるなど、外れたお店が入った）
  - **利用先が「iDデビット」とだけ載るデビットの通知は、お店を空にする**（店名が載らないため。人が入れる。`NO_STORE_MERCHANTS` / `feedStoreName`）
- お店は記録の入力の中で直せる（登録したお店から選ぶ／打った名前を「この記録だけに使う」か「お店に登録して使う」）

### 9.7 Amazon の注文メールの品目を、カードの利用通知に割り振る（2026-10-16に決定）

**2026-10-20: やめた。** Amazon の買い物は注文メールから明細を作る（§9.10）。以下は経緯として残す。

Amazon は注文した日ではなく**発送した日**にカードへ請求が立つ。メールは「**注文メール → カードの利用通知**」の順に届き、
1回の注文でも発送が分かれれば利用通知は何通かに分かれる（A500円・B300円・C250円の注文に、500円と550円の2通、など）。
利用通知には合計しか無いので、**注文メールの品目を覚えておき、利用通知が届いたら請求額に合う品目を割り振って、品目つきの記録にする**
（§9.6.3 の「記録は1つのカテゴリ」の例外。割り振れたときだけ）。

#### 9.7.1 届くメール（2026-10-16に、受信している Gmail で実物を確かめた）
- 注文メール: 差出人 `auto-confirm@amazon.co.jp`、件名「注文済み: 「…」2点とさらに4点の商品」。**1通に注文が何件も入る**（注文番号ごと）。本文は
  `注文番号` の次の行に番号、品目は `* 品名` / `数量: N` / `{単価} JPY`、注文ごとの末尾に `合計` と額
  - **品目の額は単価**（個数をかける前）。単価 × 個数の和は「合計」と一致しないことがある（実物: 4,859円に対し合計4,607円、11,648円に対し11,499円。
    クーポン等の値引きと思われる）。この差を**調整額**（`money_amazon_orders.adjust`＝合計 − 品目の和）として覚え、値引きなら割引率の初めの値に使う（§9.7.3）
  - **合計が 0 円の注文は覚えない**（2026-10-16に決定。実物: 品目に935円・1,320円と載るのに `合計 ￥0`。全額がポイント・ギフト券などで、カードに請求が立たない）。
    単価が 0 円の品目（無料の商品）も覚えない。1通に0円の注文と払う注文が入るときは、払う注文だけ覚える（`parseAmazonOrderMail`）
    覚えるものが無いメールは、関数が `skipped` と返す（読めない書式は `ignored` で、ログに残る）。Apps Script は、スレッドのメールが全部 `skipped` なら
    ラベル **「かぞく手帳対象外」**、そうでなければ「かぞく手帳済」を付ける（2026-10-17に決定。どちらも付いたスレッドは探さない）。
    ラベルを付けたスレッドは**受信トレイからアーカイブ**する（ラベルの中には残る。未読のまま）。すでに付いて受信トレイに残っているものは、関数 `archiveLabeledThreads` を手で実行して片づける
- カードの利用通知（Amazon）: §9.6.1 と同じ形。実物はまだ届いていない（届いたら、利用先の表記を確かめる）。
  Amazon の利用かどうかは、**利用先に Amazon・アマゾンが入っているか、カード名に Amazon が入っている**（`isAmazonCharge`）

#### 9.7.2 覚える（注文メールが届いたとき）
- Apps Script（`tools/gas/gmail-feed.gs`）が差出人 `auto-confirm@amazon.co.jp`・件名「注文済み」のメールも送る。**前の版を貼ってある場合は貼り直す**
- Edge Function `money-feed-ingest` が読み（`_shared/amazonOrder.ts`・`npm run test:amazon-order`）、注文と品目を `money_amazon_orders`・`money_amazon_lines` に入れる。
  同じ注文番号は1回だけ。開始日時（`START_AT`）より前のメールは入れない
- 品目の種類（カテゴリ）はこのとき決めておく: **同じ品名（`money_items.receipt_name`）の過去の品目の種類 → 無ければ Claude Haiku 5.5 に小分類の一覧から選ばせる**
  （§10.3 と同じ手本の考え方。決まらなければ空のまま）。記録の品目の `receipt_name` にはメールの品名をそのまま入れるので、
  直して保存すると次の注文の手本になる。記録の品名（`name`）は、先頭の【EC限定】などを外して40字までに縮めたもの
- **直した品名・種類は、次から自動で当てる**（2026-10-16）。Amazon の品名は長い（検索用の言葉が並ぶ）ので、記録の入力で「Babygoo おむつ防臭袋」のように直して保存する。

#### 9.7.3 割り振る（Amazon のカードの利用通知が届いたとき）
- **値引きは商品ごとに掛かる**（2026-10-16。実物で確認）。2026-09-14の注文（アタック 1,379円・ブラックキャップ 1,509円。小計 2,888円・割引 −138円・請求 2,750円）は、
  定期おトク便（自動配達）のアタックだけが 1,241円（10%引き）で請求され、ブラックキャップは値引きなしだった。
  **全体への按分ではない**（同日、按分と書いた資料を見て一度そう作ったが、実物で外れたので取り下げた）。
  2026-10-16の注文の差 252円も、アタック 1,100円の10%（110円）とディアナチュラ 1,419円の10%（142円）の合計で説明がつく。
  注文メールも発送メールも品目の額は値引き前で、ポイントの利用額・どの商品の値引きかは載らない
- そこで、注文メールの「合計」が品目の和より安いぶん（`money_amazon_orders.adjust` がマイナス）を**値引きの予算**として持ち、
  **請求との差がその範囲に収まる組み合わせ**を当てる（`matchAmazonCharge` の `discountLeft`。割り振った値引きは `discount_used` で予算から引く）。
  合計が品目の和より**高い**ときの差は、送料などの上乗せ（`fee`）として、残りの全部をまとめた請求に足す
- 覚えている注文（90日以内）のうち、**まだ割り振っていない品目**から、請求額に合う組み合わせ S を探す（同じ注文の中。注文をまたぐ組み合わせは当てない）。
  S の値引き δ ＝（S の品目の和）−（請求 − 送料など）として、次の順に見る
  1. **δ = 0**（値引きなしで額が合う）。古い注文から。同じ額になる組み合わせが複数あるときは、注文メールで先に並んだ品目
     （額は合うので、違っていれば記録の入力で品目を直す）
  2. **0 < δ ≤ 残りの予算**（値引きのある商品が当たる）。**額の違う候補が複数あるときは当てない**（紛れるので未確認に回す）
     - 例（実物）: アタックの請求 1,241円は、アタックだけが当たる（ブラックキャップに当てると 268円引きで予算 138円を超える）。ブラックキャップの 1,509円は①で当たる
  3. **δ が予算を超える**（Amazon ポイントの利用など。額は載らない）。超えたぶんが品目の和の2割以内（`MAX_UNKNOWN_DISCOUNT`）の候補のうち、割合がいちばん小さいもの。
     ただし、額の違う別の候補が割合で2倍以内に並ぶときは当てない
  - **注文の残りの全部を請求するときは、予算を使い切るはず**なので、δ が残りの予算より小さいものは外す（アタックだけを 1,379円で請求 → 値引きが残るので当てない）
  - δ < 0（請求の方が品目の和より高い）は当てない
- 当たったら、出金元・日付（利用日）はこれまでの利用通知と同じで、**品目ごとの行**（個数 × 単価・種類）を持つ支出の記録にする。お店は利用先に当たるお店（§9.6.3）、無ければ「Amazon」。
  **品目の額は、その発送の値引きを品目の価格の比で配った額**（1つの品目だけの発送なら、その品目の値引き。端数は小数部の大きい品目から1円ずつ。
  個数で割り切れなければ1個として扱う。レシートの外税の配り方と同じ考え方）。送料などは「送料など」の1行（種類はいちばん金額の大きい品目と同じ）。
  **品目の和より高い請求・半分より安い請求は作らない**（DB の `money_feed_amazon_create`。0112）
- 例: 注文（A500・B300・C250）→ 利用通知500円はA、550円はB・Cの2つの記録になる（550円が先に届いても、B・C → 残りのA の順になるだけ）
- 割り振りは Edge Function が決め（`money_feed.amazon_line_ids`）、DB の `money_feed_amazon_create` が、品目がまだ空いていて額が合うときだけ記録を作る。
  `money_feed_process` では、**手入力との確認（同じ額・同じ出金元の手入力の記録がある）のあと、取り込みのルールで自動の記録を作る前**に呼ぶ
  （手入力と二重に作らない／覚えたお店のルールより品目つきを優先する）
- 当たらなければ今までどおり（覚えたルール → 未確認）。品目は空いたまま残るので、次の利用通知で当たる
- 出金元の口座の対応が済んでいない（初めての口座名）ときは、「口座を選ぶ」のあとの突き合わせ直しで同じ割り振りが働く

- **2026-10-18: 自動で記録するのをやめた（0116）。** Gmail の明細は、確かめてから記録する（ルール・振替の組み合わせで作るもの以外）。
  口座の対応を保存したときの突き合わせ直しで、「三井住友カード（Amazon）」を誤って銀行に結んだまま品目つきの記録が2件作られたため。
  割り振り（`amazon_order_id`・`amazon_line_ids`）は明細に残すが、`money_feed_process` は `money_feed_amazon_create` を呼ばず、未確認に回す。
  未確認から品目つきで記録する画面は、まだ作っていない

#### 9.7.4 まだやらないこと

### 9.9 カード名の読み分けと、取り込まない利用通知（2026-10-20に決定。PR1）

取り込む元をお店とカードで1つに決めた: **Amazon・楽天市場の買い物は注文メールから、Olive フレキシブルペイの利用（クレジット・デビット）は利用通知から**。

### 9.13 Amazon の明細を発送パッケージ（＝請求1件）ごとにする（2026-10-23に決定）

**前提**: Amazon は**発送した日に、発送パッケージごとに**カードへ請求する。別々に注文した品目が同じ荷物になれば、その合計で1回の請求になり、
1つの注文が何個の荷物に分かれれば請求も分かれる。カードの利用通知は請求そのものではない（§9.9 のとおり捨てる）。
今までは注文単位で記録していたので、合計は合っても**記録とカードの明細の請求がかみ合わず、締めで振り返るのに苦労した**。
記録の日付も注文日だと、発送が翌月になったときに締めの月がずれる。

**決めたこと**
- **未確認の明細は、荷物1つ（＝請求1件）につき1件**。注文メールと発送メールが**両方そろうまで、未確認に出さない**（§9.10 の「注文ごと」「メール1通につき1件」（0131）は使わない）
- **日付は発送日**（発送メールの受信日、日本時間。振り返りの利便性を優先）
- **注文メール**: 品目・個数・単価と、注文の合計（値引き・ポイントを引いた、払う額 = 真の価格）を覚える（今まで通り。`money_amazon_orders`・`money_amazon_lines`）
- **発送メール**（`shipment-tracking@amazon.co.jp`、件名「発送済み：「…」」）: 荷物1つにつき1通。本文は注文メールと同じ形（`注文番号` / `* 品名` / `数量: N` / `{単価} JPY` / `合計`）。
  **載る単価・合計は値引き前**（実物: 注文メールの合計 136円＝ポイント利用 の焼き網シートが 1,248円）なので額は使わず、**どの注文のどの品目が何個、同じ荷物に入ったか**と日付だけを使う
  （`parseAmazonShipmentMail`。表 `money_amazon_shipments`・`money_amazon_shipment_lines`）
- **額**（注文メールの額から。2026-10-23に変更、0133）: 荷物の額 = 荷物の品目の値引き前の額 − その荷物に乗る値引き
  - 注文メールの「合計」は**注文番号ごとに1つ**で、品目ごとの値引き後の額は載らない（品目の額は値引き前）。
    注文番号の品目が全部同じ荷物で届けば、その注文の合計がそのまま荷物の額になる（1回に1商品で注文すれば必ずこれ）
  - 値引き（品目の和 − 合計）は、品目ごとに「なし・5%・10%」（定期おトク便。1個あたり四捨五入 × 個数）で説明できる組み合わせが
    **1通りだけ**なら、その品目に乗せる（荷物が分かれても、値引きの付いた品目の荷物に乗る）
    - 例（実物 250-7991927）: 合計 4,607円。アタック 1,100 の 110 ＋ ディアナチュラ 1,419 の 142 = 252 だけが当てはまる
      → 荷物A（アタック・ディアナチュラ）2,267円、荷物B（防臭袋 1,170×2）2,340円（Amazon の請求と同じ）
  - 当てはまらない値引き（ポイント・クーポン。組み合わせが2通り以上も）・送料などは、**注文の最後の荷物**（注文の全部の個数が発送された荷物）の
    いちばん大きい品目に乗せる（注文の荷物の額の和 = 注文の合計）。荷物が分かれたときは請求とずれることがあるので、記録の入力で値引きの行を直す
    - 例: パンパース 5,824円×2・合計 11,499円が1個ずつ2回発送 → 5,824円・5,675円
- 「記録を作成する」は、荷物の品目（発送した個数・**値引き前の単価**）と荷物の額で開く。**値引きは品目に配らず、品目の下に「値引き」のマイナスの行**
  （カテゴリはその品目と同じ。新しいカテゴリは作らない。レシートの値引き（§10.5）と同じ形）。DB の `money_feed_order_lines` が品目ごとの値引き（`discount`）を返し、
  アプリの `feedOrderItems` が行を足す。送料など（値引きがマイナス）は「送料など」の行。前の作りの明細（注文ごと・メールごと）は、合計との差を
  いちばん金額の大きい品目のカテゴリに1行（「値引き」か「送料など」）
- 荷物の品目は、注文番号と品名で注文の品目に結ぶ。品名で当たらなくても、その注文でまだ発送していない品目が1つだけならそれに結ぶ。
  **1つでも結べなければ待つ**（注文メールがあとから届いたら、そこで明細を作る。`money_amazon_order_receive`）
- 0円の荷物（ポイント・ギフト券だけ）は明細を作らない。前の作り（注文ごと・メールごと）で記録した・確認中の注文を含む荷物も作らない（二重にしない）
- Gmail のラベル: 発送メールは荷物の明細の状態で「未確認」→「済」。注文メール・注文メール待ちの発送メールは「済」

**DB・進め方**
- migration `0133_money_amazon_discount_lines.sql`（本番に適用済み）: 荷物の額の決め方（値引きを品目に当てはめる）と、`money_feed_order_lines` の品目ごとの値引き
- migration `0132_money_amazon_shipments.sql`（本番に適用済み）: 表 2つ（関数だけが触る。service_role だけに GRANT）、`money_amazon_shipment_feed`・`money_amazon_shipment_receive`、
  `money_amazon_order_receive`（明細を作らず、待っている荷物の明細を作る）、`money_feed_order_lines`（荷物の明細）。
  切り替えで、注文ごと・メールごとに作った未確認の明細は「記録しない」にした（発送メールが届けば荷物の明細として出直す）
- Edge Function `money-feed-ingest`: 発送メールを読む（デプロイ済み）
- **Apps Script（`tools/gas/gmail-feed.gs`）の貼り直しが要る**（探す差出人に `shipment-tracking@amazon.co.jp`、件名に「発送済み」を足した。関数名・プロパティ・トリガーはそのまま）。
  探すのは最後にうまく動いた時刻の1日前からなので、それより前に届いた発送メールは取り込まれない
- まだやらないこと: キャンセル・返品・発送メールが来ない荷物（デジタルの商品など。未確認に出ない）

## 10. レシートの読み取り（2026-10-12に検討）

レシートを撮ると、お店・日付・品目（品名・個数・単価・金額）・カテゴリ・出金元を入れた状態で記録の入力が開く。
人が確かめ、直すところだけ直して保存する。**黙って保存はしない**。

### 10.1 決めたこと（2026-10-12）
- **読み取りは Claude Haiku 5.5**（Edge Function から呼ぶ。鍵はサーバーにだけ置く）。比べたもの:

| 方式 | 費用 | 品目の精度 | カテゴリの推定 | 見送った理由 |
| --- | --- | --- | --- | --- |
| ML Kit（端末内のOCR）・Cloud Vision | 無料 | 低〜中（文字だけ。品名と金額の対応・値引きの行は自前） | ✕ | 読み取りの規則を作る手間と、直す量が多い |
| Azure Document Intelligence（レシート） | 月500枚まで無料 | 中〜高 | ✕ | カテゴリが出せない。日本語レシートの対応が不確か |
| Gemini Flash の無料枠 | 無料 | 高 | ○ | 入力が学習・人の確認に使われる（家計のデータは避ける） |
| Gemini Flash（有料） | 約1.3円/枚 | 高 | ○ | Haiku 5.5 の数倍 |
| **Claude Haiku 5.5** | **約0.1〜0.2円/枚**（月60枚で十数円） | 高 | ○ | ― |

  - 試算（1ドル150円）: 1506×2000px のレシートで、画像 約4,000・指示 約500 トークン（$0.10/100万）、出力と思考 約1,300〜2,300 トークン（$0.50/100万）。
    スキャナーで切り抜き、長辺1,000px程度に縮めると画像は約1/4になる
  - 使いすぎの歯止め: Edge Function で**家族ごとに月200枚まで**。Anthropic の管理画面で月の支払いの上限（5ドル）
- **撮影は mobile は ML Kit ドキュメントスキャナー**（`react-native-document-scanner-plugin`。縁を見つけて傾きを直し、レシートの幅で切り抜く）。
  長いレシートは上下に分けて複数枚撮り、まとめて1回で読む。PWA版は撮ったままの写真を送る（背景はAIに無視させる）
- **写真は保存しない**（読み取りに使って捨てる。§3.2）
- **訓練（学習させ直し）はしない。** 家族の設定（カテゴリ・お店・出金元）と過去の記録を毎回渡し、直した結果が次の手本になる（§10.3）

### 10.2 読み取りで渡すもの・受け取るもの
- 渡す: 画像、種類の一覧（小分類。`money_categories`）、お店の一覧（`money_stores`）、出金元の一覧（名前と種類）
- 受け取る（形を決めたJSON）: お店（レシートの表記）・日付・支払い（現金／カード名・下4桁）・品目（レシートの表記・整えた品名・個数・単価・金額・カテゴリの候補）・
  レシートの合計・税（8%／10%の対象額と税額、内税か外税か）
- 指示に入れること: 同じ税の欄・合計が2回写っていても1回として読む。複数枚は境目の同じ行を二重に読まない

### 10.3 覚える（新しい表は作らない）
- 列を2つ足す: **`money_items.receipt_name`**（レシートに印字された品名そのまま。手入力の品目は null）、
  **`money_records.receipt_store`**（レシートに印字された店名そのまま）
- 次に同じ表記が来たら、過去の品目・記録を表記で引き（**新しい記録を優先**）、直したあとの品名・カテゴリ・お店を入れる。
  直して保存したものがそのまま手本になるので、別の設定の作業も、あとからの補正もいらない
- 略した品名で外れることが多ければ、そのときに対応の表を考える（今は作らない）

### 10.4 項目ごとの入れ方

| 項目 | 登録・手本がある | 無い |
| --- | --- | --- |
| 出金元 | 支払いの欄から当てる（「お預り／お釣り」→ 現金の財布、カード名・下4桁 → そのカード） | **作らない**。前回の出金元を入れ「出金元を確かめてください」の印（出金元は口座の面で足す。§3.5） |
| お店 | 同じ `receipt_store` の過去の記録のお店 → 無ければ登録したお店と名前を比べる（似たお店と同じそろえ方。§3.2） | 読んだ店名を入れ、いつもの「この記録だけに使う／お店に登録して使う」を選ぶ（**はじめは「この記録だけ」**。§3.5） |
| カテゴリ | 同じ `receipt_name` か品名の過去の品目のカテゴリ → 無ければAIが**登録した小分類の中から**選ぶ | **作らない**。空にして「カテゴリを選んでください」の印 |
| 品目 | 同じ `receipt_name` の過去の品目の品名・カテゴリ | レシートの表記を整えて入れる（半角カナ → 全角など） |
| 日付 | レシートの日付 | 撮った日 |

- カテゴリごとにまとめて見せるのは今の記録の詳細と同じ（§3.2）。印の付いた行・項目は色を変えて、保存の前に気づけるようにする

### 10.5 金額
- **品目の金額はマイナスも入れられるようにする**（値引き・割引・返金）。いま `money_items.amount` は0以上の制約なので、外す。
  記録の合計（品目の和）は0以上とする（保存で確かめる）。品目の画面で金額を「−」に切り替えられるようにする（手入力でも使える）
  - 品目の値引き（「値引 −50」）は、その品目と同じカテゴリのマイナスの行にする
  - 小計への値引き（全体の○%引きなど）は、マイナスの行を1つにし、カテゴリはいちばん金額の大きい品目と同じにする（仮。使って困れば直す）
- **外税は、税を各品目に配って合計に合わせる**（大体でよい。合計が合っていればいい）。税の欄の税率ごとに、税額をその税率の品目へ金額の比で配り、
  端数はその税率でいちばん金額の大きい品目で合わせる。内税（今回のレシートの形）はそのまま
  - **AIが内税と読んでも、レシートの合計が品目の和より11%以内で大きければ外税として配る**（`effectiveTax`。2026-10-19。サンリブのレシートは
    「※8%内税対象」と印字されているが、小計1,841＋税146＝合計1,987の外税で、内税と読むと合計が146円違っていた）
  - 配り方でずれが頻発するようなら、「消費税」の品目を1行足す形に変える
- **合計の照合**: 品目の和がレシートの合計と違えば、記録の詳細の上に「レシートの合計 ◯円と ◯円違います」を出す（保存は止めない）

### 10.6 進め方（PRを分ける。mobile を先に、`src/` は同じPRで追従する）
1. 品目のマイナスの金額（DB の制約・品目の画面）。手入力でも使えるので、読み取りより先に入れる
   - DB は 0094: 品目の金額・単価の「0以上」の制約を外し、記録の合計（品目の和）が0以上かを遅らせた制約トリガ
     `money_items_check_record_total` で確かめる（`save_money_record` は変えない）
   - 品目の画面: 選んだ行に「マイナスにする／プラスに戻す」（0円の行には出さない）。電卓は金額の大きさだけを扱い、符号はそのまま。
     マイナスの行の金額は赤。記録の入力は、合計がマイナスなら保存しない
2. DB: `receipt_name`・`receipt_store` の列。Edge Function `money-receipt-scan`（Haiku 5.5・月の上限・形を決めたJSON）。Anthropic の鍵を Edge Function のシークレットに入れる
   - DB は 0095: 列2つと索引、読み取りの回数の表 `money_receipt_scans`（RLS あり・ポリシーなし＝Edge Function だけが書く）、
     `save_money_record` が `receipt_store`・品目の `receipt_name` を保存する（記録を直すとき、表記が送られてこなければ今のまま）
   - Edge Function `money-receipt-scan`: ログインの JWT で呼ぶ。`POST { images: [{ media_type, data }] }`（4枚まで）。
     AIの答えを直す処理は `_shared/receiptScan.ts`（`npm run test:receipt-scan`）。外税の配り方・お店と出金元の当て方・過去の手本の引き方もここ
   - 鍵は Edge Function のシークレット `ANTHROPIC_API_KEY`。無ければ 503 を返す（AIは呼ばない）
   - **アプリは手順3で、品目の `receipt_name` を読み・保存で送り返す**（送らないと、読み取りで入れた記録を直したときに品目の表記が消える）
3. 画面: 「＋」の隣に「レシート」→ スキャナー（mobile）／写真（PWA）→ 読み取り → 記録の入力を入れた状態で開く（§10.4・§10.5）
   - ~~右下のボタンのメニューに「**レシートを読む**」（「記録を追加」の上）~~ → 2026-10-20に、記録の入力の「**レシートから追加**」へ移した（新しい記録でも出す。§2）。mobile は `react-native-document-scanner-plugin`（`src/lib/receiptCapture.ts`。
     4枚まで・base64 で受け取り端末に残さない）。PWA は写真の選択（スマホではカメラ。複数選べる）を長辺2400px・幅1200px以内の JPEG に縮めて送る
   - 読み取り中は画面を暗くして「レシートを読み取っています…」。失敗したら関数の返した一言を出す
   - 記録の入力（`RecordEditor` の `receipt`）: 日付・出金元・お店・品目（種類ごとのまとまり。`groupsFromScan`）を入れて開く。お店は「この記録だけ」（登録は選んだときだけ）。
     合計の上に赤い枠で「レシートの合計 ◯円と ◯円違います」「出金元を確かめてください」「種類の決まっていない品目があります」（直すと消える）。
     カテゴリの無いまとまりの見出しは「カテゴリを選んでください」
   - 保存で `receipt_store` と品目の `receipt_name` を送る。品目の表記は記録を開き直して保存しても持ち回る（`MoneyItem.receiptName`）
4. 実物のレシートで試し、精度・費用を §10.7 に残す

### 10.8 既にある記録にレシートを当てる（2026-10-15。§9.6.5 の B）
カードの利用通知（§9.6）から作った記録は合計だけで1つのカテゴリなので、あとからレシートを撮って品目とカテゴリを入れ直せるようにする。
- 支出・収入の記録の詳細に「レシートを撮って品目を入れる」。読み取ったら、**出金元・日付はそのまま**で、品目をレシートの品目に入れ替えた
  記録の入力を開く（お店は記録のお店があればそのまま、無ければレシートのお店）。保存は人がする（黙って保存しない。§10）
- **合計が違う**か、**手で入れた品目**（2つ以上か、品名のある品目）があれば、先に「置き換える／スキップ」を選ぶ（`receiptReplaceNotices`）。
  置き換えたあとも、合計が違えば記録の入力の上に「レシートの合計 ◯円と ◯円違います」を出す（§10.5 と同じ）
- **レシートが先**のとき: あとから届いたカードの利用通知の明細が、レシートから入れた記録（`receipt_store` がある）1つだけと
  同じ出金元・同じ額・**前後1日**で当たれば、「手入力との確認」に回さずに結ぶ（`money_feed_process`。0107）。それ以外は今までどおり確認に回す
