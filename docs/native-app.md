# ネイティブアプリ化の検討

「すくすく手帳」をiPhone/Androidの**ネイティブアプリ**にするかどうか、するならどの
やり方にするかの検討メモ。実装前の判断材料としてまとめる。

## 前提（決定済み）

- **ストア（App Store / Google Play）には出さない。** 自分たちの端末に入れて使うだけ。
  → 審査もGoogle Playの「12人×14日テスト」も関係なくなる。これで消える論点が多い（§5）。

## 結論

**ネイティブ化は「授乳アラームを確実に鳴らす」ためだけの手段**であり、それ以外の目的では
今のPWAでほぼ足りている。そして**その目的なら、ネイティブにしなくても届く手がある**
（案A+：アラームの時刻をサーバーに予約してWeb Pushで鳴らす）。

順番としては、

1. まず **案A+** を試す。追加費用ゼロ・既存の通知の仕組みを流用でき、iPhoneでも効く
2. それで足りなければ **案B**（Capacitorの殻をかぶせる）。画面は1つも書き直さない

を推す。いきなり作り直す（案D）必要はない。

---

## 1. まず「何のためにネイティブにするのか」

今のアプリは**すでにPWAとして成立している**。ホーム画面に追加すればアドレスバーのない
全画面で立ち上がり、アイコン・テーマカラー・セーフエリア対応も入っている
（`src/app/manifest.ts` / `src/app/layout.tsx`）。予定のリマインダーもWeb Pushで
実際に端末へ届く（[notifications.md](./notifications.md)）。

ストアに出さないなら「ストアからインストールできる」という価値もない。
つまり**ネイティブでしか解決しないのは実質これだけ**。

| # | 今の困りごと | ネイティブで解決するか |
| --- | --- | --- |
| 1 | **授乳アラームが画面を消すと遅れる/鳴らない** | ○ 解決できる（ただし案A+でもかなり解決する） |
| 2 | iPhoneではバイブが使えない（`navigator.vibrate` 非対応） | ○ ネイティブのHapticsで可能 |
| 3 | iPhoneは「ホーム画面に追加」しないと通知が来ない | ○ ただし一度追加すれば済む話 |
| 4 | 圏外・電波が悪いと何も見られない（オフライン非対応） | △ ネイティブでもローカル保持を別途作る必要がある |

### 1-1. いちばん効くのは授乳アラーム

授乳中は画面を見られないので音とバイブで経過時間を知らせている
（`src/lib/alarm.ts` / `src/lib/nursingTimer.ts`）。ブラウザでは

- 画面が消える／裏に回るとタイマーが間引かれてお知らせが遅れる
- 画面が消えている間の振動要求は無視される（戻ってきたときに鳴らし直している）
- iOSはそもそも振動できない
- Screen Wake Lockで画面を消さないようにしているが、その分バッテリーを食う

という制約があり、コード側は**回避策の塊**になっている。
**「鳴らす時刻をあらかじめ予約しておく」作りにすれば、この回避策は全部要らなくなる。**
予約先がOS（案B）かサーバー（案A+）かの違いでしかない。

### 1-2. 逆に、ネイティブにしても解決しないこと

- **表示が速くなるわけではない**（案Bでは中身は同じWebのまま）
- **オフラインで使えるようになるわけでもない**。データはSupabaseにあるので、
  ネイティブにしてもローカルキャッシュを別途作らない限り圏外では白紙のまま

## 2. 選択肢の比較

ストアに出さない前提なので、Playストア用のTWA案は検討から外した。

| 案 | 中身 | 画面の作り直し | 通知の作り直し | 追加費用 | 総評 |
| --- | --- | --- | --- | --- | --- |
| **A. PWAのまま** | 今のまま | なし | なし | なし | 授乳アラームの制約が残る |
| **A+. アラームをサーバー予約** | 鳴らす時刻をサーバーへ登録し、Web Pushで鳴らす | なし | **流用**（既存の仕組みの延長） | **なし** | **まず試す価値あり**。§3 |
| **B. Capacitor（リモートURL）** | ネイティブの殻がVercel上のアプリをWebViewで開く | **なし** | **あり**（§4-1） | iPhoneは年$99 | 本命。ただし§4の条件つき |
| **C. Capacitor（アプリに同梱）** | HTML/JSを端末に同梱して開く | 大（§4-3） | あり | 同上 | Next.jsのSSR構成と相性が悪い。今は割に合わない |
| **D. React Native / Expoで作り直し** | UIを全部ネイティブで書き直す | **全部**（画面だけで約6千行） | あり | 同上 | 完成度は最高。夫婦2人で使うアプリには過剰 |

### なぜ D（作り直し）を今は採らないか

`src/components/sukusuku/` 配下のUIは約6千行あり、Tailwind + Web前提のDOMで書かれている。
React Nativeへ移すと**全画面を書き直す**ことになる。一方で移植できる資産もあり、
`src/lib/api/*`（Supabaseアクセス層）・`src/lib/dateUtils.ts`・`careLogUtils.ts`・
`nursingTimer.ts` の計算部分は素のTypeScriptなので**そのまま持っていける**。

将来ネイティブの作り込みが必要になったときに備え、**ロジックをUIから引き剥がしておく**
ことだけは今からやっておく価値がある（案A+/Bを進める場合でも損しない）。

## 3. 案A+ — ネイティブにせず授乳アラームを直す

**この検討で新たに見つけた選択肢。** 予定のリマインダーで既に作ってある
「サーバーが時刻を見てWeb Pushを送る」仕組み（[notifications.md](./notifications.md)）を、
授乳アラームにも使う。

```
[今]  タイマー開始 → 画面が生きている間だけ setInterval で見張る → 時刻が来たら鳴らす
                     ↑ 画面が消えると間引かれて遅れる／iPhoneは振動しない

[案A+] タイマー開始 → 5分後/10分後/15分後… の「鳴らす時刻」をサーバーに登録
       pg_cron（1分ごと）→ Edge Function → その端末だけにWeb Push
       sw.js が通知を出す（アプリが閉じていても、画面が消えていてもOSが鳴らす）
       タイマー停止 → 登録を消す
```

### できること / できないこと

| | 案A+（サーバー予約Web Push） | 案B（ネイティブのローカル通知） |
| --- | --- | --- |
| 画面が消えていても鳴るか | ○ | ○ |
| アプリを閉じていても鳴るか | ○ | ○ |
| iPhoneで振動するか | ○（システムの通知として鳴る/振動する） | ○ |
| 圏外でも鳴るか | **×（ネットワーク必須）** | ○ |
| ずれ | 最大1分程度（cronの粒度＋配送） | ほぼなし |
| **「ピッ/ポーン」の鳴らし分け** | **△（後述）** | ○（音声ファイルを同梱すれば維持できる） |
| 追加費用 | なし | iPhoneは年$99 |
| 作る量 | テーブル1つ＋Edge Function1つ | iOS/Androidのビルド一式 |

### いちばんの争点：音のパターンが維持できるか

今の仕組みの肝は「**短い『ピッ』1回＝5分、長い『ポーン』1回＝30分**」で、
画面を見ずに音の鳴り方だけで経過時間が分かること。案A+ではここが弱くなる。

- **通知音はOS標準のものになり、自前で合成した音は鳴らせない**。
  → 経過時間は通知の**文言**（「20分経過」）で伝えることになり、画面を見る必要が出る
- ただし**Androidは通知に振動パターンを指定できる**（`showNotification` の `vibrate`）
  ので、長短の振動パターンとしてなら今の数え方をそのまま維持できる
- iPhoneは振動パターンまでは指定できない

つまり **Androidなら今の体験をほぼ維持できる。iPhoneは「鳴ったら画面を見る」に変わる。**
ここが許容できるかどうかが、案A+で足りるか案Bへ進むかの分かれ目になる。

### 実装の要点

- 鳴らす先は**タイマーを動かしている端末だけ**。予定のリマインダーは家族全端末へ送るが、
  授乳アラームは違う。`push_subscriptions` の該当行を指定して送る
- `pg_cron` は現在5分間隔（`0013_reminder_cron.sql`）。アラーム用は1分間隔が要る
- Web Pushの `Urgency: high` を付けて配送を遅らせない
- 二重送信の防止は予定のリマインダーと同じ考え方（一意制約＋送信前に行を作る）が使える
- **既存のWeb Audio実装は消さない。** 画面を開いている間は今まで通り即座に鳴らし、
  裏に回っている間の取りこぼしをサーバー側が拾う、という二段構えが安全

## 4. 案Bを選ぶ場合に知っておくべきこと

### 4-1. WKWebViewではWeb Pushが「使えない」

iOSのWKWebView（＝Capacitorの中身）は**Service WorkerもWeb Push APIも動かない**。
Web Pushが使えるのはSafariとホーム画面に追加したPWAだけ。

つまり**Capacitorにした瞬間、今のリマインダー通知の仕組みは動かなくなる**。
ネイティブでは代わりにFCM/APNsを使うことになり、以下の作り直しが要る。

- 端末トークンを保存するテーブル（今の `push_subscriptions` はWeb Push購読専用）
- `supabase/functions/send-reminders` にFCM HTTP v1での送信経路を追加
  （今の `webpush.ts` によるVAPID署名はそのまま残し、宛先の種類で分岐）
- Firebaseプロジェクトの用意、APNsキーの登録

**これが案Bの隠れた最大コスト。** 授乳アラームだけならローカル通知で完結するので
サーバーは触らずに済むが、**予定のリマインダーは道連れで作り直しになる**。

### 4-2. ビルド環境

- **iOS版のビルドにはMacとXcodeが要る。** 手元にMacがなければ、
  クラウドのビルドサービス（EAS Build / Codemagic / GitHub ActionsのmacOSランナー）を
  使うことになり、その設定と運用がまるごと追加コストになる
- Android版はWindows/Mac/Linuxどれでもビルドできる

**Macがないなら、iPhone側は案A+で止めておくのが現実的。**

### 4-3. Next.jsを「同梱」するのは今の構成では重い（案C）

同梱するには `output: 'export'`（静的書き出し）が要るが、このアプリは

- `src/proxy.ts` によるミドルウェアで未ログイン判定とリダイレクトをしている
- `src/app/page.tsx` がServer Componentでセッション検証と初回データ取得をしている
- `src/app/auth/confirm/route.ts` というRoute Handlerがある

と、**サーバー実行を前提にした作り**になっている。静的書き出しではこれらが全部使えず、
認証とデータ取得をクライアント側へ移す改修が必要。表示速度のためにわざわざ入れた
`getClaims()` やサーバー側先読み（README「起動パフォーマンス上の設計方針」）も
組み直しになる。オフライン対応が本当に必要になるまでは着手しない。

なお `server.url`（リモートURL方式）はCapacitor公式には本番非推奨のオプションだが、
**ストア審査を受けないなら実質的な問題は「起動にネットワークが要る」ことだけ**。
審査でのグレーゾーン論点（ガイドライン4.2/4.7）は前提から外れたので考えなくてよい。

## 5. 配布方法（ストアに出さない）

### 5-1. Android

`.apk` を直接インストールする。**追加費用ゼロ、審査なし、Googleへの登録も不要。**
`server.url` 方式なら中身はVercel側で更新されるので、入れ直しはほぼ不要。

### 5-2. iPhone

**ここだけは Apple Developer Program（年$99）が実質必須。**
無料のApple IDでの署名は7日で切れるので実用にならない。

| 方法 | 有効期限 | 審査 | 備考 |
| --- | --- | --- | --- |
| **TestFlight（内部テスター）** | ビルドが90日 | **不要**（内部テスターのみなら） | 最大100人。90日ごとに新しいビルドを上げ直す |
| **Ad Hoc配布** | プロビジョニングが1年 | 不要 | 端末のUDIDを事前登録。年1回の更新 |

年$99を払う前提ならTestFlightの内部テスターが手軽。90日ごとのビルド上げ直しは面倒だが、
`server.url` 方式なら**アプリの中身を変えずに再アップするだけ**で済む。

> **iPhoneのために年$99 + 90日ごとの手作業**を払う価値があるかは、
> §3の「音のパターンが維持できるか」をどれだけ重く見るかで決まる。

## 6. 案Bでの授乳アラーム設計

案Bへ進む場合、最初に手をつけるべき部分。**サーバー側の変更が要らず、効果が最も大きい。**

開始した瞬間に、鳴らす時刻の通知を全部OSへ予約する。アプリが落ちていても、
画面が消えていてもOSが時刻通りに鳴らす。Wake Lockも不要になり、実装はむしろ単純になる。

- **「ピッ」「ピッピッ」の鳴らし分け**は、通知に添える音ファイルで表現する。
  iOSの通知音は**アプリに同梱した30秒以内の音声ファイル**しか使えないので、
  今Web Audioで合成しているパターン（長音＝30分・短音＝5分）を
  **あらかじめ書き出したファイル**として同梱する必要がある
- 予約件数には上限がある（iOSは未配信の通知64件まで）。数時間ぶんを予約しておき、
  アプリが前面に来たタイミングで先を継ぎ足す
- **マナーモードでは鳴らない。** 必ず鳴らす「Critical Alerts」はAppleへの個別申請が要り、
  個人アプリでは通しにくい。集中モード対策としてTime Sensitiveを指定しておく
- Androidは正確な時刻での発火に `USE_EXACT_ALARM` / `SCHEDULE_EXACT_ALARM` が絡む
- **鳴らし方の意味（長音＝30分・短音＝5分）は変えない。**
  体で覚えている部分なので、実装が変わっても体験は同じにする

## 7. まとめ

1. **ストアに出さないなら、ネイティブ化の理由は「授乳アラーム」ただ1つ**に絞られる。
2. その授乳アラームは、**ネイティブにしなくても案A+（サーバー予約Web Push）でかなり直せる。**
   追加費用ゼロ、既存の通知の仕組みの延長で作れる。
3. 案A+の弱点は**iPhoneで音のパターンが使えなくなる**こと（Androidは振動で維持可）。
   ここが許せないなら案Bへ進む。
4. 案Bはリマインダー通知のFCM/APNsへの作り直しと、iPhoneなら年$99＋Macが要る。

### 次にやること（案A+を選ぶ場合）

- `nursing_alarm_schedule` 相当のテーブルと、1分間隔のcron + 送信処理を追加
- タイマー開始/停止と登録/削除を紐づける
- 画面が開いている間の即時再生（今の実装）はそのまま残し、二段構えにする

### 残っている確認事項

- 主に使うのはiPhoneかAndroidか（案A+で足りるかの判断がここで変わる）
- iPhoneの場合、Apple Developer Program 年$99 を払う意思があるか
- iOSビルド用のMacがあるか（なければクラウドビルドの用意が別途必要）
