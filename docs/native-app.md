# ネイティブアプリ化の検討

「すくすく手帳」をiPhone/Androidの**ネイティブアプリ**にするかどうか、するならどの
やり方にするかの検討メモ。実装前の判断材料としてまとめる。

結論だけ先に書くと、**いきなり作り直す必要はない**。今のWebアプリを1画面も書き直さずに
ネイティブの殻をかぶせられる道（Capacitor）があり、そこで初めて手に入るものが
はっきりしているので、段階を踏むのがよい。

---

## 1. まず「何のためにネイティブにするのか」

今のアプリは**すでにPWAとして成立している**。ホーム画面に追加すればアドレスバーのない
全画面で立ち上がり、アイコン・テーマカラー・セーフエリア対応も入っている
（`src/app/manifest.ts` / `src/app/layout.tsx`）。予定のリマインダーもWeb Pushで
実際に端末へ届く（[notifications.md](./notifications.md)）。

つまり「アイコンから開ける」「通知が来る」だけが目的なら、**ネイティブ化しても
得るものはほとんどない**。ネイティブでしか解決しないのは次の4つ。

| # | 今の困りごと | ネイティブで解決するか |
| --- | --- | --- |
| 1 | **授乳アラームが画面を消すと遅れる/鳴らない** | ○ 完全に解決できる（後述） |
| 2 | **iPhoneは「ホーム画面に追加」しないと通知が来ない**。やり方を知らないと通知が一生来ない | ○ インストールすれば必ず通知が使える |
| 3 | iPhoneではバイブが使えない（`navigator.vibrate` 非対応） | ○ ネイティブのHapticsで可能 |
| 4 | 圏外・電波が悪いと何も見られない（オフライン非対応） | △ ネイティブでもデータのローカル保持を別途作る必要がある |

### 1-1. いちばん効くのは授乳アラーム

授乳中は画面を見られないので音とバイブで経過時間を知らせている
（`src/lib/alarm.ts` / `src/lib/nursingTimer.ts`）。ブラウザでは

- 画面が消える／裏に回るとタイマーが間引かれてお知らせが遅れる
- 画面が消えている間の振動要求は無視される（戻ってきたときに鳴らし直している）
- iOSはそもそも振動できない
- Screen Wake Lockで画面を消さないようにしているが、その分バッテリーを食う

という制約があり、コード側は**回避策の塊**になっている。ネイティブなら
「**開始時に、鳴らす時刻の通知をあらかじめ全部OSに予約しておく**」という作りにできる。
アプリが裏に回っていても、落ちていても、画面が消えていてもOSが時刻通りに鳴らす。
Wake Lockも不要になり、実装はむしろ**単純になる**。

### 1-2. 逆に、ネイティブにしても解決しないこと

- **表示が速くなるわけではない**（後述のCapacitor案では中身は同じWebのまま）
- **オフラインで使えるようになるわけでもない**。データはSupabaseにあるので、
  ネイティブにしてもローカルキャッシュを別途作らない限り圏外では白紙のまま
- **ストアに出す＝配布が楽になる、とは限らない**。むしろ審査という関門が増える（§4）

## 2. 選択肢の比較

| 案 | 中身 | 画面の作り直し | 通知の作り直し | ストア審査 | 総評 |
| --- | --- | --- | --- | --- | --- |
| **A. PWAのまま強化** | 今のまま。ホーム画面追加の導線を丁寧にする | なし | なし | 不要 | 費用ゼロ。ただし授乳アラームの制約は残る |
| **B. Capacitor（リモートURL）** | ネイティブの殻がVercel上のアプリをWebViewで開く。通知・振動だけネイティブ | **なし** | **あり**（§4-1） | 必要（グレー） | **本命**。既存資産をそのまま活かせる |
| **C. Capacitor（アプリに同梱）** | HTML/JSを端末に同梱して開く | 大（§4-3） | あり | 必要 | Next.jsのSSR構成と相性が悪い。今は割に合わない |
| **D. React Native / Expoで作り直し** | UIを全部ネイティブで書き直す | **全部**（画面だけで約6千行） | あり | 必要 | 完成度は最高。夫婦2人で使うアプリに対しては過剰 |
| **E. AndroidだけTWA** | PWAをそのままPlayストアに包む | なし | なし | 必要 | Androidだけ。iPhoneの困りごとが1つも解決しない |

### なぜ D（作り直し）を今は採らないか

`src/components/sukusuku/` 配下のUIは約6千行あり、Tailwind + Web前提のDOMで書かれている。
React Nativeへ移すと**全画面を書き直す**ことになる。一方で移植できる資産もあり、
`src/lib/api/*`（Supabaseアクセス層）・`src/lib/dateUtils.ts`・`careLogUtils.ts` ・
`nursingTimer.ts` の計算部分は素のTypeScriptなので**そのまま持っていける**。

将来どうしてもネイティブの作り込みが必要になったときに備え、**ロジックをUIから
引き剥がしておく**ことだけは今からやっておく価値がある（案Bを進める場合でも損しない）。

## 3. 推奨する進め方

### フェーズ0（すぐ・コード変更ほぼなし）— 目的を確定する

「ストアに並べたい」のか「授乳アラームを確実に鳴らしたい」のかで、やることが変わる。
**後者だけが目的なら、ストア公開せずに自分たちの端末にだけ入れる配布方法がある**（§5-2）。
審査という最大の面倒がまるごと消えるので、まずここを決めたい。

### フェーズ1（低コスト）— PWAで取れる分を取る

ネイティブ化を待たずにできること。

- iPhoneでSafariのタブから開いているときに「ホーム画面に追加すると通知が使えます」を
  もっと目立つ位置で案内する（今は設定タブの通知トグルの下だけ）
- Service Workerに最低限のオフライン表示（`public/sw.js` は現在キャッシュを一切しない）

### フェーズ2（本命）— Capacitorの殻をかぶせる

`ios/` `android/` のプロジェクトをリポジトリに追加し、`server.url` でVercel上の
本番URLを開くだけの薄い殻を作る。**Webのコードは1行も書き直さない**。
そのうえで、ネイティブでしかできない部分だけをプラグイン経由に差し替える。

```
アプリ起動 ─→ WKWebView / Chrome Custom WebView ─→ https://<本番URL>
                        │
                        └─ Capacitorのブリッジ（JSから呼べる）
                              ├─ LocalNotifications … 授乳アラームの予約
                              ├─ Haptics            … iPhoneでも振動
                              └─ PushNotifications  … 予定のリマインダー（FCM/APNs）
```

Web側は `Capacitor.isNativePlatform()` で分岐し、**ブラウザで開いたときは今まで通り
Web Audio / vibrate / Web Push を使う**。つまり既存の実装を消さずに済む。

### フェーズ3（必要になったら）

- オフライン対応（ローカルDB + 同期）
- ストア公開（審査を通す作り込み）
- それでも足りなければ案Dの部分的なネイティブ化

## 4. 先に知っておくべき落とし穴

検討の結果、**やってみてから気づくと痛い**事実がいくつか判明したので明記しておく。

### 4-1. WKWebViewではWeb Pushが「使えない」

iOSのWKWebView（＝Capacitorの中身）は**Service WorkerもWeb Push APIも動かない**。
Web Pushが使えるのはSafariとホーム画面に追加したPWAだけ。

つまり**Capacitorにした瞬間、今のリマインダー通知の仕組みは動かなくなる**。
ネイティブでは代わりにFCM/APNsを使うことになり、以下の作り直しが要る。

- 端末トークンを保存するテーブル（今の `push_subscriptions` はWeb Push購読専用）
- `supabase/functions/send-reminders` にFCM HTTP v1での送信経路を追加
  （今の `webpush.ts` によるVAPID署名はそのまま残し、宛先の種類で分岐）
- Firebaseプロジェクトの用意、APNsキーの登録

**これが案Bの隠れた最大コスト**。逆に授乳アラームは端末内で完結する
ローカル通知なのでサーバー側の変更は不要で、こちらだけ先にやる手もある。

### 4-2. `server.url` はグレーゾーン

Capacitorの `server.url` は本来ライブリロード用のオプションで、公式には本番利用を
推奨していない。App Storeの審査でも、中身が全部サーバー由来のアプリはガイドライン
4.2（最低限の機能）・4.7（第三者コンテンツ）で突っ込まれることがある。

- 通過しやすくする条件は「Webサイトの丸写しでないこと」。ローカル通知・Haptics・
  ネイティブのプッシュを入れれば、その分は主張材料になる
- そもそも**ストアに出さない配布**を選べばこの論点は消える（§5-2）

### 4-3. Next.jsを「同梱」するのは今の構成では重い（案C）

同梱するには `output: 'export'`（静的書き出し）が要るが、このアプリは

- `src/proxy.ts` によるミドルウェアで未ログイン判定とリダイレクトをしている
- `src/app/page.tsx` がServer Componentでセッション検証と初回データ取得をしている
- `src/app/auth/confirm/route.ts` というRoute Handlerがある

と、**サーバー実行を前提にした作り**になっている。静的書き出しではこれらが全部使えず、
認証とデータ取得をクライアント側へ移す改修が必要。表示速度のためにわざわざ入れた
`getClaims()` やサーバー側先読み（README「起動パフォーマンス上の設計方針」）も
組み直しになる。オフライン対応が本当に必要になるまでは着手しない。

### 4-4. ストア公開そのものの手間

| | Apple | Google |
| --- | --- | --- |
| 費用 | Apple Developer Program 年$99 | 初回$25のみ |
| 審査 | あり（初回は数日みておく） | あり |
| 個人アカウントの追加要件 | — | 2023/11/13以降に作った個人アカウントは、**12人以上のテスターで14日間連続のクローズドテスト**を終えないと公開できない |

夫婦2人で使うアプリのためにテスターを12人集めるのは現実的でない。
**Androidも「ストアに出さない配布」を第一候補にすべき**。

## 5. 配布方法（ストアに出さない道）

### 5-1. Android

`.apk` を直接インストールできる。ストア審査も12人テストも不要。$25も不要。
Google Playの自動更新は効かないので、更新のたびに入れ直す（あるいは
`server.url` 方式なら**中身はVercel側で更新されるので入れ直しはほぼ不要**）。

### 5-2. iPhone

Apple Developer Program（年$99）に入ったうえで、次のどちらか。

| 方法 | 有効期限 | 審査 | 備考 |
| --- | --- | --- | --- |
| **TestFlight（内部テスター）** | ビルドが90日 | **不要**（内部テスターのみなら） | 最大100人。90日ごとに新しいビルドを上げ直す |
| **Ad Hoc配布** | プロビジョニングが1年 | 不要 | 端末のUDIDを事前登録。年1回の更新 |

年$99を払う前提なら**TestFlightの内部テスターが一番手軽**。90日ごとのビルド上げ直しは
面倒だが、`server.url` 方式なら**アプリの中身を変えずに再アップするだけ**で済む。

> 無料のApple IDでの署名は7日で切れるので、実用にはならない。

## 6. 授乳アラームのネイティブ設計案

案Bで最初に手をつけるべき部分。**サーバー側の変更が要らず、効果が最も大きい**。

現在の作り（`nursingTimer.ts` の `setInterval` で見張り、時が来たらその場で鳴らす）を、
**開始した瞬間に鳴らす時刻を全部OSへ予約する**作りに変える。

```
[今]  タイマー開始 → 画面が生きている間だけ見張る → 時刻が来たら鳴らす
                     ↑ 画面が消えると間引かれて遅れる

[案]  タイマー開始 → 5分後/10分後/15分後… の通知をまとめてOSに予約
                     ↑ アプリが落ちていてもOSが時刻通りに鳴らす
      タイマー停止 → 予約を全部取り消す
```

実装上の注意点。

- **「ピッ」「ピッピッ」の鳴らし分け**は、通知に添える音ファイルで表現する。
  iOSの通知音は**アプリに同梱した30秒以内の音声ファイル**しか使えないので、
  今Web Audioで合成しているパターン（長音＝30分・短音＝5分）を
  **あらかじめ書き出したファイル**として同梱する必要がある。
  お知らせは最大でも数時間ぶんなので、パターンの数は現実的な範囲に収まる。
- 予約する件数には上限がある（iOSは未配信の通知64件まで）。数時間ぶんを予約しておき、
  アプリが前面に来たタイミングで先を継ぎ足すのが安全。
- **マナーモードでは鳴らない**。必ず鳴らす「Critical Alerts」はAppleへの個別申請が要り、
  個人アプリでは通しにくい。集中モード対策としては
  Time Sensitive（時間指定要約を突き抜ける）を指定しておく。
- Androidは正確な時刻での発火に `USE_EXACT_ALARM` / `SCHEDULE_EXACT_ALARM` が絡む。
  アラーム用途として認められる範囲かは実装時に確認する。
- **鳴らし方の意味（長音＝30分・短音＝5分）は変えない。**
  ここはユーザーが体で覚えている部分なので、実装が変わっても体験は同じにする。

## 7. まとめ（判断のポイント）

1. **目的が「授乳アラームを確実に鳴らす」なら、ネイティブ化する価値は大きい。**
   それ以外（アイコン・通知・見た目）は今のPWAでほぼ足りている。
2. **やるなら案B（Capacitor + リモートURL）。** 画面を1つも書き直さずに済む。
3. **ストア公開は目的にしない。** Androidは`.apk`直接、iPhoneはTestFlight内部配布で
   審査も12人テストも回避できる。
4. **リマインダー通知はFCM/APNsへの作り直しが必要**という点だけは避けて通れない。
   ただし授乳アラーム（ローカル通知）だけなら**サーバーは触らずに実現できる**ので、
   そこから始められる。

### 決めてほしいこと

- ネイティブ化の主目的はどれか（授乳アラーム / 通知の確実性 / ストアに並べたい / その他）
- Apple Developer Program（年$99）を払う意思があるか。ないならiPhoneはPWAのまま
- 使う端末は2人ぶんだけか（TestFlight・Ad Hocの前提）
