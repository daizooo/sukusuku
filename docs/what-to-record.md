# 何を記録すべきか — 育児記録の設計を組み直す

記録タブは「授乳・おむつ・搾乳を1件ずつ、時刻付きで残す」形で作ってきた。
入力の手数を減らす話をしていて、そもそも**その項目は後で誰かが読むのか**という
ところに戻ったので、記録の目的から仕分け直したメモ。

結論を先に書く。

- **回数（おしっこ・うんち・授乳）と、ミルクの実測量。ここは今のままでよい。**
- **体温とうんちの写真が抜けている。** 受診のときに本当に要るのはこの2つ（§4）。
- 記録は**3つの層**に分かれていて、層ごとに必要な丁寧さが違う。いまは全部を
  同じ丁寧さで扱っているのが、入力が重い原因でもある（§3）。
- **母乳の左右別の分数は残す。** 「足りているか」の判断材料にはならないが（§2）、
  残すと決めた。判断の経緯は§10。
- **メモ欄は削らない。** 実データを見たら、吐き戻しの記録と夫婦のやりとりが
  ここに溜まっていた（§11-3）。仕分けのうち、ここだけ想定が外れた。

**決まったことは§10に、実データで確かめた結果は§11にまとめてある。**
本文の分析は当時のまま残し、結論が変わったところには§10・§11への参照を置いている。

---

## 1. 記録は誰が読むのか

読み手を並べると4人しかいない。それぞれ**読む時間軸**が違う。

| 読み手 | いつ読むか | 何を見るか | 保存しておく必要 |
| --- | --- | --- | --- |
| 自分たち（運用） | 数時間〜今日中 | 最後の授乳はいつか／次はどっちの乳か／今日うんちは出たか | **ほぼ無い**（最新の1件で足りる） |
| 小児科（受診時） | 異常が起きたとき | いつからか・何回か・熱・様子 | 必要。ただし頻度は低い |
| 健診（1ヶ月・3-4ヶ月…） | 数ヶ月に1度 | 体重の増え方・授乳回数・うんちの回数・心配ごと | **1日単位の合計で足りる** |
| 将来の自分・子ども | 何年も後 | 思い出 | 記録タブの仕事ではない（写真とメモの領域） |

ここから出る一番大きい示唆は、**運用のための記録は翌日には価値がゼロになる**ということ。
いま `care_logs` に1件ずつ時刻付きで積んでいるものの大半がこれにあたる。
1日の合計に畳んでしまえば、明細まで永久に持つ必要はない。

### 母子健康手帳との住み分け

健診の結果と予防接種の履歴は**母子健康手帳が正本**で、アプリが持ち直す意味はない。
アプリが引き受けるのは、母子手帳に書ききれない**日々の経過**と、
**次にいつ何をするかの段取り**（予定タブ）の2つに絞る。

## 2. 「足りているか」は量では分からない

いちばん判断したいのは「足りているか」だが、**母乳の哺乳量は測れない**。
左右の授乳時間を測っても、出の良し悪しや吸い方で変わるため哺乳量とはほとんど対応しない。
つまり `nursingTimer.ts` と前面サービスで丁寧に測っている左右別の分数は、
**後から読んで何かが分かるデータになっていない**。

実際に「足りているか」の判断に使われているのは次の3つ。

1. **体重の増え方** — これが唯一の答え合わせ
2. **おしっこの回数** — 出ていれば水分は足りている、という形で使う
3. 機嫌・元気

したがって記録すべきものは、こう言い直せる。

> 排せつの回数（特におしっこ）＋ ミルクの実測量 ＋ **体重**
> ＝ これで「足りているか」は判断できる。
> 母乳の量・時間は、記録しても判断材料にならない。

ただしこれは「足りているかの判断に使えるか」という一点の話であって、
**記録を残す理由はそれだけではない。** 母乳の分数は残すことにした（§10）。

具体的な体重増加やおしっこ回数の目安は月齢で変わるので、
**1ヶ月健診・3-4ヶ月健診で言われた数字を正とする**。アプリ側に基準を焼き込むなら、
その値を設定として持てるようにしておく（決め打ちにしない）。

## 3. 記録を3層に分ける

層ごとに、必要な丁寧さと保存の仕方が違う。

### 層1: 状態（保存しない／最新だけ分かればよい）

最後の授乳の時刻、次はどっちの乳か、最後のおむつ、搾乳ストックの残り。

- これは「いまどうなっているか」であって、履歴に意味がない。
- **1タップで更新できれば足りる。** 画面を開く必要すらない。

### 層2: 日ごとの数（1日1行に集約できる）

- おしっこ ◯回 / うんち ◯回
- 授乳 ◯回（母乳・ミルクの内訳）
- ミルク合計 ◯ml

- 健診も日々の判断も、**この粒度で足りる**。
- 重要なのは、**回数しか使わないなら時刻すら要らない**こと。
  「おむつを替えた」を押すだけ、詳細ゼロ、時刻は自動でよい。
  … ただし**カウンタにはしなかった**。入力画面のまま項目を削るところで止めている（§7-1）。
- 明細を残すのは構わないが、数日を過ぎたら1日1行に畳んでよい。

### 層3: 異常イベント（頻度は低い。ここだけ丁寧に残す）

- **体温**（発熱時）… **入れた**（§4-1・§8の2）
- **うんちの写真＋便色カードの番号**（色が気になるとき）… 色名の6択は**外した**（§7-1）。
  いまは気になったときメモ欄に書く。写真はまだ無い（§4-2・§8の6）
- 嘔吐・発疹・受診の記録 … 吐き戻しは独立した記録に**しない**（§11-3。メモ欄に書く）。発疹と受診の記録はまだ無い
- 体重・身長（`growth_records`）… **既にある。層3の主役**

**いまのアプリは層1〜3を全部同じ丁寧さで扱っている。**
実際には「ほぼゼロ手間でよいもの」と「今より丁寧に残すべきもの」に二極化している。

## 4. いま足りていないもの

削る話の前に、足りていないものを先に挙げる。ここが記録の値打ちを決める。

### 4-1. 体温 ★最優先

`care_logs` の `type` は `milk / diaper / pumping`（＋過去の `sleep`）で、**体温がない**。

- 受診したとき**必ず**「いつから・何度か」を聞かれる
- 月齢が低いうちの発熱は、それ自体が受診の判断につながる
- **時系列に意味があるほぼ唯一のデータ**（何時に何度、上がったか下がったか）

授乳の分数を1年分残すより、発熱した3日間の体温の折れ線1本のほうが価値が高い。
オムロン MC-687 で測った値を入れるだけなので、入力は数字1つで済む。

実装は `care_logs` の `type` に `temperature` を足し、`details` に `{ celsius: 数値 }` を入れる。
`0019` と同じ形で check 制約を張り直す1本のマイグレーションで済む。

> **入れた（§8の2）。** マイグレーション `0028_care_logs_temperature.sql` と、
> `mobile/` の体温の入力画面。値の上げ下げは0.1℃刻みのボタンで、直接打つこともできる。
> 37.5℃以上は発熱、38.0℃以上（と35.0℃未満）は受診の目安として、記録したその場に出す。
> ~~**凍結したPWA版（`src/`）には出さない。**~~ → **PWA版（`src/`）にも入れた。**
> ネイティブ化を一時凍結し、`src/` が当面の本体に戻ったため
> （native-app-rewrite.md 冒頭の【現況】）。`mobile/` の入力画面をそのまま移してある。
>
> **あわせて「正常範囲」と「その子の平熱」を入力画面に出すようにした。**
> 数字だけ出しても、それが高いのかどうかが分からない。しかも**平熱は子どもによって違う**ので、
> 一般の正常範囲（36.5〜37.5℃）だけでは足りない。同じ 37.2℃ でも、平熱 36.6℃ の子には
> 高く、平熱 37.1℃ の子にはいつもどおり。
>
> 平熱は**その子自身の記録から数える**。**正常範囲に入る記録だけ**を新しい順に最大30件
> 平均し、3件たまるまでは出さない。発熱した値を混ぜると平熱そのものが上がってしまい、
> 「この子にしては高い」がかえって見えなくなるため。**絞ってから新しい順に取る**ので、
> 熱が何日か続いても平熱を見失わない（先に新しい順で切ると、その数日で埋まってしまう）。
>
> 正常範囲の内でも平熱から 0.5℃ 以上離れていれば、そのことだけを出す。
> 記録タブの体温のボタンは、その日にまだ測っていなければ平熱を出す（測ったときの比べる相手になる）。
> **何回測ったかは出さない**（§7-2の最後）。回数そのものは判断に使わないため。

### 4-2. うんちの色は「6択」ではなく「写真」

> **6択とかたさ3択は外した（§7-1）。** 以下の分析のうち「色の6択をやめる」ところは
> そのとおりにした。残っているのは**写真＋便色カードの番号**のほう（§8の6）。

`DiaperLogModal` は色を6色×2グループから選ばせているが、実際に効いてくるのは
**白・赤・黒だったときだけ**で、そのとき小児科が見たいのは**色名ではなく現物**。
母子健康手帳の便色カード（番号1〜7）と突き合わせるのが正規の手順でもある。

→ 毎回の色選択をやめ、**「気になる色だった」を押したときだけ、写真1枚＋便色カードの番号**。
`documents` の Storage バケットが既にあるので、置き場所は用意済み。

### 4-3. 予防接種は「記録」ではなく「予定」

生後2ヶ月から始まり、同時接種のスケジュール管理が実質必須になる。
これは記録タブではなく `tasks` の仕事。**記録タブを軽くする代わりに、
予定タブにこれを載せるほうが投資対効果が高い。**
接種の結果そのものは母子手帳が正本なので、アプリは日程の段取りだけ持てばよい。

## 5. いま余っているもの

読み返す場面が無さそうな項目を挙げ、残すか落とすかを付けた。
**残す**が付いているものは、検討のうえで残すと決めたもの（§10）。

| 項目 | 判断 | 理由 |
| --- | --- | --- |
| 母乳の左右別の分数 | **残す**（決定・§10） | 哺乳量の指標にはならないが、残すと決めた |
| うんちのかたさ3択 | **落とす** | 異常時のメモで足りる |
| うんちの色6択 | **写真に置き換え**（§4-2） | 色名では受診時に役立たない |
| 記録した人（パパ/ママ） | **詳細画面だけに出す**（決定・§10） | 一覧では場所を取るわりに読まれない |
| 搾乳のパック単位のストック | **残す**（紐付けも含めて・§10） | 実在庫と一致していないと困る。紐付けも実運用で効いている |

### ストップウォッチとアラームの役目

**授乳中に一定間隔で鳴らす仕組みは、記録とは別の道具**として捉える。
片乳に偏らせない・吸わせすぎないためのもので、記録を残すためのものではない。

> **記録の価値と、操作の価値は別。**

分数を残すと決めたので（§10）両方の役目を兼ねることになるが、この区別は残しておく。
アラームの設計を変えるときに「記録のためだから」と引きずられないようにするため。
フェーズ1で作った前面サービス（Kotlin）とアラームは、いずれにせよそのまま活きる。

## 6. 削ると不安が増える、への手当て

正直なところ、月齢が低いうちの記録は
**「足りているか不安だから付ける」**という面が大きい。
項目を削ると、その不安の行き場がなくなる。

だから**削る代わりに、判断そのものをアプリが出す**のがセットになる。

```
今日  おしっこ 7回   ✓ 目安に届いている
      うんち   2回
      授乳     9回（母乳7・ミルク2 / 160ml）
      体重     前回から +28g/日   ✓
```

記録は減るのに、**知りたかったこと（足りているか）は前より分かる**。
健診の前日にこの画面を遡れることが、記録を付けている意味そのものになる。

## 7. 何を記録するかが決まると、入力設計も決まる

入力の手数を減らす話は、層ごとに答えが変わる。

| 層 | 入力のかたち |
| --- | --- |
| 層1 状態 | ウィジェット／通知アクションの1タップ。画面を開かない |
| 層2 数 | 1タップのカウンタ。**時刻を入れる必要すらない** |
| 層3 異常 | ここだけ入力画面で丁寧に。むしろ項目を増やしてよい |

つまり「何を記録すべきか」を決めるほうが先で、それが決まれば入力の速さは後から付いてくる。
相対時刻の入力やまとめ入力といった案は、層2を「時刻の要らないカウンタ」にしてしまえば
そもそも不要になる部分がある。**入力の高速化は、この仕分けが済んでから別メモに切り出す。**

### 母乳を残したことで、層2のカウンタ化には線が引かれる

母乳の分数を残すと決めたので（§10）、**授乳の記録をすべて1タップのカウンタにはできない**。
線はこう引く。

| 記録 | 入力 |
| --- | --- |
| おむつ | **カウンタ**。1タップ、詳細ゼロ、時刻は自動 |
| ミルク | **量だけ**。回数と ml が取れれば足りる |
| 母乳 | **ストップウォッチ経路が主**。測れば分数は自動で埋まる |

母乳は、その場でストップウォッチを使っているかぎり入力の負担はもともと小さい
（`MilkLogModal` が計測値をそのまま分数の欄に入れる）。重いのは**あとからまとめて記録するとき**で、
そのときは分数を思い出せない。

**そこで「分数が未入力のまま保存できる」ことを担保する。** いまの `MilkLogModal` は
未選択と0分を区別する作りになっているのに、保存時に `leftMinutes ?? 0` としているため、
**未入力が0分としてDBに入る**。「測らなかった」と「0分だった」が後から見分けられないので、
分数を残すなら、ここは分けておきたい（§8 の3で扱う）。

### 7-1. 記録タブの入力を削る（作ったもの）

§7の表のとおりに作ろうとして、**おむつを1タップのカウンタ**（おしっこ／うんち／両方の
3ボタン、時刻は自動、詳細ゼロ）にしたが、**使ってみて取り止めた**。

- カウンタはカードで場を取り、記録ボタン・おむつ・体温・搾乳ストックの4つが縦に並んで
  **画面がごちゃついた**（CLAUDE.md「画面の作り方」で、タブの中で縦に積むのを避けている）
- 日時とメモは**残したい**。押した時刻でよい（§11-5）としたが、あとから直せるだけでは
  足りず、その場で入れられるほうがよかった

**落とせたのは色とかたさのほうだった。** おむつの入力画面に残したのは
**種類（おしっこ／うんち／両方）・日時・メモ**の3つだけで、
うんちの**色6択とかたさ3択は外した**（§11-1・§11-2。色は51件すべてで選んでいたのに
「気になる色」は0件、かたさは9割が既定値のまま）。気になったときは**メモ欄に書く**。
§8の6（写真に置き換え）のうち、6択・3択を畳むところはこれで済んでいる。

> すでに保存されている色・かたさは消さない。編集して保存し直しても、そのまま持ち回す。
> 表示（タイムラインのバッジ）も残してあるので、過去の記録は今までどおり見える。

### 7-2. 授乳に搾乳をまとめ、記録タブを3つに戻した

記録ボタンは**授乳・おむつ・体温の3つ**（1列に収まる数）。「ミルク」は**授乳**に改名した。
母乳・搾乳・ミルクをまとめて指すので、そのほうが実態に合う。

**搾乳（搾った分）は授乳の入力画面へ寄せた。** 記録としては別物（搾った分は搾乳ストックの
1パックになる）だが、**どちらも授乳まわりの操作**なので入口を分ける必要がなかった。

切り替えは、入力画面の**「飲ませたもの」で「搾乳」を選んだところにだけ**置いている
（**「搾乳を」→ 飲ませた／搾った**）。母乳やミルクを選んでいるときは関わらない話なので、
いちばん上に置いて全部の画面に出すのはやめた。「搾った」を押すと搾乳の入力画面へ移り、
そこで「飲ませた」に戻すと**搾乳を選んだ状態**で戻ってくる。

**授乳のボタンに出すのは、その日の回数・量・分数ではなく「いまの搾乳ストック」**
（`ストック・240ml`）。何パックあるかは飲ませるときに選ぶので、ボタンには**合計だけ**出す。

- 回数・量・分数は**後から読まない**。「足りているか」を決めるのは体重の増え方と
  おしっこの回数で、授乳の合計値はそこに入ってこない（§2）
- 逆に**ストックは、次に飲ませるときその場で要る**（層1の状態）。
  搾乳ストックだけの行を独立して置くより、授乳のボタンに載せたほうが場所も取らない

**おむつのボタンには「おしっこ ◯回 / うんち ◯回」を出す。** 合わせた回数には使い道がなく、
おしっこは水分が足りているか、うんちはお通じと、**見たいことが別**だから（層2＝§5）。
「両方」の記録は、おしっこにもうんちにも数える。

体温のボタンは、まず**いまの値**（その日にまだ測っていなければ平熱）。
その下に、何度か測った日は**その日の平均**、熱が下がったあとは**その日の最高**を
添える（`平均 37.4・最高 38.4 ℃`）。平均はその日1日を1つの数で言うのに近く、
最高はいま平熱でも熱が出ていたことを残す。1回しか測っていない日の平均は
いまの値と同じなので出さない。

## 8. 進め方

> **ネイティブ化を一時凍結したので、対象は `src/`（PWA）に読み替える。**
> `mobile/` にだけ足した2（体温）・3（吐き戻し）は実機で動かせないまま積み上がっていた
> ため、まず**その2つを `src/` へ移した**（native-app-rewrite.md 冒頭の【現況】）。
> 以降の項目も、凍結が解けるまでは `src/` に作る。`mobile/` 側は消さずに置いておく。

**1は済んだ（結果は§11）。** その結果を受けて、2以降の順番を入れ替えている。
**2（体温）は済んだ**（`mobile/` と `src/` の両方）。
**3（吐き戻し）はやめた**（§11-3。メモ欄に書く形に戻す）。
**4（おむつ）は形を変えて済んだ**。カウンタは取り止め、入力画面のまま
種類・日時・メモだけに削っている（§7-1）。あわせて**授乳に搾乳をまとめ**、
記録ボタンを授乳・おむつ・体温の3つに戻した（§7-2）。

| 順 | やること | 対象 | 備考 |
| --- | --- | --- | --- |
| 1 | ~~実データで裏を取る~~ | — | **済（§11）。** 落とす判断は裏が取れた。メモ欄は想定と違った |

ただし8/15〜8/21は入院中で1日3〜5件しかなく、**家に帰ってからの8/22以降が実データ**
（1日16〜30件）。母数は小さいので、比率は傾向として読む。

**結果を先に書く。**

- **落とす判断（色6択・かたさ3択）は、想定どおり裏が取れた**（11-1・11-2）

- **母乳の分数の0は「測らなかった」ではなく「片乳だけ」だった**。急ぎではなくなった（11-4）
- **「後からまとめて付けている」ことの裏が、時刻の丸めから取れた**（11-5）

### 11-1. うんちの色6択 → 落としてよい

| | 件数 |

| うんちを含むおむつの記録 | 51 |

| うち「茶色」 | 2 |

### 11-2. うんちのかたさ3択 → 落としてよい

### 11-3. メモ欄 → **想定と食い違った。削らない。むしろ主役**

今回いちばん大きい発見。

- 埋まっていたのは161件中**33件（20.5%）**。「たまに使う」ではない
- 書いているのは主に妻（30% / 夫11%）。記録の件数自体は81・80でほぼ半々
- 平均29文字、最長164文字

中身を分類すると、**運用のためのメモではなかった**。

| 中身 | 件数 |
| --- | --- |
| **吐き戻し** | **9** |
| ゲップ・抱き方の試行錯誤（「縦抱き5分、横抱き10分→吐き戻しなし」） | 7 |
| 授乳の切り上げどき・寝落ち（「寝たかな？で切り上げると泣く傾向」） | 6 |
| 冗談・思い出・夫婦間のねぎらい | 6 |

ここから3つ言える。

1. **§4で「いま無い」と書いた嘔吐は、実際にはメモ欄で毎日記録されている。**
   メモの27%がこれ。**構造化する候補として、体温の次に来るのはこれ**。
   「吐き戻し あり」を押すだけ＋直前の授乳との紐付けで、いま手で書いている内容の
   大半は残せる。

   > ~~**入れた（§8の3）。**~~ → **やめた。独立した記録にはしない。**
   >
   > いちど `mobile/` と `src/` の両方に量の3択（少し／たくさん／噴水のように）の
   > 入力画面を入れたが、**使う前に取り止めた**。吐き戻しは**気になったときだけ、
   > 授乳などの記録のメモ欄に書く**形に戻す。
   >
   > 見落としていたのは、**このメモが「アプリが型を与えるべきもの」の例として
   > 挙がっていたこと自体が、型を与えてよい根拠にはなっていない**という点。
   > 上の分析が言っているのは「メモ欄に吐き戻しがよく書かれている」という事実までで、
   > そこから「毎回3択を押す記録にすべき」は出てこない。実際にできたものは、
   > **吐いたと思うたびに画面を開いて選ぶ**入力で、メモに一行書くより手数が増えていた。
   >
   > **メモ欄は§11-3の結論どおり「いま一番中身のある記録」のまま残す。**
   > 3択に畳むと、いま書かれている「縦抱き5分、横抱き10分→吐き戻しなし」のような
   > 中身のほうが落ちる。落とすべきは記録ではなく、**記録の型のほう**だった。
   >
   > **DBには手を付けない。** `care_logs.type` の check 制約（`0029`）と、
   > すでに保存された `spitup` の行はそのまま残す。§8の「既存の行は消さない」に従い、
   > アプリ側が読まなくなるだけにしてある（気が変わったときに戻せる）。
2. **ゲップの姿勢と時間を、自前で実験ログとして付けている。**
   「ゲップなし、縦抱き5分、横抱き10分。→吐き戻しなし」という書き方が繰り返し出てくる。
   これは異常の記録（層3）ではなく、**当人たちが仮説検証している最中のデータ**。
   アプリが型を与えれば、吐き戻しとの対応が見えるようになる。

   > **入れていない。** ゲップの姿勢と時間は「吐き戻しなし」で終わった回も含めて
   > 残す必要があり、吐き戻したときの記録に足すだけでは半分しか拾えないため。
   > その吐き戻しの記録自体もやめたので（§11-3）、**この書き方はメモ欄のまま**。
   > いまの形が、いまのところいちばんよく拾えている。
3. **§1で「思い出は記録タブの仕事ではない」と切ったが、実際には切れていない。**
   夫婦間のやりとりと冗談がメモに入っている。記録タブが**読み返して笑う場所**にも
   なっている以上、**メモ欄を狭くする方向の変更はしない**。

なお1件だけ「右2分→左5分→右3分」というメモがあり、**左右を往復した授乳はいまの
「左◯分・右◯分」では書けない**のでメモに逃げている。分数を残すと決めた以上（§10）、
往復を1回の記録で表せないことは頭に入れておく（いますぐ直す必要はない）。

### 11-4. 母乳の分数の0 → 「測らなかった」ではなく「片乳だけ」だった

| | 件数 |
| --- | --- |
| 母乳の記録 | 64 |
| `leftMinutes` / `rightMinutes` の**キーが無い**もの | **0** |
| どちらかが0 | 25（39%） |
| **両方とも0** | **0** |

0は多い（39%）が、**両方0の記録は1件も無い**。メモにも「右だけで寝た」
「起きたので左もできた！」とあり、0は**「その側はあげていない」**の意味で入っている。
つまり `leftMinutes ?? 0` が「測らなかった」を0に潰す事故は、**まだ起きていない**。

→ §8の「分数を未入力のまま保存できるように」は、**やる価値はあるが急がない**。順番を下げる。
片乳0が4割ある以上、サマリ（§6）で分数を足すときに0を「その側はしていない」として
扱うのは、いまのままで正しい。

### 11-5. 時刻の分布 →「後から付けている」裏が、時刻の丸めから取れた

**時間帯の偏りは無い。** 0〜23時のどこにも記録があり、深夜0〜6時だけで40件ある。
「日中に入力する」前提の設計はできない。**片手・暗いところ・音を出せない**が常に前提。

そのうえで、§9で「今のスキーマでは分からない」と書いた
**「その場で付けたのか、後からまとめて付けたのか」に、間接的な答えが出た。**

分の値が5の倍数に寄っている。

| | 分が5の倍数 |
| --- | --- |
| 全体 | **67.7%**（161件中109件） |
| **おむつ** | **82.0%**（61件中50件） |
| 授乳 | 58.0% |

でたらめなら20%のはず。しかも :00 が32件、:30 が23件あり、この2つだけで全体の34%。

新規の記録は**既定でその時の時刻**が入り、丸める処理はどこにも無い。
さらにおむつの記録は**Webからしか作れない**（`mobile/` にはおむつの入力画面が無く、
表示だけ）ので、`<input type="time">` にスナップも無い。
つまりこの丸めは、**人が時刻を打ち直した跡**と読める。

→ **おむつの記録の8割は、時刻を手で入れ直している。**その時刻はもともと概算でしかない。
§8の「おむつをカウンタにする（時刻は自動）」は**失うものが無い**ので、優先度を上げる。
→ **カウンタにしてみたが、取り止めた（§7-1）。** 時刻を自動にしても失うものは無い、
までは正しかったが、**入力画面ごと無くすところまでは要らなかった**。日時とメモは残っている。

ただしこれで分かるのは「時刻を触った」ところまでで、**どれくらい後に入力したかは分からない**。
そこまで知りたければ、やはり `created_at` を足すしかない（§9）。
