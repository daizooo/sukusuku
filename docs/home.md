# 暮らしタブ（防災備蓄・日用品・特別費）の検討

家（住まい）にまつわるものを1つのタブにまとめるための設計メモ。
「ホーム」は以前あったホーム画面（2026-10-02に育児タブへ統合）と紛らわしいので、
タブの名前は **「暮らし」** とする（§2。2026-10-06に決定）。

結論を先に書く。

- **新しく持つのは「防災備蓄」と「日用品」の2つ。** どちらも家族で共有し、
  リストと同じ `family_id` 単位のRLSにする（§3・§4）。
- **防災備蓄の本当の課題は「数を数えること」ではなく「期限切れに気づくこと」。**
  1行＝品名×期限（ロット）で持ち、期限の近い順に並べ、近づいたら知らせる（§3）。
- **日用品は「よく買うもの」の台帳。** リストの「よく買うもの」（docs/lists.md §8
  フェーズ2の残り）はこの台帳で置き換える。台帳から1タップで買い出しリストへ送り、
  **お店の名前とリストのグループ名が一致すればそのグループへ入れる**（§4.2）。
- **日用品の在庫数は持たない。** 毎日減るものを数え続けるのは続かない。
  「切れそう」と思った瞬間にリストへ送れれば足りる（§4.3）。
- ~~家計は「Zaimの代わり」を作らない。アプリは特別費の見通しに特化する（§5。2026-10-06に決定）~~
  → **2026-10-07に変更: 家計は独立した「家計」タブにし、日々の収支と月・年の振り返りを持つ**（docs/kakei.md）。
  Zaim は口座・証券の残高を見る用に絞る。特別費は家計タブへ移す。

## 3. 防災備蓄

### 3.1 データ（`stock_items`）

| 列 | 内容 |
| --- | --- |
| `id` / `family_id` | 家族単位で共有。RLSは `current_family_id()` |
| `category` | 「飲料・水」「食料品」「衛生用品」「日用品・生活雑貨」「照明・情報・電池類」など。**自由入力**（候補は既存の値から出す） |
| `name` | 「カゴメ 野菜たっぷりスープ（豆）」 |
| `quantity` | 数（numeric） |
| `unit` | 「本」「袋」「個」「PC」「回分」「枚」。自由入力 |
| `expires_on` | 賞味・使用期限（date, null可）。期限の無いもの（衛生用品・ラジオ・ランタン・ポータブル電源など）はnull |
| `expires_month_only` | 期限が「2027.06」のように月までしか無いとき true。`expires_on` は**その月の末日**で持つ |
| `note` | 置き場所など（任意） |
| `position` / `created_at` / `updated_at` | |

- **1行＝品名×期限（ロット）。** 同じ品でも期限が違えば別の行にする
  （今のシートでもカゴメのスープは 12PC と 4PC で期限が違う）。画面でも1行ずつ並べる（§3.2）
- 点検の列は 2026-10-07 に足した（`0062_stock_inspection.sql`。§10.2）。**値段は持たない**（§10.2.1）:

| 列 | 内容 |
| --- | --- |
| `inspected_on` | 最後に点検した日。未点検は null（その場合は `created_at` から数える） |
| `inspect_interval_months` | 点検の間隔（月）。null は点検しない。期限の無い備品が対象 |

### 3.2 画面（2026-10-06に実装。フェーズ1。**2026-10-07に §10.2 の点検盤へ作り直した。以下は当時の記録**）

- 上（固定）: 見出し「防災備蓄」と「追加」、要約、カテゴリで絞るチップ（カテゴリが2つ以上のとき）
  - 要約は「期限切れ n件」「3か月以内 n件」「1年以内 n件」（0件のものは出さない。
    どれも無ければ「1年以内に期限が来るものはありません」）
- 中（スクロール）: **1行＝1ロットを期限の近い順**（期限なしは末尾、その中はカテゴリ→品名の順）。
  品名でまとめることはしない（期限の近い順に並べると、同じ品のロットが離れても期限の早い方が先に出るため）
  - 右に数と単位、その下に期限。期限の色は1年以内が橙、3か月以内・切れたものが赤
    （切れたものは「切れ 2026.09.30」）。期限の無いものは「期限なし」
- 行を押すと、下から出る枠で直す（品名・カテゴリ・数・単位・期限・メモ）。数は −/＋ で1つずつ
  減らせる（「使った」）。削除もここから
- 期限は元の一覧と同じ書き方（「2031.08.25」「2027.06」）で打ち、同じ書き方で出す。
  日付の選択画面にしないのは、月までしか無い期限があるのと、袋の数字をそのまま打つほうが早いため
- 0になったときの「補充する？」→買い出しリストは、日用品のリスト連携（フェーズ2）と一緒に入れる
- 仕組み: 期限の読み書き・色分けは `stockUtils.ts`（mobile・PWAで同じ中身。`npm run test:stock`）

### 3.5 必要数（2026-10-06に追加）

「家族3人（大人3人として数える）の1週間分」を確保できているかを品目ごとに確かめ、
**足りないものを赤で出す**（買い足すべきものが一目で分かるように）。

- 必要数は**ロットとは別の「目標」**（`stock_targets`）に持つ。1つの目標に複数のロットを数える
  （野菜スープは4種類×2ロット、水は500mlと1.8Lの両方）。ロットは `target_id` で目標を指す
- 必要数＝**1人1日あたり × 人数 × 日数**（水 3L × 3人 × 7日 = 63L）。ラジオのように人数・日数で
  増えないものは「決まった数」にする。人数・日数は家族で1つ（`families.stock_people / stock_days`、
  既定は3人・7日）。画面の −/＋ で変えられる
- 持っている量＝目標に数えるロットの「数 × 1つあたりの量」の合計。**期限切れのロットは数えない**
  （使えないため）。1つあたりの量はロットの単位を目標の単位に直す係数（水 500ml の1本は 0.5L）。既定は1
- 画面: 暮らしタブの「期限順 / 必要数」の切り替え。必要数の面は1行＝1目標で「持っている量 / 必要数」と
  「あと○○不足」（赤）か「足りています」。上の要約にも「不足 n品目」を出す。
  ロットをどの目標に数えるかは、備蓄の編集の「必要数に数える」で選ぶ
- 最初に入れた目標（3人×7日。食事は「ご飯・肉・野菜」を1日3食、おやつは別）:

| 目標 | 1人1日 | 必要数 | 数えるロット |
| --- | --- | --- | --- |
| 水 | 3L | 63L | 水 500ml（0.5L）・水 1.8L（1.8L） |
| 給水用バッグ | 決まった数 3枚（§3.6で追加） | 3枚 | ウォーターバッグ（10L） |
| ご飯（無洗米） | 0.25kg（1食約80g） | 5.25kg | まだ無い |
| 肉（やきとり缶） | 3個 | 63個 | やきとり缶 |
| 野菜（スープ） | 3食 | 63食 | カゴメ 野菜たっぷりスープ（4種×2ロット） |
| おやつ（えいようかん） | 2本（2026-10-06に1本から変更） | 42本 | えいようかん・チョコ |
| アクエリアス | 1袋（夏場の水分補給、1L） | 21袋 | アクエリアスパウダー |
| 非常用トイレ | 5回 | 105回 | BOS非常用トイレ |
| 防臭袋 | 5枚 | 105枚 | BOS防臭袋 |

- 買い足しを買い出しリストへ送る導線は、日用品のリスト連携（フェーズ2）と一緒に入れる

### 3.6 保管場所（2026-10-06に追加）

備蓄を**寝室（家に置く分）**と**持ち出し用バックパック（1日分）**に分けて置く。

- ロットごとに保管場所を持つ（`stock_items.storage`: `home`＝寝室 / `carry`＝持ち出し）。既存のロットは寝室
- 1つのロットの一部だけをバックパックへ移すことが多いので、備蓄の編集に**「一部を持ち出しへ n 個 移す」**を置く。
  元のロットの数を減らし、移した先に同じ品名・期限・数え先のロットがあればそこへ足し、無ければ新しいロットを作る
- 必要数は2段で確かめる
  - 全体: 1人1日あたり × 人数 × 日数（7日）。**寝室と持ち出しの両方を数える**（バックパックの分も家の備蓄の一部）
  - 持ち出し: 1人1日あたり × 人数 × 持ち出しの日数（`families.stock_carry_days`、既定1日）。持ち出しにある分だけ数える
  - 持ち出しに入れる品目かは目標ごとに決める（`stock_targets.carry`）。ご飯は炊くので入れない。
    決まった数の品目は、その数を全部持ち出しに入れる扱い
- 画面: 必要数の行に「持ち出し 3 / 9L 不足」を添え、どちらかが足りなければ行を赤くする。人数・日数の横に持ち出しの日数の −/＋。
  期限順の一覧では持ち出しのロットに「持ち出し」の札を付け、チップで「持ち出し」「寝室」に絞れる
- 最初の設定（2026-10-06）: **水とご飯以外**の6品目を持ち出しに入れる（やきとり缶 9個・スープ 9食・
  えいようかん 6本・アクエリアス 3袋・トイレ 15回・防臭袋 15枚）
  - **水は持ち出さない。** 1日分（9L）は約9kgで重すぎるうえ、災害時は給水が最優先で来るため、
    水の代わりに**給水用バッグ**（ウォーターバッグ 10L、1人1枚＝3枚。目標は決まった数で全部を持ち出し）を入れる

### 3.3 知らせる（2026-10-06に実装。フェーズ3）

- **期限の3か月前・1か月前**に家族全員の端末へ通知する。**毎朝9時（日本時間）に1通へまとめて**送る
  （1件ずつ送らない）。文面は「1か月以内: 水 500ml（2026.11.06）…」「3か月以内: …」で、
  品名は3つまで並べて残りは「ほかn件」。タップすると暮らしタブが開く
- **何を知らせるかは日付だけで決める。** 期限の3か月前の日・1か月前の日が「前回送った日の翌日から
  今日まで」に来た備蓄が対象（月までの期限は月末日から数える）。行ごとの「知らせた」印は持たない
  ——備蓄の行を直したり持ち出しへ移したりしても、同じお知らせは繰り返さない。
  実行が飛んでも次の朝に拾い直す（最大3日前まで。それより古い節目は知らせない）。
  期限の無いもの・期限切れ・数が0のものは対象にしない
- **受け取れるのはネイティブ版だけ。** Web Pushの送信は2026-09-18に撤去済みなので
  （docs/notifications.md）、PWA版には足していない（ネイティブでしかできないもの。CLAUDE.md）
- 予定タブには出さない（docs/lists.md §5「同じものを2か所に置かない」）
- 仕組み: 決まりごとは `_shared/stockExpiry.ts`（`npm run test:stock-expiry`）、
  配信は Edge Function `send-stock-expiry-reminders`（pg_cron が毎日0時UTCに叩く）、
  送信済み記録は `stock_expiry_deliveries`（`0058_stock_expiry_notifications.sql`）。
  通知チャンネルは `stock-expiry`

## 4. 日用品

### 4.1 データ（`household_products`）

| 列 | 内容 |
| --- | --- |
| `id` / `family_id` | 共有 |
| `name` | 「トイレットペーパー ダブル 12ロール」 |
| `category` | 自由入力（「紙類」「洗剤」「ベビー」など） |
| `store` | **いつも買うお店。** 自由入力。リストのグループ名と同じ書き方にする（§4.2） |
| `price` | いつもの値段（円、税込、int, null可） |
| `note` | 「セールなら¥398」など |
| `last_added_at` | 最後にリストへ送った日時（並び順に使う） |

- 家での置き場所は持たない（2026-10-06に決定）
- 1品＝1行。**お店ごとの値段比較は持たない**（「どこで買うか」は決め打ちできる。
  docs/lists.md §9 と同じ判断）。要るなら行を2つ作る

### 4.2 リストとの連携

- 台帳の行の「＋」で、**買い出しリストへ送る**
  - 送り先のリストは端末ごとに覚える（初回だけ選ぶ）
  - 送り先リストに **`store` と同じ名前のグループ** があればそこへ、無ければ未分類へ
  - 入れる内容は `name` だけ（値段は入れない。リストの項目は内容だけ、docs/lists.md §4）
- リストの追加欄で打ち始めると、台帳から候補を出す（逆向きの導線）
- これで docs/lists.md §8 の「よく買うもの」は**作らずに済む**（完了履歴ではなく台帳から出す）
- 台帳の行と、リストに入った項目はつながない（項目に `product_id` は持たない）。
  リスト側は今の作りのまま変えない

### 4.4 画面（2026-10-06に実装。フェーズ2）

- 暮らしタブはメニューから「**日用品**」の画面へ入る形にした（期限順/必要数は防災備蓄の中だけ。§2）。
  特別費はフェーズ4でメニューへ足す
- 日用品の面: 上に「送り先 ○○ ›」（押すと送り先のリストを選び直す）とお店のチップ。一覧はお店ごと
  （お店の名前順、お店の無いものは最後）、その中は品名の順。行の右に値段と「＋」（送る）。
  行を押すと編集（品名・お店・いつもの値段・カテゴリ・メモ・削除）。お店の候補には、台帳のお店と
  送り先リストのグループ名を出す
- 送ったら下に一言出す（「『牛乳』を買い出し（イオン）に入れました」）。**まだ買っていない同じ項目が
  既にあれば入れない**（「…に入っています」）。名前は全角・半角・前後の空白・英字の大小を気にせず比べる
- 送り先は端末ごとに覚える（mobile: AsyncStorage、PWA: localStorage）。まだ決めていない・消えたリストを
  指しているときは、選んでから送る
- **備蓄の不足もリストへ**: 必要数の面で全体が足りない行に「リストへ」を出す。内容は
  「目標の名前 不足量単位」（「肉（やきとり缶） 3個」）で、未分類へ入る。持ち出しだけの不足は
  買うのではなく移すものなので出さない
- **リストの追加欄の候補**: 項目の追加欄で打つと、台帳から名前を含むものを最大4つ出す（最近送ったものが先。
  打った文字と同じものは出さない）。押すとその内容で追加する。グループの追加欄には出さない
- 当初の「数が0になったら補充する？」は、必要数の不足から送る形で足りるため作らない
- 仕組み: 決まりごとは `shoppingUtils.ts`（`npm run test:shopping`）、送る処理は
  `living/useShoppingSender`（mobile・PWAで同じ形）

### 4.5 家計との連携（2026-10-07に決定。**設計のみ。日用品の画面を作り直すときに実装する**）

- 日用品の台帳は**食品も含めた「毎月必ず買うもの」**の台帳にする（日用品・雑貨・食品）。家計の記録の品目の画面の
  「日用品から選ぶ」ボタンから一覧で選んで入力できるようにする（docs/kakei.md §3.2）
- 台帳の品に、家計で記録するときの種類（小分類。`money_category_id`）を持たせる
- 家計の品目（`money_items.product_id`・`quantity`・`unit_price`）から、**品ごとの買った記録**を読む。日用品の画面で見られるようにするもの:
  - **いつ・何個買ったか**（日付・個数・単価・お店の一覧）
  - **毎月どのくらい買ったか**（月ごとの個数と金額）
  - **1日あたり・月あたり・年あたりの金額**（買った金額の合計を、最初に買った日から今日までの日数で割って出す）
- 「いつもの値段」（`price`）は、家計で記録したときの単価で更新する
- 在庫数は持たない（§4.3）のまま。買った記録から「そろそろ切れる頃」を出すかは、使ってから決める

### 4.3 在庫数を持たない理由

- 日用品は毎日減る。数を記録し続けないと数字がすぐ嘘になり、嘘の数字は無いより悪い
- 必要なのは「切れそう」と思ったときにすぐリストへ入ること。§4.2の1タップで足りる
- 例外は防災備蓄（減らない・期限がある）なので、そちらだけ数を持つ

## 5. 家計（特別費）とZaimの棲み分け

### 5.1 前提の確認

- **個人のアプリが銀行・カードと直接つながることはできない。** 銀行の更新系・参照系APIは
  電子決済等代行業の登録と各銀行との契約が要る。Zaimやマネーフォワードはこれを持っている
- **Zaim APIでは口座連携の明細は取れない（と報告されている）。** 取れるのは手入力した記録・
  カテゴリ・口座の一覧だけ（OAuth 1.0a）。連携口座の明細をアプリへ持ってくるには、
  ZaimのWebからのCSV出力を使うしかない
- つまり「自作アプリに統一」すると、**実績は手入力かCSVの取り込み**になる。
  毎月の明細を自分で取り込み続けるのは、Zaimの自動取得に比べて明らかに後退する

### 5.2 棲み分け（2026-10-06に決定。**2026-10-07に docs/kakei.md §1.1 で置き換えた**）

| 口座・カードの明細 | ◎ 自動取得 | × 持たない |
| 毎月のカテゴリ別予算 | ◎（既に機能がある） | × 作らない |
| 特別費（年に数回の大きな出費） | △ | ◎ |
| 備蓄の買い替え費 | × | ~~期限×値段から年ごとに自動で出す~~ → **値段は持たない**（2026-10-07。§10.2.1） |

- このアプリが作るのは**特別費だけ**。月々の家計簿は作らない（**2026-10-07: 家計管理全体を移す考えがあり、この線は見直す可能性がある。§10.3・§10.8**）

### 5.4 妻の資料を見て決めたこと（2026-10-07に決定。フェーズ4aは同日に実装）

#### 資料の中身

家の特別費のシート（年度＝4月〜3月）。シート単位ではこうなっている。

| シート | 中身 | アプリへの扱い |
| --- | --- | --- |
| 特別費 | 月ごとのブロックに「項目・予算・実績」を並べ、年間の予算・実績・差異を出す。特別収入（賞与など）も同じ形で別にある | **移す**（本体） |
| 特別費一覧 | 項目を種類別（住居費・車維持費・保険・税金・通信費・お祝い・学費・家具家電・季節対策・冠婚葬祭・旅行・子ども・お礼・その他）に並べ、発生予測月・金額・実績の発生月・金額を持つ | **移す**（項目の定義にあたる） |
| 学費 | 小中高の学校教育費・学校外活動費の目安 | 参考。特別費の本体には入れない（下の「見送り」） |
| 月々大分類・月々小分類 | 月の予算と、カテゴリ別の月次の収支。**実績が全部空**（予算の列だけ埋まっている） | **移さない**（§5.3。実際に使われておらず、Zaimが持っている） |

資料から読み取れた、データの形への要求:

- **1つの項目が年に複数回出る。** オイル交換は年2回、灯油は冬の3か月、アルバム作成は年4回。
  回ごとに月と金額を持つ必要がある
- **年をまたぐ周期がある。** 車検は2年おき。「今年度は出ない年」を区別しないと、
  年間の予算が実態とずれる（いまのシートは月の欄が空のまま今年度に入れている）
- **月が未定・仮のものがある。** 「2月(仮)」「12月(仮)」の旅行や、月の無い車検
- **予定していなかった出費が、予算0の項目として後から並ぶ。** 家具家電・出産祝い・サブスクなど、
  実績のほうが予算を大きく上回る年がある。予定外を記録できないと、シートを置き換えられない
- **特別収入（賞与）も同じ形で持っている。** 賞与の月と額が分かれば、「特別費は賞与で賄えるか」が見える
- 金額は円の整数。年度は4月始まり（月の並びが4月→3月）

#### データ

```
special_items   項目。 id / family_id / kind('expense'|'income') / category(自由入力) / name /
                cycle_years(1=毎年, 2=2年おき…, 0=1回きり) / base_year(周期の起点の年度。毎年なら null) /
                note / position
special_plans   予定。1回ぶん=1行。 id / item_id / month(1〜12, null=月未定) / amount / tentative(仮)
special_actuals 実績。 id / item_id / occurred_on(date) / amount / note
```

- 全部 `family_id` 単位のRLS（`current_family_id()`）。`special_plans`・`special_actuals` は
  `item_id` の項目の家族で絞る（`stock_items` と同じ作り）
- **その年度に出る項目か**は、周期と起点の年度から計算する（`(年度 − base_year) % cycle_years == 0`）。
  出る年度だけ予定として数える。**将来の年度も同じ計算で並べられる**（見通し）
- 予定外の出費は「予定の無い項目」として足す（シートの「予算0・実績あり」と同じ）。
  実績の日付から年度を決める（4月〜翌3月）
- 年度の始まりは4月に固定する（シートに合わせる。要るなら家族の設定へ）

#### 画面（暮らしタブのメニューの「特別費」。2026-10-07に実装）

- 上（固定）: 年度の切り替え（‹ 2026年度 ›）、「特別費（支出）/特別収入」の切り替え、**年間の「予算・実績・差異」**
  （差異＝予算−実績。シートの年間の欄と同じ。支出で実績が予算を超えたら赤）。
  収入と支出を並べた「収入 − 支出」（予算ベース・実績ベース）も1行で出す
- 中（スクロール）: **月ごとに並べる**（4月〜3月。シートのブロックと同じ並び）。1行＝項目×回で
  「項目名・予算・実績」。まだ払っていない予定は薄く、払った（実績あり）は通常、
  予算を超えたものは赤。月未定は最後にまとめる。月の見出しに月計
- **予定の行の右の「済」を1回押すと実績になる**（予算の額・今日の日付で入る。額が違えば開いて直す）。
  これで二重入力にならない。予定の無い出費は上の「追加」から項目ごと足す
- 行を押すと下から出る枠で直す（項目・種類・予定の月と額（複数回）・周期・メモ・削除）
- 種類（住居費・車維持費など）は自由入力で、候補は既にある値から出す（備蓄のカテゴリと同じ）

#### 備蓄の買い替え費（自動。§3）

> **2026-10-07: 備蓄の値段は持たないことにした**（数年おきの買い物で、金額は当てにならないため。§10.2.1）。
> 以下の金額の自動表示は行わない（当時の案として残す）。

- `stock_items` に **`price`（1つあたりの値段。円）** を足す。期限のある備蓄のうち値段を入れたものは、
  **期限の月に「買い替え」の行として自動で並べる**（数×値段。期限切れ・値段なしは出さない）
- 特別費の予定とは別の読み取り専用の行（「備蓄の買い替え」の種類）。実績にはしない
  （買ったら備蓄の期限・数を更新し、特別費として払った分は上の「済」で記録する）

#### 見通し（先の年度）

- 年度の切り替えで先の年度も見られる。さらに「これから5年」の年度ごとの合計
  （特別費の予定＋備蓄の買い替え − 特別収入の予定）を並べる面を足す（フェーズ4c）。
  いまのシートは今年度しか持てないので、これが置き換え以上の価値になる

#### 見送り

- **学費の目安**（小中高の教育費）: 年齢×学校段階の長期の見通しになり、特別費の「項目×回」とは
  形が違う。**特別費には入れず、目安として別で管理する**（2026-10-07に決定）。
  特別費が回ってから、子の年齢をもとにした別の面として足す（中身・置き場所はそのとき決める）
- **月ごとの積立の目安**（年間の予算 ÷ 12）: 要るかは使ってから決める。年間の合計は出るので、
  1行足すだけで足せる
- **月々の家計簿・予算**: §5.3のとおり作らない（シートでも使われていない）

#### 移し替え

- シートの内容（項目・予定・実績）は、移行のmigrationではなく**一度だけのSQL**で入れる
  （家族の私的なデータをリポジトリに残さない。§3.4と同じ）。移したあとはシートを更新しない
  （正はアプリ）。**移し替えは、migrationを本番へ適用してから行う**

#### 仕組み（フェーズ4a）

- 年度・周期・予定と実績の突き合わせは `specialUtils.ts`（mobile・PWAで同じ中身。`npm run test:special`）、
  読み書きは `api/specialExpenses.ts`、画面は `living/SpecialPanel`・`SpecialItemSheet`（PWAは `…Modal`）・
  `SpecialActualSheet`
- 予定にひも付く実績は `special_actuals.plan_id` で持つ（「済」で入る）。ひも付かない実績・
  予定を消した実績は「予定外」の行（予算0）として実績の月に並ぶ。項目を消すと予定・実績も消える
- 予定外の出費は「1回きり」の項目（予定なし）＋実績として入る。その実績を消すと項目も残さない
- 実績の日付から年度を決める（4月〜翌3月）。月未定の予定は、「済」にすると実績の月に移る

## 9. 福引チャンス（旧称「補助くじ」。2026-10-06に実装）

画面での名前は「**福引チャンス**」（2026-10-06に「補助くじ」から変更。そのままの名前で味気ないため、
わくわくする名前にした）。コード・DBの名前（`subsidy_draws`・`Lottery*`）はそのまま。

### 9.1 家のルール

お小遣い制だが、趣味以外で必要なものを買うときは家族のお金から出す。
「家族のお金か、お小遣いか」で迷うのをなくすため、次のルールにする。

- **対象**: 趣味以外で必要なもので、**税込500円以上3,000円以下**の商品
- **回数**: **1人あたり月2回まで**（日本時間の月）。**誕生月は3回**。余った回数は繰り越さない（ただし貯福で報われる。§9.3）
- **補助率**: くじ（ガラポン）で決める。**25%・50%・75%・100%の4つ。はずれはない**
- **補助額**: 100%は**商品代そのもの**（計算しない。全額、家族のお金で買う）。それ以外は補助率をかけて**100円単位**
  （49円以下は切り下げ、50円以上は切り上げ。2,480円の25%＝620円→600円）。残りはお小遣いから払う

### 9.2 玉と確率

福引のガラポン抽選機をイメージして、**玉の色が補助率**になっている。

| 玉 | 賞 | 補助率 | 出やすさ（重み） |
| --- | --- | --- | --- |
| 白玉 | ちょこっと賞 | 25% | 40 |
| 青玉 | はんぶん賞 | 50% | 30 |
| 赤玉 | たっぷり賞 | 75% | 20 |
| 金玉 | **まんがく賞** | **100%** | 10 |

- 重みは `subsidyLotteryUtils.ts` の `BALLS` で決める。**重みは変えず、救済で調整する**（2026-10-06に決定）
- 賞の名前・一言は `BALLS` だけで変えられる（金玉は「まんがく賞」。2026-10-06に福の神賞から変更）
- **画面では玉の色の名前（白玉・金玉など）を文字にしない**（2026-10-06）。賞品一覧・結果は玉の絵と賞の名前だけ。
  ヘルプでは「白＝25%・青＝50%・赤＝75%・金＝100%」と色で書き、100%は「**金賞**」と呼ぶ

### 9.3 救済（どれも自動。押さなくてよい）

確率の重みは変えず、引く前に玉の候補を絞る・補助率を上げることで調整する。
補助率は、その玉が出たときの補助率（ラッキーカラーで上がったあと）で数える。

| 救済 | 中身 |
| --- | --- |
| なだらか救済 | 25%が続くほど25%が出にくくなる（1連続で半分、2連続でゼロ）。月をまたいで数える |
| 3連続ブレーカー | 同じ補助率が3連続したら、次は別の補助率 |
| ラッキーカラー | 毎月1色（白・青・赤のどれか。家族共通で、月ごとに自動で決まる）が決まり、その色の玉が出たら**補助率が1段上がる**（100%まで届く）。2色にはしない（ラッキー感が薄れるため） |
| ひと押し券 | **25%が出るたびに1枚**もらえる。引く前に使うと、そのガラポンで25%が出なくなる（50%以上）。**期限なし** |
| 貯福 | **先月に引かなかった回数**があれば、今月の**最初の1回だけ**下限が上がる。1回分で50%以上、2回分で75%以上、3回分（誕生月の先月）で100%確定 |
| 月ならし | 先月に**2回以上**引いて、**すべて50%以下**なら、今月の最初の1回は75%以上 |

- 下限（貯福・月ならし・ひと押し券）が重なったときは、**一番高いものだけ**を使う（足し算しない）
- 貯福・月ならしは、**くじを始める前の月には権利が付かない**（`FEATURE_START_MONTH`＝2026-10）
- 候補が無くなるときは、3連続ブレーカー→なだらか救済の順にゆるめる
- ホームに今月のラッキーカラーと下限（「50%以上確定！」など）を出し、効いている救済は「賞品一覧」の枠に出す。確率は画面に出さない

**実際の確率**（`npm run test:lottery` のシミュレーション。月2回で毎回引く、ひと押し券は貯まり次第使う）

| 条件 | 年間の100%（1人） | 平均の補助率 |
| --- | --- | --- |
| 重みだけ（救済なし） | 2.4回 | 50.0% |
| 救済すべて | **約5.2回** | **約63%** |

- 目標は1人あたり年5〜6回（2か月に1回は出る）
- 貯福は、引かなかった月の次の1回の平均が、1回分で約67%、2回分で約83%、3回分で100%
- 費用の目安: 平均価格1,500円なら、平均63%で1回あたり約950円の補助

### 9.4 券と図鑑

くじで手に入る券は、**アカウントごと**に持つ（`lottery_coupons`）。「券」の面で見る。

| 券 | 手に入る場面 | 使い方 | 期限 |
| --- | --- | --- | --- |
| ひと押し券 | 25%が出るたび | くじの画面で、引く前に使う | なし |
| 補助率アップ券 | 100%の箱（図鑑の5・6） | くじの**結果の画面**で使う。**25%か50%の結果だけ**1段上がる（75%・100%には使えない）。引いて1日以内 | **なし** |

| カフェデート券 | 100%の箱（図鑑の3） | 同上 | 1か月 |
| ピクニックデート券 | 100%の箱（図鑑の4） | 同上 | 1か月 |

  （期限があると、使うために買い物を探すことになるため。2026-10-06に決定）
- 補助率アップ券は、5と6が全く同じ券（図鑑の2枠）

以前の「くじ・券・履歴」の3面の切り替えはやめた）。

  多く、金玉は光の筋が2重）。並びは「賞の名前・補助率の札 → 家族のお金から／お小遣いから（下に買うもの・価格）」だけ。

  いま効いている救済を「今回のおまけ」として並べる
- **持っている券**（枠）: 自分の使える券。お菓子・映画・カフェ・ピクニック・旅行の券は「使った」にする。

  - 金色の帯: 何周目（2周目からは「コンプリート n回」も）・集めた数（「3 / 6」）・6つの目盛り
  - 6枚のメダル: 集めたものは金色で特典のアイコンと名前、きらりと光る（押すと特典の説明）。
    まだのものは鍵と「？？？」で、押すと震える

  「金賞コレクション コンプリート！」とごほうびの券が弾んで出る（紙吹雪・光の筋）
- **履歴**（枠）: **アカウント（家族）ごと**に、過去のくじを月ごとに見る。**家計の合計や精算は出さない**（家計との連携は不要）

## 10. 画面の作り直し（2026-10-07に決定。**設計案。実装は面ごとに別チャット**）

### 10.1 なぜ作り直すか

暮らしタブの面（防災備蓄・日用品・特別費）は、同じ型（「見出し＋追加ボタン → 切り替え → 白いカードの縦一覧 →
行を押すと下から編集」）で作られている。作る手間は減ったが、**面ごとの「本当の問い」に答える形になっていない**。

| 面 | いまの型 | 本当の問い | いまの形が答えられていないこと |
| --- | --- | --- | --- |
| 防災備蓄 | 期限順の縦一覧 / 必要数の縦一覧（2つの面を切り替え） | 「いま、足りないもの・期限が迫るものは？ 手を打つには？」 | 期限順と必要数が別の面で、同じ品が2か所に出る。期限なしの備品が一覧の末尾に埋もれる。見つけたあとの「手を打つ」（買う・入れ替える・使う）が行ごとに遠い |
| 特別費 | 月ごとの縦一覧 | 「年間の資金繰りは足りるか？ 直近で何を払うか？」 | 年の全体像（月ごとの山・賞与との釣り合い）が一覧からは読めない。近々払うものが年の流れに埋もれる |
| 日用品 | 店ごとの縦一覧＋行の「＋」 | 「切れたものを、手早く買い出しに送る」 | 一覧を探して1件ずつ押す。リストに既にあるかが見えない。よく送るものが上に来ない |
| メニュー | 4つのアイコンカード＋要確認の件数 | 「いま暮らしで気にすることは？」 | 開かないと中身が分からず、毎回どれかに入って確かめる |

方針: **共通の部品（編集の下から出る枠・チップ・色）は使い回すが、画面の構成・並び・操作は面ごとに作り分ける。**
工数より使いやすさを優先する。

### 10.2 防災備蓄（形: 状態を見渡す「点検盤」。**2026-10-07に実装**）

- **上に「備えの状況」**（固定）: 「3人×7日分」に対する充足（全体の不足 n品目・持ち出しの不足 n品目）、
  期限切れ n件・3か月以内 n件。数字は押すと、その「要対応」へ飛ぶ
- **「要対応」を最上段に分ける**（あるときだけ出る）: 期限切れ・3か月以内・不足の品を、**一覧とは別のカードの束**にして
  置く。各カードに**その場の操作**を付ける
  - 期限が近い／切れた: 「買い替えた」（新しい期限と数を入れて、同じ品の新しいロットにする）、「食べた/使った」（−1）、
    「処分」
  - 不足: 「リストへ」（既存）
- **本体は「目標ごとのまとまり」**: 水・ご飯・肉…の目標ごとに1つの塊（進捗バー「持っている / 必要」、持ち出しの分を並べて）、
  その下にロットを期限順で入れ子にする。**期限順の面と必要数の面を1つにする**（同じ品が2か所に出ない）。
  目標に数えていない品は「その他の備品」の塊にまとめる
- **期限のないもの（ラジオ・ランタン・ポータブル電源など）は、塊として分ける**: 「備品（期限なし）」。
  期限順に混ぜない。期限の代わりに**「点検日」**（最後に動作を確かめた日）と**点検の間隔**を持つ（§10.7。間隔の既定は
  半年。品ごとに変えられる）。間隔を過ぎたら「要対応」に「点検の時期」として出す
- **保管場所**（寝室／持ち出し）は、上のタブで切り替える。**持ち出しバッグは「中身のチェック表」**として見られるようにする
  （品名・数・期限が1画面に収まり、半年ごとに点検した日付を残せる）
- 「先に使う順」: 日常で食べられるもの（ローリングストック）は、期限が近い順に「先に消費」の候補として出す
- ~~備蓄の値段を入れられるようにする~~（2026-10-07: 値段は持たない。§10.2.1）
- **「要対応」には、期限が近いもの（3か月を切ったもの）を出す**（金額は出さない）。
  3か月を切ってから出す理由: 3か月前に知れば、期限前に消費できる（通知 §3.3 と同じ線）

#### 10.2.2 実装メモ（2026-10-07。カテゴリを主役にした版）

最初の版は「情報を並べ替えただけ」の文字ばかりの一覧、次の版は「期限・不足」を画面の主役にしてしまい、
カテゴリが分からなくなった。**主役は「どんな備蓄が、どれだけあるか」**。期限・不足・点検は品目に付く補助の情報で、
前面に出さない（福引のように、この画面のための見た目を追求する方針。§10.1）。

- **色は淡い橙（防災備蓄の色）と赤だけ**。赤はいま対応が要るもの（期限切れ・3か月以内・不足・点検の時期）に限る。
  橙は絵柄の丸・リング・ボタン・選んだ状態を**淡く**塗るだけ（暗い色は文字以外に使わない）。緑・青・黄は使わない
  （多いと目がチカチカして、どれが大事か分からなくなる）
- 画面の組み立ては `StockBoard`（mobile: `components/living/StockBoard.tsx` / PWA: `components/sukusuku/living/StockBoard.tsx`）。
  「確認が必要なもの」は `StockAttention`、品目の詳しい画面は `StockProductDetail`、持ち出しバッグの点検は `StockBagCheck`、
  見た目の部品（リング・品名に合う絵柄）は `stockVisual.tsx`。並べ方・数え方は `stockUtils.ts`（`buildStockBoard`・
  `groupStockProducts`・`storageShares`・`stockIconKey` など。mobile・PWAで同じ中身。`npm run test:stock`）
- **寝室／持ち出し用の切り替えは置かない**（2026-10-07に決定）。一覧は全体の1つだけで、場所ごとの数は品目の詳しい画面で見る
- 上（固定。**まとめて静かに**。2026-10-07に整理）
  1. 見出し「‹ 防災備蓄」の右に、**淡い橙の丸いボタンを2つだけ**: 「バッグ」（持ち出しバッグの点検を開く。点検の時期だけ赤い点）と
     「＋」（そのまま追加の画面を開く。選ぶメニューは出さない）
  2. **備え度と「確認が必要」を1枚に**: 小さなリングと「3人×7日分」、その下に赤で「確認が必要 8件（不足 6・期限 2）」
     （0件なら「確認が必要なものはありません」と薄く）。押すと「確認が必要なもの」
  3. **カテゴリのタブ**（すべて／飲料・水／食料品…。文字だけで、選んだものに淡い橙の下線）
- **人数・日数は画面では変えない**（ほとんど変えないため。変えるときはプログラム・DB側で `families.stock_people` などを直す）
- 一覧（スクロール。寝室と持ち出し用を合わせた全体の備蓄）
  - **カテゴリの見出し（大きく太く）と品目数**、その下に品目の行（リスト。**余白を詰める**。品名は全文）
  - 行: 品名（普通の太さ）と、**全体の数（右に大きく太く）と単位（薄く小さく）**（絵柄・進捗の線は置かない）。
    品名の下の一行は**1つだけ**で、対応が要るものを先に（不足「あと3L不足」→ 期限「あと13日」→ 点検「点検の時期」。
    無ければ、いちばん近い期限か「点検まで4か月」を薄く）。場所ごとの数・必要数は詳しい画面へ
  - 同じ目標に数えるロット、または目標の無い同名のロットを1品目にまとめる。押すと**品目の詳しい画面**
  - 備品（期限なし）も、ほかの備蓄と同じくカテゴリの中に並べる
- **追加の画面（「＋」）で、必要数も一緒に決める**: 「必要数」の欄で「なし」／既にある必要数／「＋ 新しく決める」を選ぶ。
  新しく決めるときは、必要数と単位（例: 3 L）、「1人1日あたり／全体で決まった数」、「持ち出しバッグにも入れる」をその場で入れる
  （必要数の名前・カテゴリは品名・カテゴリを使う）。「この品1本あたり 2 L」と、目安「3人×7日分＝63L（バッグに 9L）」を出す。
  保存すると、先に必要数を作ってから品目をそれに数える。**別の「目標（必要数）を追加」は置かない**。
  既にある必要数を直すのは、品目の詳しい画面の「必要数を直す」から
- **品目の詳しい画面**（常に出すボタンは置かない。見るための画面）
  1. **全体の数の箱**: 「全体 49L　必要 63・あと 14」。その中に**寝室・持ち出し用の帯**（それぞれの要る量の幅で並べ、持っている分を
     塗り、足りない分は淡い赤）と、1行ずつ「寝室 48 / 54L　あと 6L」「持ち出し用 1 / 9L　あと 8L」。**足りない場所だけ赤**。
     片方が多く、もう片方が足りないときは「2食多い（分けられます）」と添える。目標の無い品目は数の内訳だけ
     - 持ち出し用の要る量＝人数×バッグの日数（持ち出しに入れる目標だけ）。寝室の要る量＝全体の必要数 − 持ち出し用の要る量
  2. **ロットを保管場所ごと**（「寝室 48L」「持ち出し用 1L」の見出し）に期限順で。行は期限（「2026.12 まで」「あと2か月」）・数・鉛筆。
     **期限の無い備品は、期限の代わりに点検した日と次の点検**（「2026.02.10 に点検」「次は 2026.08.10 ごろ・あと4か月」／
     時期が来たら赤で「点検の時期です」。点検しない備品は「期限なし」）
  3. ロットを押すと編集。**持ち出し用へ分ける／寝室へ戻すは、編集の「保管場所」のすぐ下**（「持ち出し用へ分ける − 2本 ＋ ［分ける］」。
     1つだけのロットも移せる。全部移すときは保管場所を切り替えて保存。1回分けたら、ほとんど触らないため）
- 「確認が必要なもの」（上の帯から開く）: 期限が近い・切れた（あと○日、買い替え／使った −1／処分）、
  足りないもの（あと○、リストへ）、
  点検の時期（持ち出しバッグの「確かめる」＝バッグの点検を開く、備品の「点検した」、「まとめて点検した」）
- **持ち出しバッグの点検**（「バッグ」と「確かめる」から開くシート）: 確認の進捗リング、前回の点検、足りないものの札、
  **バッグの中身の行（カテゴリごと）**（左の丸を押すと淡い橙の✓に。右の鉛筆で編集）。全部確かめると下の「点検完了」が押せて、
  全ロットの点検日に今日を記録する（チェックは画面の中だけ）
- 点検の時期は**画面の「確認が必要なもの」だけ**で、通知は出さない（§10.8 で決定）。持ち出しバッグは全体で半年（固定）
- 見送り: 「先に使う順」（ローリングストック）。日常で食べるものを見分ける印が要るため、次に回す

#### 10.2.1 値段は持たない（2026-10-07に決定）

- **備蓄の値段・費用・見込み額は、画面にも DB にも持たない。** 数年おきの買い物で、金額は当てにならないため
  （最初は1つあたりの値段・最小単位あたり・必要数を揃える費用・買い替えの見込み額を出す案だったが、取り下げた）
- 一覧・品目の詳しい画面・「確認が必要なもの」・編集・買い替えのどこにも金額を出さない（入力欄も置かない）
- 特別費の面には備蓄の買い替えを出さない（§10.3。2026-10-07に決定）

### 10.4 日用品（形: 手早く送る「買い物かご」）

- **よく送るものを上に**: 「最近送った」「よく送る」を先頭の段に（`last_added_at`）。切れたら、まずここから1タップ
- **店ごとのタイル**: 店のタブ（または見出し）ごとに、品名を**押しやすい大きさのタイル**で並べる（一覧の行ではなく）。
  タイルを押すと「かご」に入り、**まとめて送る**（送り先リストと店のグループへ振り分け）。1件ずつ送ることもできる
- **リストの状態を見せる**: 既に買い出しリストにある（まだ買っていない）品は、タイルに「入っています」の印。
  二重に送らない（いまは送ったあとにしか分からない）
- 検索欄で絞り込み。値段は小さく添える（店の比較はしない。§4.1）
- 編集（品名・お店・値段・カテゴリ・メモ）は、タイルの長押し／「編集」から（いまの下から出る枠）

### 10.5 メニュー（形: 今日の「暮らし」ダッシュボード）

- カードを**情報のある要約**にする: 備蓄＝「期限3か月以内 n件・不足 n品目」、特別費＝「今月の未払 n件（¥）」、
  日用品＝「買い出しリスト n件・最近送ったもの」。押すとその面の「要対応」へ入る
- 福引チャンスは、ゲームなので小さな入口に下げる（要約のカードと同じ並びに置かない）
- 「要確認」の件数は、面を開かなくても見えるようにする（いまの赤い札を、要約の中へ）
