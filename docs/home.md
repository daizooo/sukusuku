# 暮らしタブ（防災備蓄・日用品・特別費）の検討

家（住まい）にまつわるものを1つのタブにまとめるための設計メモ。
「ホーム」は以前あったホーム画面（2026-10-02に育児タブへ統合）と紛らわしいので、
タブの名前は **「暮らし」** とする（§2。2026-10-06に決定）。

結論を先に書く。

- **新しく持つのは「防災備蓄」と「日用品」の2つ。** どちらも家族で共有し、
  リストと同じ `family_id` 単位のRLSにする（§3・§4）。
- **防災備蓄の本当の課題は「数を数えること」ではなく「期限切れに気づくこと」。**
  1行＝品名×期限（ロット）で持ち、期限の近い順に並べ、近づいたら知らせる（§3）。
- **日用品は「よく買うもの」の台帳。** リストの「よく買うもの」（docs/lists.md §8
  フェーズ2の残り）はこの台帳で置き換える。台帳から1タップで買い出しリストへ送り、
  **お店の名前とリストのグループ名が一致すればそのグループへ入れる**（§4.2）。
- **日用品の在庫数は持たない。** 毎日減るものを数え続けるのは続かない。
  「切れそう」と思った瞬間にリストへ送れれば足りる（§4.3）。
- **家計は「Zaimの代わり」を作らない。** 実績（口座・カードの明細）は引き続きZaim。
  アプリは**特別費（年に数回の大きな出費）の見通しに特化**する（§5。2026-10-06に決定）。

## 3. 防災備蓄

### 3.1 データ（`stock_items`）

| 列 | 内容 |
| --- | --- |
| `id` / `family_id` | 家族単位で共有。RLSは `current_family_id()` |
| `category` | 「飲料・水」「食料品」「衛生用品」「日用品・生活雑貨」「照明・情報・電池類」など。**自由入力**（候補は既存の値から出す） |
| `name` | 「カゴメ 野菜たっぷりスープ（豆）」 |
| `quantity` | 数（numeric） |
| `unit` | 「本」「袋」「個」「PC」「回分」「枚」。自由入力 |
| `expires_on` | 賞味・使用期限（date, null可）。期限の無いもの（衛生用品・ラジオ・ランタン・ポータブル電源など）はnull |
| `expires_month_only` | 期限が「2027.06」のように月までしか無いとき true。`expires_on` は**その月の末日**で持つ |
| `note` | 置き場所など（任意） |
| `position` / `created_at` / `updated_at` | |

- **1行＝品名×期限（ロット）。** 同じ品でも期限が違えば別の行にする
  （今のシートでもカゴメのスープは 12PC と 4PC で期限が違う）。画面でも1行ずつ並べる（§3.2）
- 価格は持たない（特別費（§5）で買い替え費を出すときに足す）

### 3.2 画面（2026-10-06に実装。フェーズ1）

- 上（固定）: 見出し「防災備蓄」と「追加」、要約、カテゴリで絞るチップ（カテゴリが2つ以上のとき）
  - 要約は「期限切れ n件」「3か月以内 n件」「1年以内 n件」（0件のものは出さない。
    どれも無ければ「1年以内に期限が来るものはありません」）
- 中（スクロール）: **1行＝1ロットを期限の近い順**（期限なしは末尾、その中はカテゴリ→品名の順）。
  品名でまとめることはしない（期限の近い順に並べると、同じ品のロットが離れても期限の早い方が先に出るため）
  - 右に数と単位、その下に期限。期限の色は1年以内が橙、3か月以内・切れたものが赤
    （切れたものは「切れ 2026.09.30」）。期限の無いものは「期限なし」
- 行を押すと、下から出る枠で直す（品名・カテゴリ・数・単位・期限・メモ）。数は −/＋ で1つずつ
  減らせる（「使った」）。削除もここから
- 期限は元の一覧と同じ書き方（「2031.08.25」「2027.06」）で打ち、同じ書き方で出す。
  日付の選択画面にしないのは、月までしか無い期限があるのと、袋の数字をそのまま打つほうが早いため
- 0になったときの「補充する？」→買い出しリストは、日用品のリスト連携（フェーズ2）と一緒に入れる
- 仕組み: 期限の読み書き・色分けは `stockUtils.ts`（mobile・PWAで同じ中身。`npm run test:stock`）

### 3.5 必要数（2026-10-06に追加）

「家族3人（大人3人として数える）の1週間分」を確保できているかを品目ごとに確かめ、
**足りないものを赤で出す**（買い足すべきものが一目で分かるように）。

- 必要数は**ロットとは別の「目標」**（`stock_targets`）に持つ。1つの目標に複数のロットを数える
  （野菜スープは4種類×2ロット、水は500mlと1.8Lの両方）。ロットは `target_id` で目標を指す
- 必要数＝**1人1日あたり × 人数 × 日数**（水 3L × 3人 × 7日 = 63L）。ラジオのように人数・日数で
  増えないものは「決まった数」にする。人数・日数は家族で1つ（`families.stock_people / stock_days`、
  既定は3人・7日）。画面の −/＋ で変えられる
- 持っている量＝目標に数えるロットの「数 × 1つあたりの量」の合計。**期限切れのロットは数えない**
  （使えないため）。1つあたりの量はロットの単位を目標の単位に直す係数（水 500ml の1本は 0.5L）。既定は1
- 画面: 暮らしタブの「期限順 / 必要数」の切り替え。必要数の面は1行＝1目標で「持っている量 / 必要数」と
  「あと○○不足」（赤）か「足りています」。上の要約にも「不足 n品目」を出す。
  ロットをどの目標に数えるかは、備蓄の編集の「必要数に数える」で選ぶ
- 最初に入れた目標（3人×7日。食事は「ご飯・肉・野菜」を1日3食、おやつは別）:

| 目標 | 1人1日 | 必要数 | 数えるロット |
| --- | --- | --- | --- |
| 水 | 3L | 63L | 水 500ml（0.5L）・水 1.8L（1.8L） |
| 給水用バッグ | 決まった数 3枚（§3.6で追加） | 3枚 | ウォーターバッグ（10L） |
| ご飯（無洗米） | 0.25kg（1食約80g） | 5.25kg | まだ無い |
| 肉（やきとり缶） | 3個 | 63個 | やきとり缶 |
| 野菜（スープ） | 3食 | 63食 | カゴメ 野菜たっぷりスープ（4種×2ロット） |
| おやつ（えいようかん） | 2本（2026-10-06に1本から変更） | 42本 | えいようかん・チョコ |
| アクエリアス | 1袋（夏場の水分補給、1L） | 21袋 | アクエリアスパウダー |
| 非常用トイレ | 5回 | 105回 | BOS非常用トイレ |
| 防臭袋 | 5枚 | 105枚 | BOS防臭袋 |

- 買い足しを買い出しリストへ送る導線は、日用品のリスト連携（フェーズ2）と一緒に入れる

### 3.6 保管場所（2026-10-06に追加）

備蓄を**寝室（家に置く分）**と**持ち出し用バックパック（1日分）**に分けて置く。

- ロットごとに保管場所を持つ（`stock_items.storage`: `home`＝寝室 / `carry`＝持ち出し）。既存のロットは寝室
- 1つのロットの一部だけをバックパックへ移すことが多いので、備蓄の編集に**「一部を持ち出しへ n 個 移す」**を置く。
  元のロットの数を減らし、移した先に同じ品名・期限・数え先のロットがあればそこへ足し、無ければ新しいロットを作る
- 必要数は2段で確かめる
  - 全体: 1人1日あたり × 人数 × 日数（7日）。**寝室と持ち出しの両方を数える**（バックパックの分も家の備蓄の一部）
  - 持ち出し: 1人1日あたり × 人数 × 持ち出しの日数（`families.stock_carry_days`、既定1日）。持ち出しにある分だけ数える
  - 持ち出しに入れる品目かは目標ごとに決める（`stock_targets.carry`）。ご飯は炊くので入れない。
    決まった数の品目は、その数を全部持ち出しに入れる扱い
- 画面: 必要数の行に「持ち出し 3 / 9L 不足」を添え、どちらかが足りなければ行を赤くする。人数・日数の横に持ち出しの日数の −/＋。
  期限順の一覧では持ち出しのロットに「持ち出し」の札を付け、チップで「持ち出し」「寝室」に絞れる
- 最初の設定（2026-10-06）: **水とご飯以外**の6品目を持ち出しに入れる（やきとり缶 9個・スープ 9食・
  えいようかん 6本・アクエリアス 3袋・トイレ 15回・防臭袋 15枚）
  - **水は持ち出さない。** 1日分（9L）は約9kgで重すぎるうえ、災害時は給水が最優先で来るため、
    水の代わりに**給水用バッグ**（ウォーターバッグ 10L、1人1枚＝3枚。目標は決まった数で全部を持ち出し）を入れる

### 3.3 知らせる（2026-10-06に実装。フェーズ3）

- **期限の3か月前・1か月前**に家族全員の端末へ通知する。**毎朝9時（日本時間）に1通へまとめて**送る
  （1件ずつ送らない）。文面は「1か月以内: 水 500ml（2026.11.06）…」「3か月以内: …」で、
  品名は3つまで並べて残りは「ほかn件」。タップすると暮らしタブが開く
- **何を知らせるかは日付だけで決める。** 期限の3か月前の日・1か月前の日が「前回送った日の翌日から
  今日まで」に来た備蓄が対象（月までの期限は月末日から数える）。行ごとの「知らせた」印は持たない
  ——備蓄の行を直したり持ち出しへ移したりしても、同じお知らせは繰り返さない。
  実行が飛んでも次の朝に拾い直す（最大3日前まで。それより古い節目は知らせない）。
  期限の無いもの・期限切れ・数が0のものは対象にしない
- **受け取れるのはネイティブ版だけ。** Web Pushの送信は2026-09-18に撤去済みなので
  （docs/notifications.md）、PWA版には足していない（ネイティブでしかできないもの。CLAUDE.md）
- 予定タブには出さない（docs/lists.md §5「同じものを2か所に置かない」）
- 仕組み: 決まりごとは `_shared/stockExpiry.ts`（`npm run test:stock-expiry`）、
  配信は Edge Function `send-stock-expiry-reminders`（pg_cron が毎日0時UTCに叩く）、
  送信済み記録は `stock_expiry_deliveries`（`0058_stock_expiry_notifications.sql`）。
  通知チャンネルは `stock-expiry`

### 3.4 今のシートからの移し替え

- 「災害備蓄品一覧」（PDF）の26品目と、ポータブル電源（Jackery 2000 New・200Wソーラーパネル、

- 「防災グッズ」シート（購入計画）は移さない。未購入の物が出たら買い出しリストへ入れる

## 4. 日用品

### 4.1 データ（`household_products`）

| 列 | 内容 |
| --- | --- |
| `id` / `family_id` | 共有 |
| `name` | 「トイレットペーパー ダブル 12ロール」 |
| `category` | 自由入力（「紙類」「洗剤」「ベビー」など） |
| `store` | **いつも買うお店。** 自由入力。リストのグループ名と同じ書き方にする（§4.2） |
| `price` | いつもの値段（円、税込、int, null可） |
| `note` | 「セールなら¥398」など |
| `last_added_at` | 最後にリストへ送った日時（並び順に使う） |

- 家での置き場所は持たない（2026-10-06に決定）
- 1品＝1行。**お店ごとの値段比較は持たない**（「どこで買うか」は決め打ちできる。
  docs/lists.md §9 と同じ判断）。要るなら行を2つ作る

### 4.2 リストとの連携

- 台帳の行の「＋」で、**買い出しリストへ送る**
  - 送り先のリストは端末ごとに覚える（初回だけ選ぶ）
  - 送り先リストに **`store` と同じ名前のグループ** があればそこへ、無ければ未分類へ
  - 入れる内容は `name` だけ（値段は入れない。リストの項目は内容だけ、docs/lists.md §4）
- リストの追加欄で打ち始めると、台帳から候補を出す（逆向きの導線）
- これで docs/lists.md §8 の「よく買うもの」は**作らずに済む**（完了履歴ではなく台帳から出す）
- 台帳の行と、リストに入った項目はつながない（項目に `product_id` は持たない）。
  リスト側は今の作りのまま変えない

### 4.4 画面（2026-10-06に実装。フェーズ2）

- 暮らしタブはメニューから「**日用品**」の画面へ入る形にした（期限順/必要数は防災備蓄の中だけ。§2）。
  特別費はフェーズ4でメニューへ足す
- 日用品の面: 上に「送り先 ○○ ›」（押すと送り先のリストを選び直す）とお店のチップ。一覧はお店ごと
  （お店の名前順、お店の無いものは最後）、その中は品名の順。行の右に値段と「＋」（送る）。
  行を押すと編集（品名・お店・いつもの値段・カテゴリ・メモ・削除）。お店の候補には、台帳のお店と
  送り先リストのグループ名を出す
- 送ったら下に一言出す（「『牛乳』を買い出し（イオン）に入れました」）。**まだ買っていない同じ項目が
  既にあれば入れない**（「…に入っています」）。名前は全角・半角・前後の空白・英字の大小を気にせず比べる
- 送り先は端末ごとに覚える（mobile: AsyncStorage、PWA: localStorage）。まだ決めていない・消えたリストを
  指しているときは、選んでから送る
- **備蓄の不足もリストへ**: 必要数の面で全体が足りない行に「リストへ」を出す。内容は
  「目標の名前 不足量単位」（「肉（やきとり缶） 3個」）で、未分類へ入る。持ち出しだけの不足は
  買うのではなく移すものなので出さない
- **リストの追加欄の候補**: 項目の追加欄で打つと、台帳から名前を含むものを最大4つ出す（最近送ったものが先。
  打った文字と同じものは出さない）。押すとその内容で追加する。グループの追加欄には出さない
- 当初の「数が0になったら補充する？」は、必要数の不足から送る形で足りるため作らない
- 仕組み: 決まりごとは `shoppingUtils.ts`（`npm run test:shopping`）、送る処理は
  `living/useShoppingSender`（mobile・PWAで同じ形）

### 4.3 在庫数を持たない理由

- 日用品は毎日減る。数を記録し続けないと数字がすぐ嘘になり、嘘の数字は無いより悪い
- 必要なのは「切れそう」と思ったときにすぐリストへ入ること。§4.2の1タップで足りる
- 例外は防災備蓄（減らない・期限がある）なので、そちらだけ数を持つ

## 5. 家計（特別費）とZaimの棲み分け

### 5.1 前提の確認

- **個人のアプリが銀行・カードと直接つながることはできない。** 銀行の更新系・参照系APIは
  電子決済等代行業の登録と各銀行との契約が要る。Zaimやマネーフォワードはこれを持っている
- **Zaim APIでは口座連携の明細は取れない（と報告されている）。** 取れるのは手入力した記録・
  カテゴリ・口座の一覧だけ（OAuth 1.0a）。連携口座の明細をアプリへ持ってくるには、
  ZaimのWebからのCSV出力を使うしかない
- つまり「自作アプリに統一」すると、**実績は手入力かCSVの取り込み**になる。
  毎月の明細を自分で取り込み続けるのは、Zaimの自動取得に比べて明らかに後退する

### 5.2 棲み分け（2026-10-06に決定）

| | Zaim | このアプリ |
| --- | --- | --- |
| 役目 | **実績**（何にいくら使ったか） | **特別費の見通し**（いつ・何に・いくら要るか） |
| 口座・カードの明細 | ◎ 自動取得 | × 持たない |
| 毎月のカテゴリ別予算 | ◎（既に機能がある） | × 作らない |
| 特別費（年に数回の大きな出費） | △ | ◎ |
| 備蓄の買い替え費 | × | ◎ **期限×値段から年ごとに自動で出す**（§3） |

## 9. 福引チャンス（旧称「補助くじ」。2026-10-06に実装）

画面での名前は「**福引チャンス**」（2026-10-06に「補助くじ」から変更。そのままの名前で味気ないため、
わくわくする名前にした）。コード・DBの名前（`subsidy_draws`・`Lottery*`）はそのまま。

### 9.1 家のルール

お小遣い制だが、趣味以外で必要なものを買うときは家族のお金から出す。
「家族のお金か、お小遣いか」で迷うのをなくすため、次のルールにする。

- **対象**: 趣味以外で必要なもので、**税込500円以上3,000円以下**の商品
- **回数**: **1人あたり月2回まで**（日本時間の月）。**誕生月は3回**。余った回数は繰り越さない（ただし貯福で報われる。§9.3）
- **補助率**: くじ（ガラポン）で決める。**25%・50%・75%・100%の4つ。はずれはない**
- **補助額**: 100%は**商品代そのもの**（計算しない。全額、家族のお金で買う）。それ以外は補助率をかけて**100円単位**
  （49円以下は切り下げ、50円以上は切り上げ。2,480円の25%＝620円→600円）。残りはお小遣いから払う

### 9.2 玉と確率

福引のガラポン抽選機をイメージして、**玉の色が補助率**になっている。

| 玉 | 賞 | 補助率 | 出やすさ（重み） |
| --- | --- | --- | --- |
| 白玉 | ちょこっと賞 | 25% | 40 |
| 青玉 | はんぶん賞 | 50% | 30 |
| 赤玉 | たっぷり賞 | 75% | 20 |
| 金玉 | **まんがく賞** | **100%** | 10 |

- 重みは `subsidyLotteryUtils.ts` の `BALLS` で決める。**重みは変えず、救済で調整する**（2026-10-06に決定）
- 賞の名前・一言は `BALLS` だけで変えられる（金玉は「まんがく賞」。2026-10-06に福の神賞から変更）
- **画面では玉の色の名前（白玉・金玉など）を文字にしない**（2026-10-06）。賞品一覧・結果は玉の絵と賞の名前だけ。
  ヘルプでは「白＝25%・青＝50%・赤＝75%・金＝100%」と色で書き、100%は「**金賞**」と呼ぶ

### 9.3 救済（どれも自動。押さなくてよい）

確率の重みは変えず、引く前に玉の候補を絞る・補助率を上げることで調整する。
補助率は、その玉が出たときの補助率（ラッキーカラーで上がったあと）で数える。

| 救済 | 中身 |
| --- | --- |
| なだらか救済 | 25%が続くほど25%が出にくくなる（1連続で半分、2連続でゼロ）。月をまたいで数える |
| 3連続ブレーカー | 同じ補助率が3連続したら、次は別の補助率 |
| ラッキーカラー | 毎月1色（白・青・赤のどれか。家族共通で、月ごとに自動で決まる）が決まり、その色の玉が出たら**補助率が1段上がる**（100%まで届く）。2色にはしない（ラッキー感が薄れるため） |
| ひと押し券 | **25%が出るたびに1枚**もらえる。引く前に使うと、そのガラポンで25%が出なくなる（50%以上）。**期限なし** |
| 貯福 | **先月に引かなかった回数**があれば、今月の**最初の1回だけ**下限が上がる。1回分で50%以上、2回分で75%以上、3回分（誕生月の先月）で100%確定 |
| 月ならし | 先月に**2回以上**引いて、**すべて50%以下**なら、今月の最初の1回は75%以上 |

- 下限（貯福・月ならし・ひと押し券）が重なったときは、**一番高いものだけ**を使う（足し算しない）
- 貯福・月ならしは、**くじを始める前の月には権利が付かない**（`FEATURE_START_MONTH`＝2026-10）
- 候補が無くなるときは、3連続ブレーカー→なだらか救済の順にゆるめる
- ホームに今月のラッキーカラーと下限（「50%以上確定！」など）を出し、効いている救済は「賞品一覧」の枠に出す。確率は画面に出さない

**実際の確率**（`npm run test:lottery` のシミュレーション。月2回で毎回引く、ひと押し券は貯まり次第使う）

| 条件 | 年間の100%（1人） | 平均の補助率 |
| --- | --- | --- |
| 重みだけ（救済なし） | 2.4回 | 50.0% |
| 救済すべて | **約5.2回** | **約63%** |

- 目標は1人あたり年5〜6回（2か月に1回は出る）
- 貯福は、引かなかった月の次の1回の平均が、1回分で約67%、2回分で約83%、3回分で100%
- 費用の目安: 平均価格1,500円なら、平均63%で1回あたり約950円の補助

### 9.4 券と図鑑

くじで手に入る券は、**アカウントごと**に持つ（`lottery_coupons`）。「券」の面で見る。

| 券 | 手に入る場面 | 使い方 | 期限 |
| --- | --- | --- | --- |
| ひと押し券 | 25%が出るたび | くじの画面で、引く前に使う | なし |
| 補助率アップ券 | 100%の箱（図鑑の5・6） | くじの**結果の画面**で使う。**25%か50%の結果だけ**1段上がる（75%・100%には使えない）。引いて1日以内 | **なし** |
| 休日のお菓子・アイス＋1個券 | 100%の箱（図鑑の1） | 「使った」にする | 1か月 |
| 映画デート券 | 100%の箱（図鑑の2） | 同上 | 1か月 |
| カフェデート券 | 100%の箱（図鑑の3） | 同上 | 1か月 |
| ピクニックデート券 | 100%の箱（図鑑の4） | 同上 | 1か月 |
| 日帰り旅行券 | 図鑑の6つが集まったとき | 同上 | **なし** |

- **100%（金玉）が出ると、3つの箱から1つ選んで開ける。** 中身は、図鑑で**まだ集めていない枠**からランダムに1つ（**重複なし**）。
  どの箱を選んでも同じ（サーバーで決める）。6つ目で日帰り旅行券も出て、図鑑は次の周（2周目）に進む
- 図鑑は**1人ずつ**集める。**使った券・期限切れの券も、図鑑には残る**（使わずに溜め込まないように）
- 期限は**手に入れた日から1か月**（お菓子・映画・カフェ・ピクニックの券）。**ひと押し券・補助率アップ券・日帰り旅行券は期限なし**
  （期限があると、使うために買い物を探すことになるため。2026-10-06に決定）
- 補助率アップ券は、5と6が全く同じ券（図鑑の2枠）

### 9.5 画面

暮らしタブのメニューの1つ「福引チャンス」。**くじのホーム1枚**で、ほかは中央の枠で開く（2026-10-06に作り直し。
以前の「くじ・券・履歴」の3面の切り替えはやめた）。

- **ホーム**: 赤〜橙の1枚の面（区切りの枠を作らない）に、左上に福引券の残り（「福引券 あと2回」の1つにまとめる）、
  右上に「**持っている券 n**」（使える券があるときだけ）、ガラポンの絵、チップ（「今月のラッキーカラー ●青玉」・
  「50%以上確定！」などの下限・ひと押し券を使うか）、**買いたいもの・金額**（入力欄の注釈は「買いたいもの」「金額（例：2000）」だけ）、
  大きな「ガラポン！」、下に「**賞品一覧**」「**金コレ**」「**履歴**」「**ヘルプ**」のボタン。
  ルールの文や救済の説明はホームに出さない。**確率はどこにも出さない**
- **回す**: 「ガラポン！」→ 確認（引き直しはできない）→ ホームのガラポンが回る（「ガラガラガラ…」。そのあいだに記録する）
  → 受け皿に玉が転がり出る → **結果の枠**が開く
- **結果の枠**: 出た玉が弾むように出て、後ろで光の筋が回り紙吹雪が舞う（はずれは無いので毎回。補助率が高いほど紙吹雪が
  多く、金玉は光の筋が2重）。並びは「賞の名前・補助率の札 → 家族のお金から／お小遣いから（下に買うもの・価格）」だけ。
  ラッキーカラー・補助率アップ券で上がったときは一言、25%ならひと押し券をもらった一言（「次回以降、使うと25%が出なくなります」）。
  25%か50%で補助率アップ券があればその場で使える。100%なら箱（順番に揺れる）を選んで開ける
- **賞品一覧**（枠）: 玉の絵・賞の名前・補助率（％は確率と紛れないよう「補助率」と添える）。今月のラッキーカラーの玉に印、
  いま効いている救済を「今回のおまけ」として並べる
- **持っている券**（枠）: 自分の使える券。お菓子・映画・カフェ・ピクニック・旅行の券は「使った」にする。
  券は使うものなので、下のボタンには置かず、持っているときだけホームの右上にボタンを出す
- **金賞コレクション**（ホームのボタンだけ「金コレ」。枠の見出しなど、ほかは「金賞コレクション」と書く。枠）:
  台紙（`LotteryCollectionBoard`）と、使用済み・期限切れの券。台紙は上から
  - 金色の帯: 何周目（2周目からは「コンプリート n回」も）・集めた数（「3 / 6」）・6つの目盛り
  - 6枚のメダル: 集めたものは金色で特典のアイコンと名前、きらりと光る（押すと特典の説明）。
    まだのものは鍵と「？？？」で、押すと震える
  - 宝箱: 集めた数が多いほど大きく・せわしなく揺れる。下に「あとnつそろうと…？」（あと1つで「宝箱がガタガタ言っている…！」）。
    押すと震えて「まだ開かない…」などの一言が順に出る
  **6つそろえたごほうび（日帰り旅行券）は書かない**。そろった瞬間の結果の枠で、6つの枠が順に光り
  「金賞コレクション コンプリート！」とごほうびの券が弾んで出る（紙吹雪・光の筋）
- **履歴**（枠）: **アカウント（家族）ごと**に、過去のくじを月ごとに見る。**家計の合計や精算は出さない**（家計との連携は不要）
- **ヘルプ**（枠）: 「対象」「補助」「うれしい仕組み」「注意」の4つの見出しに、短い1行ずつ（「：」の前は太字）。下にテストモード（§9.6。夫にだけ出す）
- **知ってしまうと面白くないものは画面に書かない**: 確率、金賞の特典の中身、金コレをそろえたごほうび、救済の細かい数字
- 動きは端末の「アニメーションを減らす」設定でも止めない（くじの演出そのものなので）
- 絵と動きは `GaraponMachine`・`LotteryCelebration`、枠は `LotteryDialog`（mobile・PWAで同じ形。PWA版の動きは `globals.css`）

### 9.6 データと仕組み

- ルール説明（「？」）の文言は `subsidyLotteryUtils.ts` の `lotteryHelp()`（mobile・PWAで同じ。数字は定数から作る）
- `subsidy_draws`（1行＝1回）: 引いた人・買うもの・税込価格（500〜3,000円）・出た玉・補助率・補助額・補助率アップ券を使ったか・
  使ったひと押し券・時刻。家族みんなが読め、引けるのは自分の分だけ。**update / delete のpolicyは置かない**（引き直し防止。
  補助率アップ券の反映は関数 `lottery_use_rate_up` だけが行う）
- `lottery_coupons`: 券。**書き込みは関数・トリガーだけ**（アプリから直接は入れられない）
  - 25%が出たらひと押し券を渡す・使ったひと押し券を使用済みにする: トリガー
  - 100%の箱: `lottery_open_box`（中身・図鑑の周・日帰り旅行券をサーバーで決める。同じ100%の箱は1回だけ開けられる）
  - 「使った」にする: `lottery_use_coupon`、補助率アップ券: `lottery_use_rate_up`
- トリガーが、引いた時刻をサーバーの時刻にし、**月の回数（日本時間）を超えたら断る**。誕生月は `family_members.birth_date` から+1回
- check制約で、玉と補助率の組み合わせ、補助額の計算（100円単位の丸め）、価格の範囲を守る
- 乱数は端末で振り、**記録してから結果を見せる**。決まりごと（確率・回数・救済・券）は `subsidyLotteryUtils.ts`
  （mobile・PWAで同じ中身。`npm run test:lottery`）
- 月の数え方は端末の時間（日本にいる限りDBの日本時間と同じ）

#### テストモード（確認用。migration 0060）

動作確認のたびに月の回数（2回）を使い切らないための、確認専用の仕組み。ヘルプの枠の下の「テストモード」のスイッチで切り替える
（アプリを開き直すとOFFに戻る）。

- **テストモードは、開発をしている夫（`family_members.relation = 'husband'`）にだけ出す・使える**（2026-10-06）。
  ほかの人にはスイッチを出さず、くじは常に本物として引く（`loadMyLotteryProfile` の `canTest`。画面側の制限）

- ONで引いたくじ・出た券は `is_test = true` で記録し、**本物と完全に別**にする
  - 月の回数に数えない（回数は減らない・何回でも引ける）。履歴・券・救済（確率の計算）もテストだけで数える
  - 家族のお金の集計に入れない。家族の履歴にも出ない（**テストの行は引いた本人にしか見えない**）
  - テストの券は本物のくじに使えず、本物の券もテストに使えない。図鑑（箱・日帰り旅行券）もテストと本物で別に数える
- 確認が済んだら、テストモード中の「テストデータを削除」で、**自分のテストのくじ・券だけ**をまとめて消す
  （関数 `lottery_delete_my_test_data`。本物の行・ほかの人の行には触らない）
- 注意: テストの行は「家族のお金」に出ない約束で成り立つ。補助くじの集計を作るときは、必ず `is_test = false` に絞ること

### 9.8 やめたこと・見送り

| やめたこと | 理由 |
| --- | --- |
| 補助額を0円・1,000円・2,000円・全額にする案 | 安い商品で補助が全額になりやすく、くじの意味が薄いため補助率にした |
| はずれ（0円） | 補助が前提のため |
| 月ごとの家計の合計・精算済みの印 | 履歴はアカウントごとに見るだけでよい（家計との連携は不要） |
| ペア賞 | 夫婦が一緒に引くわけではない |
| 金玉で券（回数）が増える特典 | インパクトが大きすぎる |
| 七福神のコレクション | 古くさい。小さな特典を6つ集める図鑑にした |
| 年間の大当たり表示 | 見るだけで実益がない |
| ひと押し券の欠片制度 | 不要 |
| 応援スタンプ | 押さないと不穏になる |
| 券の繰り越し | 益が大きすぎる。貯福（次の1回の下限が上がる）にした |
| 重みを変えて100%を増やす | 救済で調整する方針 |
