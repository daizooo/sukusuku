# カレンダー機能 仕様

家族で予定を共有するためのカレンダー機能の仕様。

**仕様の正はmobile版（`mobile/`）。** PWA版（`src/`）はmobile版のWEB版（兼開発確認用）
として、この仕様書の更新を追いかけて反映する（ルートの `CLAUDE.md` 参照）。

---

## 1. 予定の入力項目

入力欄はGoogleカレンダーの追加画面にならい、種別（予定/タスク）をまず選ぶ形にしている。
「ゲスト」にあたる欄は、外部の相手を招待する仕組みではなく、家族の誰の予定かを
複数選べる「参加者」にしている（この家族アプリでは招待する相手が常に家族の誰かのため）。
ビデオ会議の追加やカレンダー選択のような、この家族には要らない項目は作っていない。

| 項目 | DBカラム | 内容 |
| --- | --- | --- |
| 種別 | `kind` | **予定(event) / タスク(task)** の2択。タスクは場所・参加者・終わりの時刻を持たない |
| タイトル | `title` | 必須 |
| 日付 | `start_date` | 必須（出生日基準の場合を除く） |
| 時刻 | `start_time` / `end_time` | **予定・タスクとも**任意。未設定なら「終日」。終わりの時刻は予定のみ |
| 繰り返し | `recurrence` | 任意。Googleカレンダーと同じ選択肢（下の「繰り返し」） |
| 参加者 | `participants` | 予定のみ。**大造 / いづみ / 岳** の複数選択（0人以上） |
| 場所 | `place` | 予定のみ。任意。例文のプレースホルダーは置かない |
| 詳細 | `note` | 任意。例文のプレースホルダーは置かない |
| 共有設定 | `is_private` | **共有（家族全員）/ 自分だけ** の2択。既定は共有 |

既存の「カテゴリ」「持ち物」は入力欄の「その他の項目」に折りたたんで残している。

### 繰り返し

Googleカレンダーと同じく、「繰り返し」欄の選択肢から選ぶ。開始日から決まる定番の選択肢と
「カスタム…」の2段構え。

| 選択肢（開始日が2026-10-02の金曜のとき） | 保存される中身 |
| --- | --- |
| 繰り返さない | `null` |
| 毎日 | `freq: daily, interval: 1` |
| 毎週 金曜日 | `freq: weekly, byWeekday: [5]` |
| 毎月 第1金曜日 | `freq: monthly, byNthWeekday: {nth: 1, weekday: 5}`（第5週は `nth: -1` ＝最終） |
| 毎年 10月2日 | `freq: yearly` |
| 毎週平日（月〜金） | `freq: weekly, byWeekday: [1,2,3,4,5]` |
| カスタム… | 下の「カスタムの繰り返し」の画面で決める |

- 開始日を変えると、定番の選択肢を選んでいた場合は新しい日付の曜日・日付に合わせ直す
  （カスタムはそのまま）
- 定番に当たらない設定は、欄に要約（例:「毎週 金・土曜日」）を1行足して出す
- **カスタムの繰り返し**（別画面。「完了」で反映、「キャンセル」で捨てる）:
  繰り返す間隔（数＋単位: 日ごと／週間ごと／か月ごと／年ごと）→
  曜日（週間ごと。複数選べる。最後の1つは外せない）→
  毎月の数え方（か月ごと。「毎月 2日」か「毎月 第1金曜日」。月末の週は「最終金曜日」も出る）→
  終了日（なし／終了日を指定／回数を指定）
- 毎月・毎年の「何日か」は開始日から決まるので保存しない
- 日付が決まらない「生後日数で指定」のタスクには繰り返しを持たせない（欄を出さない）

#### 繰り返しの展開

繰り返す予定・タスクは、DBには1件（元の予定）のまま持ち、**表示するたびにルールから回ごとの日付を
計算して**カレンダーに並べる（回ごとの行は作らない）。計算は `recurrenceExpand.ts`
（`npm run test:recurrence`）、画面への展開は `scheduleExpand.ts` の `expandOccurrences`。

- 数え方はGoogleカレンダーと同じ:
  - ルールに当てはまる日を、開始日以降で数える。開始日自体がルールに当てはまらない
    （開始日が金曜で「毎週 月曜」など）ときは、最初の回は開始日の次の月曜になる
  - 毎月の31日・毎年の2月29日のように、その月・年に無い日の回は飛ばす
  - 「2週間ごと」などは、開始日を含む週（日曜始まり）を1週目として数える
  - 終了は 終了日（その日を含む）／回数（開始日以降に数えた最初のn回）／なし
- 画面ごとに展開する範囲が違う:
  - 月 — マスに出る範囲（前後の月の日を含めて最大6週）
  - 日 — 選んでいる日
  - 直近のスケジュール・リスト — 今日から366日先まで。**過ぎた回は期限切れにも完了済みにも並べない**
    （毎日の予定が過去ぶん全部「期限切れ」になるのを避ける。過ぎた回は月・日で見返せる）
- **完了は回ごと。** 繰り返す予定は `done_dates`（完了にした回の日付の配列）に回の日付が入って
  いるかで決まる。`is_done` は使わず false のまま。繰り返さない予定は今までどおり `is_done`
- **編集・削除は全部の回に効く。** 開いているのは1回ぶんだが、直すのは元の予定
  （詳細・編集画面にその旨を出す）。「この回だけ」「これ以降」の変更はまだ無い
- 日付や繰り返しを直して保存すると、開いていた回が無くなることがあるので、詳細は閉じる
- 回の見分けは `occurrenceKey`（`<id>@<日付>`。繰り返さないものは id）。`id` は元の予定のまま

### 参加者（旧ラベル）

以前は「パパ/ママ/家族」という役割の単一選択（`assignee`）だったが、
実際の名前を複数選べる「参加者」（`participants`、text[]）に一本化した
（`0039_task_participants_kind.sql`）。

- パパ → **大造** / ママ → **いづみ** / 家族（3人まとめて） → **岳**（子）
- 一覧・月表示での色分けは、参加者がちょうど1人のときだけその人の色にし、
  0人または複数のときは既定の色にする（`getParticipantsTone`）
- 参加者での絞り込みは、月表示で全体を見渡せるため持たない（2026-09-30に廃止）

### 共有設定

「自分だけ」にした予定・タスクは、作成した本人以外の家族には表示されない
（`0040_task_privacy.sql`）。

- DBには `created_by`（作成者）・`is_private`（自分だけ）の2列を持つ
- 表示の制御はアプリ側の絞り込みではなく **RLS（行レベルセキュリティ）** で行う。
  `is_private = true` の行は `created_by = auth.uid()` の人にしか select できない
  （参照・更新・削除いずれも）
- **通知も作成者の端末だけ。** 通知を送るEdge Functionは `service_role` で動きRLSが効かないため、
  宛先を自前で絞る（`_shared/reminderRecipients.ts`）。「自分だけ」の予定・タスクは
  `push_subscriptions.user_id = created_by` の端末にだけ送り、作成者が分からない（ユーザー削除で
  `created_by` が null）ときは誰にも送らない。通知にタイトルと場所が入るため、全端末へ送ると
  他の家族に中身が見えてしまう（`0051` で直した。それまでは家族全員に届いていた）
- 既定は共有（`is_private = false`）。既存の予定・タスクはすべて共有のまま
- 共有・自分だけの2択のみで、特定の相手を選んで共有する仕組みは持たない

## 2. 日付の決まり方の2種類

これは前節の「種別(kind: 予定/タスク)」とは別の軸で、日付の決まり方で2種類に分かれる。
`anchor_type` で区別する。

| 種類 | `anchor_type` | 日付の決まり方 |
| --- | --- | --- |
| 日付指定 | `absolute` | `start_date` を直接指定する |
| 出生日基準 | `birth_relative` | `子の誕生日 + days_after_birth` で決まる |

- 出生届や健診など、出生日を起点に時期が決まる予定のために `birth_relative` を残している。
- **出生日が未登録のときだけ**、入力欄に「生後日数で指定」の選択肢が出る。
  登録済みの場合は日付指定に一本化される。
- 誕生日は設定タブ（`family_profiles` の `child_fields`）に保存される。
  誕生日を変更すると出生日基準の予定の日付がまとめて追随する。
- 出生日基準の予定の日付解決は**クライアント側**（`SukusukuApp` の `dynamicTodos`）で行う。
  誕生日が jsonb に入っているためSQLからは引きにくく、
  予定は全件まとめて読み込むため日付での絞り込みも不要なため。
  `start_date` カラムは日付指定（`absolute`）の予定でのみ使う。

## 3. 画面

### スケジュールタブ

カレンダーを主役に置き、**月 / 日 / リスト**の3つの面を持つ。既定は月。
上に「月・週・日・リスト」の切り替えの帯や担当の絞り込みは置かない（縦の高さをカレンダーと
直近のスケジュールに回すため）。面の移り方は次のとおり。

- 月 → 日: 月グリッドの日付の数字をタップ（マスの予定の無いところは予定の追加）
- 月 → リスト: 「直近のスケジュール」の見出し（または期限切れの件数）をタップ
- 日・リスト → 月: 左上の戻るボタン（矢印のみ。文言は付けない）。ブラウザ・スマホの戻る操作でも月へ戻る
- 週表示は持たない（リストで足りるため）

- **月表示**（既定） — 月グリッド。前後の月の日も含めて週単位で埋める
  - **押したところで動きが分かれる**（Googleカレンダーと同じ）:
    日付の数字 → その日の日表示／予定のチップ → 予定の詳細／**それ以外のマスの中
    （予定の無いところ） → その日を初期値にした予定・タスクの追加**。
    **手触りは予定と空きで逆**（Googleカレンダーと同じ）: 予定のチップ・日付の数字・予定の行
    （直近のスケジュール・リスト・日表示）は、触れている間（PWA版はカーソルを合わせたときも、
    カーソルが指の形になり）色が変わる。予定の無いマスの中・「予定はありません」の枠は、
    カーソルは矢印のまま色も変えない（押すと追加が開く）
  - 予定はタイトル入りのチップで積む。1マスに2件まで出し、超えたぶんは `+n件`。
    下に「直近のスケジュール」が並ぶぶんマスが低くなるため、2件入らない高さのマスは
    出す件数を減らして `+n件` に寄せる（`MonthView` の `chipsThatFit`）
  - 完了した予定はグレーの取り消し線
  - **育児記録はここには出さない**。月表示は予定を見渡すための面で、記録は日をタップした先で見る
  - 日付の数字をタップすると日表示へ移る。チップをタップすると予定の詳細が開く
  - 生後日数の節目（生後7/30/50/100/180日・月齢・誕生日）を日付の下に小さく出す
  - 予定のない月では「次に予定がある月へ」で空の月を飛ばせる
  - **カレンダーの下に「直近のスケジュール」を置く**（以前はホームタブにあった）。
    高さはカレンダー 5 : 直近のスケジュール 3 で分け、上の帯をなくして空いた高さも
    この比でどちらにも回る。一覧は画面の中に収め、あふれた分はその中だけでスクロールする
    - 今日以降の未完了の**予定**（種別が「予定」のもの。タスクは出さない）を近い順（同じ日なら時刻順）に最大10件
    - 各行は 日付・タイトル・場所・主催者 の列で、列の幅をそろえて並べる（時刻は一覧では出さず、詳細で見る）
      - 日付は2段で、上に年（小さく薄く）、下に「10/19(月)」（青の太字）。「あと3日」のような日数は出さない
      - タイトルは濃い色の太め、場所は小さく薄い色（あるときだけタイトルの下に出す）
      - 主催者は主体(owner)の名前を色付きの札で出す
        （主体が未設定の古い予定は、参加者が1人のときだけその人）
    - 期限切れは件数だけ見出しに出し、押すとリスト表示へ移る（中身は並べない）
    - **見出しをタップするとリスト表示へ移る**（旧「すべて見る」）。行のチェックで完了にでき、行をタップすると詳細が開く
    - 予定の追加ボタンは、右下の丸いボタンだと一覧の右下に重なって隠すため、
      月表示だけはこの見出しの中の小さなボタンにしている（他の表示は右下のまま）
- **日表示** — その日の予定と育児記録を合わせて見る面
  - 記録は閲覧のみ。追加・編集は「記録タブで開く」から記録タブで行う
    （同じ入力導線を2か所に置かない）
  - 「この日に追加」でその日を初期値にした予定の追加ができる。予定が無いときの
    「予定はありません」の枠を押しても同じ
- **リスト表示** — 日付順（同じ日なら時刻順、終日が先）に全件を並べる
  - 誕生日が未登録で日付が確定しない予定は「日付未定」として末尾にまとめる
- 月表示で全体を見渡せるため、参加者による絞り込みは持たない
- 月・日はネイティブのピッカーで任意の月日へ直接ジャンプできる

### 育児記録の取得範囲

記録は日数が経つほど増えるため、**表示中の範囲だけ**を取りに行く（`listCareLogsInRange`）。

- 月表示・リスト表示 — 記録を出さないため問い合わせない
- 日表示 — その1日分
- これから来る日には記録が存在しないため、未来だけの範囲も問い合わせない
- 記録タブが持つ1日分の一覧とは表示範囲が違うため、状態は別に持つ。
  記録を追加・更新・削除したときはカレンダー側の取得済みの印を落として取り直す

### 予定の詳細・編集

日付・時刻・場所・参加者・繰り返し・詳細を表示（タスクは場所・参加者を持たない。時刻は持てる）。
編集は追加と同じ入力欄を使う。

## 4. 日付の扱い

- **`date` + `time` で保持する**（`timestamptz` は使わない）。
  終日予定を `timestamptz` にするとタイムゾーン起因で日付が1日ずれるため。
  家族全員が同一タイムゾーンにいる前提。
- `'YYYY-MM-DD'` のパースは `parseDateString()` を通す。
  `new Date('2026-08-15')` は UTC 深夜として解釈されるため直接使わない。

## 5. 通知

**予定・タスクとも、設定した日時に必ず通知する。** リマインダー（何分前か）の設定は
持たない（2026-10-02に廃止。以前は 通知しない／予定の時刻／10分前／30分前／1時間前／
前日／2日前 から選べた）。

- 時刻を決めたものはその時刻に、時刻が無い（終日の）ものは 09:00 に届く
- 通知時刻は `start_date` + `start_time` から決める（`remind_minutes_before` 列は見ない。
  `0049_task_notify_at_set_time.sql`）
- 完了にしたものは通知しない。**繰り返す予定は、完了にした回だけ通知しない**
- **繰り返す予定は回ごとに通知する。** 日付指定で繰り返すものは `task_reminder_schedule` ビューが
  返さず（`0050_task_recurrence_expansion.sql`）、Edge Function `send-reminders` がルールを展開して
  通知する回を求める（`_shared/recurringReminders.ts`、`npm run test:recurring-reminders`）。
  二重送信は今までどおり `reminder_deliveries` の一意制約（予定・端末・通知時刻）で防ぐ

配信は Supabase Edge Function `send-reminders` が行う（`pg_cron` が1分おきに呼び、
通知時刻を過ぎた予定をその家族の全端末へ送る）。
仕組みと初回セットアップの手順は [notifications.md](./notifications.md) を参照。

## 6. マイグレーション

`supabase/migrations/0010_calendar_fields.sql` で以下を適用済み。

- `start_date` / `start_time` / `end_time` / `anchor_type` / `remind_minutes_before` を追加
- 既存の予定は `days_after_birth` から作られているため `anchor_type = 'birth_relative'` に設定
- ラベルの旧値 `'二人で'` `'未定'` を `'家族'` へ移行
- `has_notification = true` の予定を `remind_minutes_before = 1440`（前日）へ移行
- `(family_id, start_date)` のインデックス追加

### 後片付け

`has_notification` カラムの削除と、ラベルの `check` 制約を3値へ絞る作業は
`0011_drop_has_notification.sql` に分けてある。

0010 の時点では「マージ後に削除する」としていたが、0010 のコードは
カラムが残っている間の整合のため `has_notification` を明示的に書き込んでいた。
そのため 0011 は、**書き込みを外したコードが本番にデプロイされた後**でないと適用できない
（適用が先だと本番の予定の追加・更新が失敗する）。書き込みを外す変更は
リマインダー配信のPRに含めてある。

### リマインダー配信のマイグレーション

- `0012_push_notifications.sql` — 購読情報・送信済み記録・通知時刻のビュー
- `0013_reminder_cron.sql` — `pg_cron` による定期実行の登録

> **未実施（2026-10-09時点）:** `tasks.remind_minutes_before` 列の削除。本番DBに列が残り、`api/tasks.ts`（mobile・PWA）が今も参照している。
> 旧APK・旧Web版が使われなくなったことを確かめてから、参照を外して別のmigrationで消す。繰り返しの「この回だけ」「これ以降」の変更も未実装。残りの一覧は [remaining-work.md](./remaining-work.md)。

### 参加者・種別のマイグレーション

`0039_task_participants_kind.sql` で以下を追加。

- `participants`（text[]）・`kind`（'event' | 'task'、既定 'event'）を追加
- 既存の `assignee`（パパ/ママ/家族）を `participants`（大造/いづみ/岳）へ移行
- `assignee` カラムを削除

参加者・種別を読み書きする新しいAPKを両端末に入れ終え、**Web版（`src/`、Vercel）も
同じ新形式のコードをデプロイしてから**適用すること（旧APK・旧Web版が動いている間に
適用すると、そこからの予定の追加・更新が失敗する）。逆に、新形式のWeb版は適用前の
DBに対しては予定の追加・更新が失敗するので、**適用とWeb版のデプロイはできるだけ
続けて行う**。0039〜0042はまとめて適用する。

### 共有設定のマイグレーション

`0040_task_privacy.sql` で以下を追加。

- `created_by`（uuid、`users.id` 参照）・`is_private`（boolean、既定 false）を追加
- 1つだった `tasks_family_all`（全操作共通）ポリシーを select/insert/update/delete
  ごとに分け、select・update・delete には
  `not is_private or created_by = auth.uid()` の判定を追加

### 通知を「設定した日時に必ず」へ一本化するマイグレーション

`0049_task_notify_at_set_time.sql` で以下を行う。

- 既存の予定・タスクの `remind_minutes_before` をすべて 0 にそろえ、列の既定値も 0 にする
- `task_reminder_schedule` ビューを作り直し、`remind_minutes_before` を見ずに
  `remind_at` を予定の日時そのものにする（通知なし(null)の行も対象になる）
- 列は**消さない**。まだ列へ書き込む旧版（旧APK・旧Web版）が動いている間に消すと、
  そこからの予定の追加・更新が失敗する。ビューが値を見ないので、旧版が null や「前日」を
  書いても通知時刻は変わらない。そのためこのマイグレーションは**新版のデプロイの前後どちらで
  適用してもよい**。列は旧版が使われなくなったあとの別のマイグレーションで消す

### 繰り返しの展開のマイグレーション

`0050_task_recurrence_expansion.sql` で以下を行う。

- `done_dates`（date[]、既定 空）を追加。繰り返す予定で、完了にした回の日付を持つ
- `task_reminder_schedule` ビューを、日付指定で繰り返す予定・タスクを返さないように作り直す
  （回ごとの通知は Edge Function が担当する）

**適用の順序: 先に Edge Function `send-reminders` をデプロイし、そのあとに適用する。**
関数は `done_dates` が無い間、繰り返す予定だけを読み飛ばす（ビューは変えていないので、
繰り返す予定も開始日の1回ぶんは今までどおり届く）。適用した瞬間から関数が回ごとの通知を
担当し、ビューは外れるので、通知の空白も二重も起きない。逆の順序だと、関数をデプロイする
までの間、繰り返す予定は通知されない。

新しい画面は、適用の前だと回ごとの完了の保存に失敗する（元に戻って警告が出るだけ）ため、
アプリの配布と続けて適用する。

### 「自分だけ」の通知のマイグレーション

`0051_task_reminder_schedule_privacy.sql` で、`task_reminder_schedule` ビューの末尾に
`is_private` と `created_by` を足す（Edge Function が宛先を作成者の端末に絞るのに使う）。

**適用の順序: 先にこれを適用し、そのあとに Edge Function `send-reminders` をデプロイする。**
旧い関数は足した列を読まないだけなので、適用しても通知は今までどおり届く。関数を先に出すと、
列が無い間は「自分だけ」の判定ができず全員に届いてしまう。繰り返す予定の通知は `tasks` から
直接読むため、関数のデプロイだけで絞られる。
