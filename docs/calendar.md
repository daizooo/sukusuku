# カレンダー機能 仕様

家族で予定を共有するためのカレンダー機能の仕様。

**対象はmobile版（`mobile/`）のみ。** PWA版（`src/`）は凍結中で、この仕様書の
更新をPWA版に反映する必要はない（docs/native-app-rewrite.md参照）。

---

## 1. 予定の入力項目

入力欄はGoogleカレンダーの追加画面にならい、種別（予定/タスク）をまず選ぶ形にしている。
「ゲスト」にあたる欄は、外部の相手を招待する仕組みではなく、家族の誰の予定かを
複数選べる「参加者」にしている（この家族アプリでは招待する相手が常に家族の誰かのため）。
ビデオ会議の追加やカレンダー選択のような、この家族には要らない項目は作っていない。

| 項目 | DBカラム | 内容 |
| --- | --- | --- |
| 種別 | `kind` | **予定(event) / タスク(task)** の2択。タスクは場所・参加者・時刻を持たない |
| タイトル | `title` | 必須 |
| 日付 | `start_date` | 必須（出生日基準の場合を除く） |
| 時刻 | `start_time` / `end_time` | 予定のみ。任意。未設定なら「終日」 |
| 参加者 | `participants` | 予定のみ。**大造 / いづみ / 岳** の複数選択（0人以上） |
| 場所 | `place` | 予定のみ。任意。例文のプレースホルダーは置かない |
| 詳細 | `note` | 任意。例文のプレースホルダーは置かない |
| リマインダー | `remind_minutes_before` | 予定の何分前に通知するか。null は通知なし |

既存の「カテゴリ」「持ち物」は入力欄の「その他の項目」に折りたたんで残している。

### 参加者（旧ラベル）

以前は「パパ/ママ/家族」という役割の単一選択（`assignee`）だったが、
実際の名前を複数選べる「参加者」（`participants`、text[]）に一本化した
（`0039_task_participants_kind.sql`）。

- パパ → **大造** / ママ → **いづみ** / 家族（3人まとめて） → **岳**（子）
- 一覧・月表示での色分けは、参加者がちょうど1人のときだけその人の色にし、
  0人または複数のときは既定の色にする（`getParticipantsTone`）
- 担当での絞り込み（すべて / 大造 / いづみ / 岳）は、選んだ人が参加者に
  含まれる予定・タスクを表示する

## 2. 日付の決まり方の2種類

これは前節の「種別(kind: 予定/タスク)」とは別の軸で、日付の決まり方で2種類に分かれる。
`anchor_type` で区別する。

| 種類 | `anchor_type` | 日付の決まり方 |
| --- | --- | --- |
| 日付指定 | `absolute` | `start_date` を直接指定する |
| 出生日基準 | `birth_relative` | `子の誕生日 + days_after_birth` で決まる |

- 出生届や健診など、出生日を起点に時期が決まる予定のために `birth_relative` を残している。
- **出生日が未登録のときだけ**、入力欄に「生後日数で指定」の選択肢が出る。
  登録済みの場合は日付指定に一本化される。
- 誕生日は設定タブ（`family_profiles` の `child_fields`）に保存される。
  誕生日を変更すると出生日基準の予定の日付がまとめて追随する。
- 出生日基準の予定の日付解決は**クライアント側**（`SukusukuApp` の `dynamicTodos`）で行う。
  誕生日が jsonb に入っているためSQLからは引きにくく、
  予定は全件まとめて読み込むため日付での絞り込みも不要なため。
  `start_date` カラムは日付指定（`absolute`）の予定でのみ使う。

## 3. 画面

### スケジュールタブ

カレンダーを主役に置き、**月 / 週 / 日 / リスト**の4つの面を切り替える。既定は月。

- **月表示**（既定） — 月グリッド。前後の月の日も含めて週単位で埋める
  - 予定はタイトル入りのチップで積む。1マスに3件まで出し、超えたぶんは `+n件`
  - 完了した予定はグレーの取り消し線
  - **育児記録はここには出さない**。月表示は予定を見渡すための面で、記録は日をタップした先で見る
  - 日をタップすると日表示へ移る。チップをタップすると予定の詳細が開く
  - 生後日数の節目（生後7/30/50/100/180日・月齢・誕生日）を日付の下に小さく出す
  - 予定のない月では「次に予定がある月へ」で空の月を飛ばせる
- **週表示** — 7日分を縦に並べる。各日の予定と、その日の育児記録の合計を1行で出す
- **日表示** — その日の予定と育児記録を合わせて見る面
  - 記録は閲覧のみ。追加・編集は「記録タブで開く」から記録タブで行う
    （同じ入力導線を2か所に置かない）
  - 「この日に追加」でその日を初期値にした予定の追加ができる
- **リスト表示** — 日付順（同じ日なら時刻順、終日が先）に全件を並べる
  - 誕生日が未登録で日付が確定しない予定は「日付未定」として末尾にまとめる
- 参加者による絞り込み（すべて / 大造 / いづみ / 岳）は全表示で共通
- 月・日はネイティブのピッカーで任意の月日へ直接ジャンプできる

### 育児記録の取得範囲

記録は日数が経つほど増えるため、**表示中の範囲だけ**を取りに行く（`listCareLogsInRange`）。

- 月表示・リスト表示 — 記録を出さないため問い合わせない
- 週表示 — その週の7日分 / 日表示 — その1日分
- これから来る日には記録が存在しないため、未来だけの範囲も問い合わせない
- 記録タブが持つ1日分の一覧とは表示範囲が違うため、状態は別に持つ。
  記録を追加・更新・削除したときはカレンダー側の取得済みの印を落として取り直す

### 予定の詳細・編集

日付・時刻・場所・参加者・リマインダー・詳細を表示（タスクは時刻・場所・参加者を持たない）。
編集は追加と同じ入力欄を使う。

## 4. 日付の扱い

- **`date` + `time` で保持する**（`timestamptz` は使わない）。
  終日予定を `timestamptz` にするとタイムゾーン起因で日付が1日ずれるため。
  家族全員が同一タイムゾーンにいる前提。
- `'YYYY-MM-DD'` のパースは `parseDateString()` を通す。
  `new Date('2026-08-15')` は UTC 深夜として解釈されるため直接使わない。

## 5. リマインダー

選択肢は 通知しない / 予定の時刻 / 10分前 / 30分前 / 1時間前 / 前日 / 2日前。

配信は Service Worker + Web Push で行う。`pg_cron` が5分おきに Supabase Edge Function
`send-reminders` を呼び、通知時刻を過ぎた予定をその家族の全端末へ送る。
仕組みと初回セットアップの手順は [notifications.md](./notifications.md) を参照。

終日予定は 09:00 を予定時刻とみなすため、「前日」を選ぶと前日の 09:00 に届く。

## 6. マイグレーション

`supabase/migrations/0010_calendar_fields.sql` で以下を適用済み。

- `start_date` / `start_time` / `end_time` / `anchor_type` / `remind_minutes_before` を追加
- 既存の予定は `days_after_birth` から作られているため `anchor_type = 'birth_relative'` に設定
- ラベルの旧値 `'二人で'` `'未定'` を `'家族'` へ移行
- `has_notification = true` の予定を `remind_minutes_before = 1440`（前日）へ移行
- `(family_id, start_date)` のインデックス追加

### 後片付け

`has_notification` カラムの削除と、ラベルの `check` 制約を3値へ絞る作業は
`0011_drop_has_notification.sql` に分けてある。

0010 の時点では「マージ後に削除する」としていたが、0010 のコードは
カラムが残っている間の整合のため `has_notification` を明示的に書き込んでいた。
そのため 0011 は、**書き込みを外したコードが本番にデプロイされた後**でないと適用できない
（適用が先だと本番の予定の追加・更新が失敗する）。書き込みを外す変更は
リマインダー配信のPRに含めてある。

### リマインダー配信のマイグレーション

- `0012_push_notifications.sql` — 購読情報・送信済み記録・通知時刻のビュー
- `0013_reminder_cron.sql` — `pg_cron` による定期実行の登録

### 参加者・種別のマイグレーション

`0039_task_participants_kind.sql` で以下を追加。

- `participants`（text[]）・`kind`（'event' | 'task'、既定 'event'）を追加
- 既存の `assignee`（パパ/ママ/家族）を `participants`（大造/いづみ/岳）へ移行
- `assignee` カラムを削除

参加者・種別を読み書きする新しいAPKを両端末に入れ終えてから適用すること
（旧APKが動いている間に適用すると、旧APKからの予定の追加・更新が失敗する）。
