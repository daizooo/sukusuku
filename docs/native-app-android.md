# Android版ネイティブアプリの設計（Capacitor）

[ネイティブアプリ化の検討](./native-app.md)で残していた案Bを、**Androidだけ**に絞って
具体化した設計メモ。実装の前に、作る順番と落とし穴を先に洗い出しておく。

> **この案は採らないことにした（2026-08-24）。** 殻がPWAを開くだけでは
> 「設計そのものがネイティブになっていない」ため、画面ごと作り直す案Dへ進む。
> 進め方は [ネイティブへ作り直す](./native-app-rewrite.md) を参照。
> このメモは、WebViewにWeb Pushが無いこと（§2）や、Androidで鳴らし分けを
> 保つやり方（§3の案②）など**作り直しでもそのまま使える調べ**を含むので残す。

## 決めたこと（前提）

- **Androidだけ作る。** iPhoneは当面いまのPWAのまま。
  → Apple Developer Program 年$99 も iOSビルド用のMacも要らなくなる。
- **ストアには出さない。** `.apk` を自分たちの端末に直接入れる。審査も登録も無い。
- **画面は書き直さない。** 殻がVercel上の今のアプリをWebViewで開く（リモートURL方式）。
- **いまのPWAはこれ以上更新しない。** 今後の作り込みはネイティブ側に置く。
  ただし出来上がっている画面は**ネイティブ化で活用する**（だから書き直さない）。
- **目的は「授乳アラームを確実に鳴らす」の一点。** それ以外は今のままで足りている。

いま通知を登録している端末はAndroid 2台とMac 1台で、主に使うのはAndroidの2台。
いちばん困っている授乳アラームがAndroidで直れば用は足りる。

---

## 1. 全体の形

```
[Androidの殻(Capacitor)]
  ├ WebView ──→ https://<Vercelのアプリ>   ← 画面は今のまま。1行も書き直さない
  │                    │
  │                    │ ネイティブ判定して呼び分ける
  │                    ↓
  └ ネイティブ側 ← 授乳の計測の開始/切り替え/停止
       └ 鳴らす時刻をOSに預ける → 画面が消えていても・アプリを閉じていても・圏外でも鳴る
```

いまWeb側でやっている回避策（Screen Wake Lockで画面を消させない、裏に回っている間の
取りこぼしを戻ってきたときに鳴らし直す、サーバーに予約してWeb Pushで鳴らす）は、
**Androidの殻の中では全部要らなくなる**。

---

## 2. 最大の落とし穴 — WebViewにはWeb Pushが無い

Android System WebView は Service Worker こそ動くが、**Push API と Notification API を
持っていない**。つまり殻の中で開いたアプリには、いま作ってある通知が**1つも届かない**。

| 通知 | いまの仕組み | 殻の中では |
| --- | --- | --- |
| 予定のリマインダー | Web Push (`send-reminders`) | **届かない** |
| 次の授乳の目安 | Web Push (`send-feeding-reminders`) | **届かない** |
| 授乳の経過時間お知らせ | Web Push (`send-nursing-alarms`) | 届かない（ネイティブで置き換える） |

これは案Bの隠れたコストとして[検討メモ](./native-app.md)の§4-1に書いてあったもので、
Androidに絞っても消えない。そこで段階を分ける。

### 段階1 — 授乳アラームだけネイティブにする

殻は「授乳中に使うもの」と割り切り、予定のリマインダーと次の授乳の目安は
**当面ホーム画面のPWA側で受ける**。端末には殻とPWAの2つが並ぶ。

- 良い点: サーバー側を一切触らない。作る量が最小で、効果はいちばん大きいところに出る
- 悪い点: アイコンが2つ並ぶ。どちらから開いたかで通知の届き方が違う、という
  分かりにくさが残る

### 段階2 — 通知をFCMへ移して殻1本にする

予定のリマインダーと次の授乳の目安をFCMへ移し、PWAを畳む。

- 端末トークンのテーブル（いまの `push_subscriptions` はWeb Push購読専用）
- `send-reminders` / `send-feeding-reminders` に FCM HTTP v1 の送信経路を追加
  （`_shared/webpush.ts` のVAPID署名はそのまま残し、宛先の種類で分岐）
- Firebaseプロジェクトの用意

**いまのPWAをこれ以上更新しない以上、通知の受け皿としてPWAを残し続けるのは中途半端**
なので、段階2は「余裕があれば」ではなく**行き先**として置いておく。
ただし段階2で触るのはSupabase側（Edge Functionとテーブル）で、画面のコードではない。

段階2まで進んだら、授乳のお知らせのWeb Push（`nursing_alarms`・1分おきのcron・
`send-nursing-alarms`）は役目が終わるので、そこで片付ける。

> **実機で最初に確かめること**: 殻の中で `'PushManager' in window` と
> `'Notification' in window` が本当に `false` になるか。
> ここが `true` なら段階2は丸ごと不要になるので、真っ先に潰しておく。

## 3. 授乳アラームをどう鳴らすか（本題）

いまの仕組みの肝は「**短い『ピッ』1回＝5分、長い『ポーン』1回＝30分**」で、
画面を見ずに鳴り方だけで経過時間が分かること（`src/lib/alarm.ts`）。
ネイティブ化の目的は、これを**保ったまま確実に鳴らす**ことにある。
Androidでのやり方は2つある。

| | 案① ローカル通知を並べて予約 | 案② 授乳中だけ前面サービスを動かす |
| --- | --- | --- |
| 中身 | `@capacitor/local-notifications` で鳴らす時刻ぶんの通知を予約 | 常駐通知を出すサービスの中で、自前のコードが時刻を見て鳴らす |
| 鳴らし分け | **チャンネルを分ければ可能**（後述の無理がある） | **そのまま再現できる**（音の合成もファイルも自由） |
| 時刻の正確さ | `USE_EXACT_ALARM` を宣言すれば正確 | 正確（自分のプロセスの中で数える） |
| アプリを閉じても鳴るか | ○ | ○（サービスが生きている） |
| 圏外でも鳴るか | ○ | ○ |
| マナーモード | 鳴らない | 鳴らせる（音声属性をアラーム扱いにできる） |
| 経過時間の常時表示 | できない | **常駐通知に「授乳 12分 左」と出せる** |
| Kotlinを書くか | 書かない（プラグインだけ） | 小さなプラグインを書く（Service + 通知 + 音） |

### 案①に出てくる無理

Android 8以降、**通知の音と振動パターンは「通知チャンネル」に固定される**。
通知1件ごとには変えられず、チャンネルは作ったあとに音を変えられない。
つまり長短の鳴らし分けを保つには、**鳴らし方のパターンの数だけチャンネルが要る**。

5分間隔・90分ぶんなら18通り（5分, 10分, …, 90分）。端末の「通知」設定に
チャンネルが18個並ぶことになり、明らかにやりすぎ。
チャンネルを1つに畳むと、鳴り方は全部同じになり、経過時間は通知の文言でしか分からない
＝ **いまのWeb Pushでの妥協（[notifications.md](./notifications.md) §6）と同じところへ戻る**。
それならネイティブにする意味が薄い。

### 案②を推す

ネイティブ化の理由が「鳴らし分けを保ったまま確実に鳴らす」ことなので、
そこを満たせるのは案②だけ。あわせて、

- 常駐通知に経過時間を出せるので、**音を聞き逃しても通知バーを見れば分かる**
- 授乳を止め忘れても常駐通知が目に入るので、[Web Push側で入れた90分の打ち切り](./notifications.md)
  のような後始末が要らない
- 端末内で完結するため、`nursing_alarms`・cron・Edge Function を経由しない
  （＝1分おきのcronも、20〜80秒の遅れも無くなる）

書く量は「授乳中だけ動くサービス1つ」ぶんで、画面は一切関係しない。
案①を先に作っても、チャンネル設計は案②では丸ごと捨てることになるので、
**最初から案②で作るほうが結果的に短い**。

### 案②の中身

```
[Web] 左/右をタップ
  └ Capacitor経由で startNursing({ side, baselineAt, intervalMinutes }) を呼ぶ
        └ 前面サービス開始 → 常駐通知「授乳 0分 左」
             └ 区切りごとに
                  ├ 音を鳴らす（長音=30分・短音=5分。res/raw の音か、その場で合成）
                  ├ 振動させる（長短のパターン）
                  └ 常駐通知の文言を更新
[Web] 左右の切り替え → updateNursing({ side, baselineAt })
[Web] 停止・記録の保存 → stopNursing() → サービス終了・常駐通知も消える
```

- 端末の**バッテリー最適化の除外**を1回設定しておく（設定 > アプリ > 電池 > 制限しない）。
  前面サービスは強い部類だが、機種によっては切られることがある
- 音は `AudioAttributes` を `USAGE_ALARM` にしておくと、マナーモードでも鳴る。
  夜中に鳴らすものなので、音量は端末のアラーム音量に乗る形が望ましい
- 「音を鳴らす」の長短の組み立ては、いまの `src/lib/alarm.ts` の規則をそのまま持っていく
  （長音＝30分・短音＝5分。この意味は体で覚えている部分なので変えない）

## 4. Web側との境目 — どこまで触るか

いまのPWAはこれ以上更新しない前提なので、Web側に入れる変更は
**ネイティブとつなぐための橋渡しだけ**に絞る。やり方は2つある。

### 案A — 橋渡しだけWeb側に入れる（推奨）

- **`@capacitor/core` と使うプラグインのJSを、今のNext.jsのバンドルに入れる。**
  リモートURL方式では、Capacitorが `capacitor.js` を差し込む経路（端末内のローカル配信）を
  通らないため、Web側が自分で持っている必要がある。
  ネイティブかどうかは `Capacitor.isNativePlatform()` で分かる
  （中身は `window.androidBridge` があるかどうかの判定なので、ブラウザでは常に `false`）。
- **`src/lib/nursingTimer.ts` の「鳴らす」ところを差し替え口にする。**
  いまは `fireAlarm()` が音とバイブを直に鳴らしているので、そこを
  「ネイティブならネイティブへ預ける / ブラウザなら今のまま」に分岐させる。
  計測そのもの（localStorage）と画面はそのまま使える。
- **ネイティブで動いているときは `nursing_alarms` に預けない。**
  預けると、ネイティブと Web Push の両方から鳴って二重になる
  （`src/lib/nursingAlarmSync.ts` の入口で `isNativePlatform()` なら何もしない）。
- **Screen Wake Lock を取らない。** ネイティブでは画面を点けておく必要がないので、
  そのぶんバッテリーが浮く。

どれも「ネイティブでないときは今と同じ」に倒せるので、**PWAの動きは何も変わらない**。
そして**Web側に触るのはこの一度きり**で、以降はネイティブ側だけを育てていける。

### 案B — Web側を一切触らない

ネイティブが WebView 越しに `localStorage` の `sukusuku:activeNursing` を読み、
計測の開始・左右の切り替え・停止を自分で見つける（`evaluateJavascript` で数秒おきに覗く）。

- 良い点: Web側の変更もデプロイもゼロ。凍結したまま使える
- 悪い点:
  - 画面の内部の持ち方（キー名とJSONの形）に張り付くので、将来Web側を直したときに黙って壊れる
  - 数秒おきの覗き見ぶん、計測の開始・停止の反映が遅れる
  - 二重に鳴るのを止める手当てが効かないので、**殻を使う端末では通知をオフにする**運用が要る
    （オフにすると、いまPWA側で受けている予定のリマインダーも受け取れなくなる）

**案Aを推す。** 一度だけWeb側を触ればあとは触らずに済み、案Bに残る壊れやすさと
「通知オフ」の運用を抱えずに済む。凍結の趣旨は「これ以上機能を足さない」ことであって、
ネイティブへ渡すための継ぎ手を1回入れることとは矛盾しない。

## 5. 殻そのものの構成

```ts
// capacitor.config.ts（案）
const config: CapacitorConfig = {
  appId: 'com.example.sukusuku',   // 端末内で一意ならよい（ストアに出さないため）
  appName: 'すくすく手帳',
  webDir: 'public',                // リモートURL方式では実質使わないが必須
  server: {
    url: 'https://<Vercelのアプリ>',
    androidScheme: 'https',
  },
};
```

- **起動にネットワークが要る。** 圏外だと殻は白紙になる（アラームはサービス側なので鳴る）。
- **Vercelのデプロイ保護**が有効だと、殻から開いたときに認証画面に当たる。
  本番URLは保護なしにしておくか、殻からは本番だけを見る。
- **認証Cookie**はWebViewが持つので、ログインは1回で済む。
  ただしPWA側とはCookieが別なので、殻でも一度ログインが要る。
- **端末の戻るボタン**はWebViewの履歴を戻る挙動にする（`@capacitor/app` の
  `backButton` を拾い、履歴が無ければアプリを閉じる）。
- **外部リンク**（もしあれば）は殻の中で開かず、ブラウザへ投げる。

`AndroidManifest.xml` に要るもの:

| 宣言 | 何のため |
| --- | --- |
| `POST_NOTIFICATIONS` | Android 13以降、通知を出すのに実行時の許可が要る |
| `FOREGROUND_SERVICE` / `FOREGROUND_SERVICE_SPECIAL_USE` | 授乳中の常駐サービス |
| `USE_EXACT_ALARM` | 正確な時刻で鳴らす（ストアに出さないので宣言してよい） |
| `WAKE_LOCK` | 画面が消えている間もサービスが動くように |
| `VIBRATE` | 振動 |
| `INTERNET` | 言うまでもなく |

## 6. ビルドと配布

- ビルドは**手元のPCで**行う（Android Studio か `./gradlew assembleRelease`）。
  Windows/Mac/Linuxのどれでもよく、Macは要らない。
  なお、いまのClaude Code側の環境にはAndroid SDKが無いのでビルドは通せない。
  コード生成までがこちら側、ビルドと実機確認が手元、という分担になる。
- **署名鍵(keystore)は1つ作って保管する。** 無くすと同じアプリとして更新できなくなる。
  リポジトリにはコミットしない（`.gitignore` に足す）。
- `.apk` を2台に入れる（USBか、ファイルを送って端末側で「提供元不明のアプリ」を許可）。
- **入れ直しはほぼ不要。** 画面はVercel側で更新されるので、入れ直しが要るのは
  殻の中身（プラグイン・サービスのコード）を変えたときだけ。

## 7. 作る順番

| # | やること | 触るもの | 手元で確かめること |
| --- | --- | --- | --- |
| 1 | 殻を作ってVercelのアプリを開く | `capacitor.config.ts`, `android/` | ログインして普段どおり使えるか。`'PushManager' in window` が false か |
| 2 | 授乳サービスのプラグインを書く | `android/` のKotlin | 画面を消して30分放置し、区切りごとに鳴るか |
| 3 | Web側の差し替え口をつなぐ | `nursingTimer.ts`, `nursingAlarmSync.ts` | 殻では二重に鳴らないか。ブラウザでは今までどおりか |

1〜4がAndroid版の本体で、サーバーは一切触らない。5は段階2。

## 8. 実機で確かめること（作る前に潰しておきたい順）

1. 殻の中で Push API / Notification API が使えないことの確認（§2）
2. リモートURL方式で、Supabaseの認証Cookieが素直に効くか
3. 前面サービスが、画面消灯・数時間の放置を越えて生き残るか（機種依存があるため）
4. アラーム音量に乗せた音が、マナーモードでも意図どおり鳴るか
5. `.apk` を入れた端末で、Vercelを更新したときに殻の中身が追随するか
